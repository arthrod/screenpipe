## Review — src-tauri slice (automation_flows.rs, main.rs, server_core.rs, shortcuts.rs)

**[P2] `apps/screenpipe-app-tauri/src-tauri/src/shortcuts.rs:48-53` — headless fallback loses the press on a fixed 3-second guess.**
When the Home window is missing, `run_demo_shortcut` opens it and then emits `DEMO_SHORTCUT_EVENT` exactly once after `tokio::time::sleep(3s)`. Three seconds is a heuristic for "webview mounted and React effect registered"; on a cold start, slow disk, or first run it can exceed that, and a Tauri event emitted before the frontend `listen()` resolves is dropped silently — the presenter presses ⌃⌥⌘D and nothing happens, with only a possible error log if the emit itself fails (which `emit_to` typically won't, even with no receiver). The emit also fires even when `ShowRewindWindow::Home.show()` failed (shortcuts.rs:44-47 only logs), and the `run_on_main_thread` result is discarded with `let _` (shortcuts.rs:43). Since this path exists precisely for the fragile headless case, consider deriving readiness from the window instead of the clock (e.g. Home signals readiness, or retry the emit a couple of times), or at least document the failure mode for demo rehearsal.

**[P3] `apps/screenpipe-app-tauri/src-tauri/src/automation_flows.rs:26-32` — the command's actual permission scope is wider than the docs claim.**
The module doc (lines 8-11) and the command doc say the key "lets only the Review Screen activate a Flow", but `get_flow_activation_key` is registered app-wide: `tauri_helper::tauri_collect_commands!()` (main.rs:1229) exposes it to every window covered by `capabilities/main.json`, which is `"windows": ["*"]` — any first-party webview's JS (chat, settings, timeline) can fetch the credential and POST an activation with `x-screenpipe-flow-activation`. The real boundary is "desktop app UI vs. out-of-process HTTP callers", which is still the meaningful win over the shared local API key, and remote pages get no IPC (`"local": true`) plus the owned-browser origin blocklist (owned_browser.rs:1597-1621). But "only the Review Screen" overstates it — worth rewording the doc so a future reader doesn't assume per-window gating that doesn't exist.

**[P3] `apps/screenpipe-app-tauri/src-tauri/src/shortcuts.rs:27-28` — the Rust↔TS constant sync has no automated guard on either side.**
`DEMO_SHORTCUT_EVENT` is duplicated as a string literal in `lib/automation-flows/demo-shortcut.ts:17`, and the "keep in sync" rule lives only in comments on both sides. The TS test that exercises the listener mocks the constant with a re-typed literal (`components/automation-flows/__tests__/demo-shortcut-listener.test.tsx:43-47`) instead of importing the real one, so renaming either string passes every test; the new Rust test (shortcuts.rs:643-652) pins the chord's parse but never runs in CI (src-tauri has no CI test job). A one-line frontend test importing the actual `DEMO_SHORTCUT_EVENT` and asserting its value would close the TS side cheaply.

**[P3] `apps/screenpipe-app-tauri/src-tauri/src/shortcuts.rs:529-536` — the demo shortcut is silently dead on trial-locked installs.**
`register_shortcut`'s shared handler wrapper suppresses every press while the onboarding trial lock is held (shortcuts.rs:208-217, `info!` log only). That's the right policy for user shortcuts, but it means a presenter on a trial-locked install pressing ⌃⌥⌘D gets zero feedback — no notification, no toast — which is a nasty demo-day failure mode for a key whose only purpose is demos. If the demo shortcut is meant to work regardless (or should tell the presenter why it didn't), it needs its own handling in the wrapper; otherwise worth a sentence in the doc comment so nobody debugs a "broken" shortcut that is suppressed by design.
