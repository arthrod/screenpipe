## Review: `crates/screenpipe-engine/src/routes/chatgpt_proxy.rs` — second half (streaming relay, error mapping, tests)

**P3** — `crates/screenpipe-engine/src/routes/chatgpt_proxy.rs:523`
**The streamed tool-call shape is untested.** `chat_stream` rewrites each function call to add a
streaming `index` (`chatgpt_proxy.rs:523-534`), but no test exercises `stream: true` with
`function_call` items: `a_streaming_caller_gets_chat_chunks_and_done` (`:838-866`) streams a text
answer and `a_function_call_becomes_an_openai_tool_call` (`:798-821`) is non-streaming. This path
is what n8n agent nodes hit when they stream with tools, and tool-call misassembly is silent
corruption on the caller side. A wiremock test with a `function_call` `output_item.done` plus
`stream: true`, asserting `delta.tool_calls[i].index` and the finish chunk, would pin the shape.

**P3** — `crates/screenpipe-engine/src/routes/chatgpt_proxy.rs:473`
**`response.incomplete` → `finish_reason` mapping has no test.** The `length` / `content_filter`
branches (`chatgpt_proxy.rs:473-481`) are the only caller-visible signal that an answer was
truncated, and they are currently uncovered: every test feeds `response.completed`. One test
streaming `response.incomplete` with `incomplete_details.reason = "max_output_tokens"` and
partial items would prove both the finish reason and that partial streamed items are still
returned.

**P3** — `crates/screenpipe-engine/src/routes/chatgpt_proxy.rs:558`
**`upstream_message` raw-body fallback is untested.** When ChatGPT answers an error with a
non-JSON body (CDN block page, HTML), the raw body is echoed into the OpenAI error message,
clipped at 300 chars (`chatgpt_proxy.rs:550-562`). The clipping is char-boundary safe on
inspection, but since this text is surfaced verbatim to end users through n8n error nodes, a
test for the fallback (non-JSON 502 body → message is the clipped body) and for a multi-byte
character straddling the cut would lock in the safety.

Nothing else to flag in this half: status pass-through for upstream errors (`:184-192`), the
in-stream failure → 502 and usage-limit → 429 mapping (`:427-441`), the chunk/usage/[DONE]
sequence (`:509-548`), and the token handling tests all look correct and match the 15 passing
tests (`cargo test -p screenpipe-engine --lib chatgpt_proxy`). The missing upstream-client
timeout at `:152-160` is already covered by an earlier review comment, so I am not repeating it.
