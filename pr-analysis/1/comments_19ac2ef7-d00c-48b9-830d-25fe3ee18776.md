**[P2] `docs/automation-flows/history/flows-round-two/issues/02-workflows-view-follows-theme.md:27-29` — the doc claims the three dialogs no longer force a white palette; all three still do, and none is touched by this PR.**

The doc's "What changed" says the access notice, the automatic-updates prompt and the cloud processing prompt "no longer force a white palette; they use the app's own tokens". In the tree, all three still hard-code a white inline palette and `git diff origin/main...HEAD` is empty for each: `workflow-access.tsx:54-56` (`background: "#fff", color: "#171815"`), `workflow-tasks-prompt.tsx:165-173` (`colorScheme: "light"`, `background: "#fff"`, light HSL token overrides), `cloud-workflows.tsx:118-126` (same). The theme test's own header comment states the opposite of the doc — "Its dialogs (access notice, automatic updates) keep the light palette on purpose" (`workflows-view-theme.test.tsx:16-18`) — so the doc contradicts both the code and the test it cites. This matters because the doc's Status line (02:9) sends the live checker to "check the access / automatic-updates dialogs": they will find white dialogs in dark mode and cannot tell whether that is the intended end state (as the test comment says) or unfinished work (as the doc says). Please correct whichever is wrong — the doc or the code.
