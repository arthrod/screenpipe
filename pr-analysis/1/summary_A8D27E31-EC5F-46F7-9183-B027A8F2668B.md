# Slice review — Review Screen actions & Learned-from provenance

Reviewer slice: `apps/screenpipe-app-tauri/components/automation-flows/flow-review.tsx` and
`apps/screenpipe-app-tauri/components/automation-flows/flow-learned-from.tsx` (PR #1, diff base `origin/main`).
Both files are new in this PR (476 insertions, no deletions — `git diff origin/main...HEAD --stat`).

## What the slice adds

- **`flow-review.tsx` (244 lines)** — the Review Screen: sticky header with the approval
  actions (Dismiss / Delete / "Review and edit" / "Open in n8n" / Restore / Pause /
  Turn on), activation error notices, summary, the n8n graph, then the three data
  sections (Learned from, Activity, History). It wires the whole screen together from
  `useFlowsLoad` (common.tsx:42-110), `useFlowActivation` (flow-activation.tsx:37-96),
  `FlowDelete`, `FlowGraph`, `FlowLearnedFrom`, `FlowActivity`.
- **`flow-learned-from.tsx` (232 lines)** — the "Learned from" provenance section: one
  card per repetition of the source Detected Task with a strip of up to 3 captures, a
  dialog that opens a capture large with per-capture thumbnails, and "View in timeline"
  only for recorder frames (`frameId > 0`, flow-learned-from.tsx:217).

## How it fits the PR

This is the Review Screen half of the Automation Flows front end (the other half is the
Flows list in `flows-tab.tsx`). It is where the PR's core safety rule is enforced in the
UI: a Flow only ever runs after a user click here ("Turn on" is rendered only when
`canActivate`, flow-review.tsx:151-156, and `api.activate` sends the UI credential,
api.ts:316-322). The plan doc `docs/automation-flows/history/hackathon/flow-front-merge.md:56-78`
describes this exact layout, and the implementation matches it (sticky header, summary,
graph, Learned from, Activity, History).

## Permission gating (focus) — assessment

- The gating seam is correct in this slice: `readVersionId={flow.read.versionId}`
  (flow-review.tsx:66) hands activation the version the user actually loaded, not the
  newest background-read one; `Turn on` is hidden while active/dismissed
  (flow-activation.tsx:92-94); every mutating action sends the UI credential via
  `clickHeaders` (api.ts:229-232), which the engine requires.
- The known hole — on `version_changed` the activation hook re-fetches and activates the
  newest version in the same click (flow-activation.tsx:60-69) — is **already posted on
  the PR** by coderabbitai (Major, on `flow-activation.tsx:60-69`); I did not duplicate it.
  It manifests through this screen's Turn-on button but the fix belongs in the hook.
- The delete-vs-activate and dismiss-vs-activate races are engine-mediated (the engine
  answers `flow_running` / refuses appropriately) and every path surfaces an inline
  error, so I did not raise them.

## Provenance (focus) — assessment

The demo evidence chain is real: demo stages are built from three recorded repetitions
with real recorder frames or embedded key frames
(`lib/automation-flows/demo-task/detected-task.ts:73-110,137-175`), frame lookups go
through the local search API with strict validation
(`lib/automation-flows/demo-task/recorded-evidence.ts:35-96`), and the UI never invents
pixels (broken/unloaded frames render a placeholder, flow-learned-from.tsx:141-146,190-195).
Two honesty problems remain, both posted as comments: load errors render as "no
repetitions" (silent absence-of-evidence), and the stage→repetition equation in
`api.repetitions` (api.ts:392-397) makes the "Times you did it by hand" label and the
count badge truthful only for demo-shaped data — for a genuinely detected task the
stages are phases (`packages/workflows-ui/src/model.ts:95-119`, `observedOccurrences`
per stage) and the real count is `WorkflowMap.repetitions` (model.ts:179), while the
plan doc wanted "one card per repetition … with its captures as a strip (email → form →
ticket)" (flow-front-merge.md:62-63).

## Findings posted (details in comments file)

1. **P2** — Learned-from load error silently rendered as the empty state
   (flow-learned-from.tsx:41-43); sibling Activity section does surface errors
   (flow-activity.tsx:58-62); no test covers the rejection path.
2. **P2** — "Times you did it by hand" count/label maps stages 1:1 to repetitions
   (flow-learned-from.tsx:74,55-57); only truthful for demo-shaped data.
3. **P3** — Timezone-dependent Learned-from test (flows-tab.test.tsx:790) — fails west
   of UTC, proven by the two runs above.
4. **P3** — `CaptureImage` stale `broken` state when the dialog switches captures
   (flow-learned-from.tsx:139-157, used unkeyed at :184-189).
5. **P3** — "Review and edit" / "Open in n8n" clicks are voided promises that can reject
   with no user feedback (flow-review.tsx:130,135; `routeNotificationDeeplink` throws,
   lib/notifications/actions.ts:171), unlike every other control on the screen.

## Considered and cleared (not posted)

- React key `at`+`event` in History (flow-review.tsx:202): engine timestamps are
  rfc3339 with nanosecond precision (crates/screenpipe-engine/src/automation_flows.rs:1090-1096),
  collisions are unrealistic.
- `[...log].reverse()` assumes oldest-first: correct — the engine appends
  chronologically (automation_flows.rs:1091).
- `data-flow-review` set while loading (flow-review.tsx:48): documented deliberate —
  `reviewScreenShown` resolves on "loading or loaded" (lib/workflows/automation-flows.ts:137-144).
- `<img src={capture.image}>`: images are validated data URLs (`EMBEDDED_IMAGE`,
  api.ts:133) or local object URLs; no injection path found.
- Unbounded image prefetch for all captures (api.ts:392-397) is bounded by the
  3-concurrent semaphore + 10 s timeout + 16 MB cap in
  lib/workflows/source-screenshot.ts:58,86-91; fine for the demo's 9 captures, noted
  here rather than posted since the seam is outside this slice.
