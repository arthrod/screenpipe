## Review — `crates/screenpipe-connect/src/connections/n8n.rs` (n8n connection client)

**[P2] `crates/screenpipe-connect/src/connections/n8n.rs:98-104` — auth failures surface as raw reqwest errors instead of an actionable message.**
The new API check ends in `error_for_status()?` with no context, so a wrong key or wrong URL reaches the UI (via `test_connection` at `connections_api.rs:610-613`, which returns `e.to_string()`) as reqwest's `HTTP status client error (401 Unauthorized) for url (…)` — or, for a malformed `api_url` such as a missing scheme, a bare `relative URL without a base`. The engine's own n8n client treats exactly this case as a setup problem — `N8nApi::send` maps 401/403 to `FlowError::Unauthorized` with the comment "report it as a setup problem of the n8n connection, not as n8n being down" (`automation_flows.rs:638-645`) — yet the connect-time check, whose whole job is validating setup, produces the least actionable message of the two. Please map 401/403 to something like "n8n rejected the request (401) — check the API URL and API key" and wrap network errors with `.with_context(|| format!("cannot reach n8n at {base}"))`. Minor related UX: with API + webhook both configured, an API-check failure discards the `done` progress and never tests the webhook, so the user fixes one problem per click without knowing the other half is fine.

**[P2] `crates/screenpipe-connect/src/connections/n8n.rs:107-115` — the webhook branch of the rewritten `test()` has no test coverage.**
This PR makes `webhook_url` optional and branches on it (n8n.rs:85-93), but the new tests only cover the API path (n8n.rs:172-196), half-configured/empty rejection (n8n.rs:199-212), and secret storage. Nothing exercises webhook-only credentials — the only configuration that existed before this PR (the old code required `webhook_url` via `require_str`) — or the combined api+webhook path with the joined message (n8n.rs:116), and `mod.rs` never calls `N8n::test` either. This branch is where a flipped condition would silently break the connect flow of every existing webhook-only user. Two wiremock tests would close it: webhook-only → expects one POST and returns "test event sent to n8n webhook"; api+webhook → both stubs hit once and the message is `"n8n API reachable; test event sent to n8n webhook"`.

**[P3] `crates/screenpipe-connect/src/connections/n8n.rs:113` — `error_for_status()` on the webhook POST echoes the secret webhook URL into the error string (pre-existing).**
reqwest status errors render `for url (<request url>)`, and for this POST the request URL *is* the `webhook_url` credential (field is `secret: true`, n8n.rs:24; the design keeps the target server-side, n8n.rs:19). `test_connection` hands `e.to_string()` straight to the client (`connections_api.rs:610-613`), so a failing webhook test leaks the secret URL into the UI response and error logs. This predates the PR — the old code had the identical pattern — so it is not a regression, but since this function was rewritten with error handling in scope, mapping the webhook failure to a URL-free message (e.g. "n8n webhook test failed with 500") would also close the secret-echo.

**No action needed (verified, for the record):** the API key goes out on `X-N8N-API-KEY` (n8n.rs:101) and is marked `secret` so `safe_connection_config`'s default-deny keeps it out of read APIs and model context (n8n.rs:38, tested n8n.rs:136-151); the injected client's same-origin-only redirect policy means the custom-header credential can't be carried off-origin on a 3xx (mod.rs:327-346); timeouts are bounded by `ConnectionManager`'s client (10s connect / 30s request, mod.rs:282-296) on both production call paths; and `instance_url`/`api_credentials`/`API_KEY_HEADER` are sensibly reused by the engine's flow client (automation_flows.rs:618,636) instead of duplicated. `cargo test -p screenpipe-connect`: 223 passed, 0 failed, 1 ignored.
