## How it fits the PR

The widening is the enabler for this PR's Automation Flows feature. `crates/screenpipe-engine/src/automation_flows.rs` is a new file in this PR (absent on `origin/main`); it imports `crate::routes::workflows::{read_catalog, workflow_id as task_id_of, WorkflowCatalogSource}` (`automation_flows.rs:33`) — impossible with `pub(super)` — and calls `read_catalog` at `automation_flows.rs:1252` inside `source_moment`, which finds the first-seen moment (earliest evidence/frame timestamp) of a Detected Task to populate the Flow's `source_moment` timeline deep link (`automation_flows.rs:1303-1320`, field at `:352`). `server.rs`'s only workflow-related change is nesting the new flows router (`server.rs:1502`); existing routes and their layers are untouched.

## API compatibility (stated focus, `workflows.rs`)

- **HTTP surface: no change.** Route mount points for `/workflows`, `/workflows/:id`, `/workflows/edits` are identical (`server.rs:1043,1050-1051`); the `server.rs` diff only adds the nested flows router plus `pub mod chatgpt_proxy` in `routes/mod.rs`. `read_catalog` is crate-internal, so `pub(crate)` cannot affect external consumers. `MAX_CATALOG_BYTES` correctly stays `pub(super)` (`workflows.rs:24`) — minimal, deliberate change.
- **Behavior of `read_catalog` unchanged**: 32 MiB cap + schemaVersion-5 gate + `catalog.backup.json` fallback + `discard_screenshot_pixels` all intact (`workflows.rs:49-79`).
- **P2 — new consumer bypasses the module's history-access invariant.** Both HTTP handlers in this file filter catalog output through `visible()`/`HistoryAccessPolicy` (`workflows.rs:171` and `:210`), with an explicit rule against trusting the catalog date (`workflows.rs:94-95`) and a dedicated test (`workflows.rs:356-364`, passing). The consumer the widening enables — `source_moment` (`automation_flows.rs:1251-1284`) — returns the earliest evidence/frame timestamp and `frameId` for a task with **no** policy filter; `rg -n "visible\(|history_access" crates/screenpipe-engine/src/automation_flows.rs` returns nothing, and the flows router sits on the same local server behind the global middleware stack (`server.rs:1502`, `pipe_permissions_layer` at `:1591`). Consequence: a caller that can read flows learns "this task was first seen at T" plus a frame pointer even when that content is outside the user's history window. Frame *contents* still require the policy-checked `/frames/:id` endpoints (`workflows.rs:234-241` shows those checks exist), so this is metadata-level exposure, not full evidence disclosure. `automation_flows.rs` is outside my slice — the deep review belongs to its owner — but the widened symbol is what enables it, so it is flagged here.

## Authorization on edit operations (stated focus, `workflow_edits.rs`)

- The handler is sound where this PR could have regressed it: `edit` rejects any request carrying pipe permissions (403, `workflow_edits.rs:217-222`), serializes writers on `WRITER` (`:223`), enforces revision conflicts (`apply_edit`, `:98-100`), and writes via the atomic `persist` under the same lock. `cargo test -p screenpipe-engine --lib "routes::workflow_edits"` → **12 passed**, including `agent_capabilities_cannot_submit_manual_edits` (`:458-478`) and the storage-failure roundtrip (`:496-554`).
- **P2 (pre-existing, not introduced by this PR)** — the owner-only gate is only as strong as the middleware's token classification. `OptionalPipePerms` (`routes/search.rs:22-45`) yields `None` for **both** token-less requests **and** `Bearer sp_pipe_*` tokens absent from the registry: the middleware deliberately treats unregistered tokens ("likely hallucinated by the model") as regular user requests (`pipe_permissions_middleware.rs:110-117`, no-token path `:121-122`). So an agent that omits or fabricates its token passes the "Only the desktop owner" gate at `workflow_edits.rs:217-222`; the gate stops only validly registered pipe tokens (the compliant Pi-extension path). Verified pre-existing: `git show origin/main:crates/screenpipe-engine/src/pipe_permissions_middleware.rs` shows identical behavior at the merge base. The PR does not regress this, but it ships agent-facing automation (chat skill, flows) around the same catalog, which raises the stakes. Suggested hardening: on owner-only mutation endpoints, reject `sp_pipe_*`-prefixed tokens that are not in the registry — defense in depth for exactly the hallucination case the middleware comment names. Posted as a comment since this file is the slice's stated authorization focus; the lead reviewer should weigh that it is pre-existing.
