## 2. The real change: `packages/workflows-ui/src/screenshots.ts`

`isEmbeddedScreenshot` (screenshots.ts:8-11) is new: true when `frameId` is a safe integer `< 0` **and** `dataUrl` matches `^data:image/(jpeg|png|webp);base64,`. `stageScreenshots` (screenshots.ts:14-20) previously kept only `frameId > 0`; it now also keeps embedded captures. `frameId === 0` stays excluded (both branches fail), consistent with the doc comment that a negative ID never names a recorder frame.

### How it fits the PR

This is the display half of the PR's "demo task setup adds embedded and recorder-backed evidence" (coderabbit's summary table). The producer is `apps/screenpipe-app-tauri/lib/automation-flows/demo-task/detected-task.ts`: a shared counter decrements per capture, so IDs are unique (−1…−9 across the three repetitions; detected-task.ts:136-141); embedded captures get `dataUrl` from the bundled `.webp` fixtures and `visualVerified: true`, recorder-backed ones get a positive `frameId` and empty pixels (detected-task.ts:159-166). Without this filter change those scripted captures were silently dropped everywhere, so the demo evidence never rendered.

### Correctness — checked, holds

- Serialization round-trip: `serializeWorkflowData` strips `dataUrl` only for `frameId > 0` (screenshots.ts:28-29), so embedded pixels persist and recorder-frame copies stay out of saved state; covered by `demo-task-evidence.test.tsx:27-32` (asserts `[[-1, pixels], [42, ""]]` after a JSON round-trip).
- Dedup is still per-stage by `frameId`; the producer's shared counter prevents collisions within a task.
- A negative-ID entry with an invalid/empty `dataUrl` fails the regex and is dropped rather than falling back to the recorder — deliberate, and pinned by `step-evidence.test.tsx:145-155` (one image renders, recorder `load` never called).
- Consumer gating is right: embedded captures get no replay button (workflow-step-evidence.tsx:80 — no recording exists to open) and render from their own pixels without a recorder lookup (workflow-step-evidence.tsx:114-118); positive-ID legacy copies still resolve through the recorder.

### Security — checked, holds

The data-URL gate is fail-closed and anchored: only `jpeg|png|webp` base64 passes, so `data:image/svg+xml` (script-capable) and non-base64 variants can never become embedded evidence, and embedded dataUrls reach the DOM only as `<img src>` (workflow-step-evidence.tsx:124, sop-screenshot.tsx:54, workflow-replay.tsx:107). The anchored regex is O(1) even on multi-MB base64 strings (only start position is tried). Case-sensitivity (uppercase MIME rejected) is fail-closed, matching the lowercase producer. This code is UI-catalog work, not the recording hot path; no per-frame allocation or callback-blocking concern under AGENTS.md's hot-path rules.

### Performance

`stageScreenshots` is O(n) per call and called during render in several components (guide.ts:149,170; catalog.ts:168,181; fixture-platform.ts:416,499) — the added cost is one regex test per non-positive candidate. Pre-existing no-memoization pattern, unchanged profile.

## 3. Findings (details in the posted comments)

1. **P2 — embedded captures now flow into SOP video scenes and break video generation.** `guideScreenshot` (guide.ts:160-167) can return an embedded capture; scenes get `imageFrameId: -1` plus the working dataUrl (packages/workflows-ui/src/guide-video.ts:37-40, review set at :91). The desktop builders prefer the frame ID: apps lib `guide-video.ts:78-79` awaits `loadVideoScreenshot(-1)`, which throws by design for non-positive IDs (`original-screenshot.ts:7`), failing the whole generation; `video-project.ts:49-55` instead catches, overwrites the dataUrl with `null`, and silently drops the scene image. Panel preview shows a spurious "Original screenshot unavailable" note (guide-video-panel.tsx:167-168 → sop-screenshot.tsx:30-43). Both builder files are pre-existing (not in the PR) — the PR's filter widening is what routes negative IDs into them. Minimal fix at packages/workflows-ui/src/guide-video.ts:40 (only pass `imageFrameId` when `> 0`); both builders already fall back to `scene.image`. Trigger: creating a video for an SOP built on a workflow whose step images are embedded fixtures — exactly what the demo task injects.
2. **P3 — latent negative frameId into `CapturedMomentButton`** via `workflow-replay.tsx:98,114`; currently unreachable (button renders null without `openCapturedMoment`, workflow-replay.tsx:27; the player only mounts when it's absent, workflow-step-evidence.tsx:49). Hardening: gate on `frameId > 0`.
3. Not posted, design observation: catalog metrics (catalog.ts:168,181) now count embedded fixtures toward `screenshotCount`/coverage, since the producer marks them `visualVerified: true` (detected-task.ts:160) — intended-looking for demo data, but it changes what those statistics measure. `workflow-replay.tsx:107` additionally displays embedded pixels as replay posters, which is the intended demo behavior.
