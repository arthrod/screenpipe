## What this slice is in the whole PR

This is the webview half of the hackathon demo shortcut ⌃⌥⌘D. The native side registers the global chord and emits an event to the Home window (`src-tauri/src/shortcuts.rs:26-28,529-536`); this slice owns everything after that event:

- `demo-shortcut.ts` — the handler: per-listener in-flight guard (one press runs, later presses return `{ignored: true}`, `demo-shortcut.ts:33-38`), runs `resetFlows` concurrently with the task reinstall and gates the notification on it (`demo-shortcut.ts:41-51`), wraps installer failures into presenter toasts (`demo-shortcut.ts:53-62`). It deliberately contains **no shortcut parsing** — the chord is parsed and registered in Rust; the only cross-language contract is the event-name string.
- `demo-shortcut.test.ts` — 8 handler-orchestration tests (happy path, suppressed notification, unreachable notifier, unreadable catalog, reset-before-notify ordering, notify-despite-reset-failure, per-press body uniqueness via invisible marks, in-flight guard). All pass (see checks).
- `demo-task/catalog.ts` — pure `upsertTask` that installs the scripted task into the desktop-owned workflow catalog: bumps task and catalog revisions so a stale open Task Page reloads (`catalog.ts:25-26`), puts the demo task at rank 1 and re-ranks the rest (`catalog.ts:32`).
- `demo-task/recorded-evidence.ts` — finds each of the 9 scripted captures in the machine's own recordings via the local `/search` API: one ascending + one descending page around the key-frame time (`recorded-evidence.ts:38-44`), 503 retry with backoff and serialized searches (`recorded-evidence.ts:45-55`), per-capture failure never throws (`recorded-evidence.ts:76-81`), one-frame-one-capture dedup nearest to the key frame (`recorded-evidence.ts:86-95`).

Shared modules (`demo-task/detected-task.ts`, `find-automation.ts`) are adjacent context I read but did not review as slice.

## Focus verdicts

### 1. Shortcut parsing/matching correctness incl. platform modifiers — OK, one doc nit

- Event name matches verbatim on both sides: `DEMO_SHORTCUT_EVENT = "shortcut-automation-flows-demo"` (`demo-shortcut.ts:17`) vs `pub const DEMO_SHORTCUT_EVENT: &str = "shortcut-automation-flows-demo"` (`shortcuts.rs:28`). Rust emits with `app.emit_to("home", ...)` (`shortcuts.rs:34,50`); the listener uses window-scoped `getCurrentWebviewWindow().listen` so only Home reacts (`components/automation-flows/demo-shortcut-listener.tsx:36`), and its test models Tauri v2's real dispatch rule and proves non-Home windows ignore the event (`demo-shortcut-listener.test.tsx:8-23,77-81`). Correct.
- Chord parsing lives entirely in Rust: `parse_shortcut` maps `SUPER|CMD|COMMAND → Modifiers::META` (`shortcuts.rs:560-572`), and `demo_shortcut_is_control_option_command_d` (`shortcuts.rs:643-652`) pins `DEMO_SHORTCUT = "Control+Alt+Super+D"` (`shortcuts.rs:26`) to CONTROL|ALT|META+D. On macOS META = ⌘, so ⌃⌥⌘D is right there. On Windows/Linux META is the Win/Super key, so the actual chord there is Ctrl+Alt+Win+D while every TS comment says "⌃⌥⌘D" (`demo-shortcut.ts:4`, `find-automation.ts:4`, `demo-task/detected-task.ts:10`) — doc-only nit, posted as P3.
- Registering the demo shortcut in every build (production impact: deletes real Flows, writes the user's real catalog) is **already commented on the PR** by coderabbitai[bot] (`src-tauri/src/shortcuts.rs:527-536`, review comment id 4330471436). Not duplicated.
- I verified the engine search contract recorded-evidence.ts relies on: `/search` accepts `window_name` (`crates/screenpipe-engine/src/routes/search.rs:155`) and `q` (`search.rs:124`), `order` deserializes `"ascending"/"descending"` (`crates/screenpipe-db/src/types.rs:710-719`), request `content_type=ocr` matches the lowercase `ContentType` (`types.rs:208-215`), and the response items are internally tagged `#[serde(tag = "type", content = "content")]` with the un-renamed variant name, i.e. `"type":"OCR"` with `frame_id/timestamp/app_name/window_name/browser_url` fields (`crates/screenpipe-engine/src/routes/content.rs:32-42,123-146`) — so `recorded-evidence.ts:40` and `recorded-evidence.ts:62-64` are both correct (I initially suspected a casing bug; it is not one). What I did **not** verify: how the engine tokenizes `q` (the code comment "requires each of them", `recorded-evidence.ts:23`, matches the fake server in `infra/automation-flows/demo/recorded-evidence.test.ts:18` but I did not trace the real matcher in the DB layer).

### 2. Assertion breadth (demo-shortcut.test.ts) — good orchestration coverage, one contract gap

The module has no parser, so "chord/invalid-input" assertions cannot live here (the chord test is `shortcuts.rs:643-652`). What the file does cover is the handler state machine, and it covers it well, including the two subtle traps: notification ordering after reset (`test.ts:84-91`) and the invisible-mark body uniqueness (`test.ts:104-121`). Gaps found and posted:

- **P2:** nothing pins `DEMO_SHORTCUT_EVENT` to the Rust literal. The listener test mocks the whole module with a hardcoded literal (`demo-shortcut-listener.test.tsx:45-48`) and emits the literal itself (`:73,79`), so a TS-side rename passes all 10 tests while the native press becomes a silent no-op. One-line test importing the real constant would close it.
- **P3:** `openTask` rejection after a successful notification (`demo-shortcut.ts:61`) propagates to the listener's catch (`demo-shortcut-listener.tsx:37`) and toasts "Demo not started" — misleading (the demo did start; the notification is out) — and untested.

### 3. Catalog data matches infra/automation-flows/demo/catalog.ts — match by construction

`infra/automation-flows/demo/catalog.ts` does not duplicate the data at all: it re-exports `upsertTask` and `Catalog` from the app module (`infra/automation-flows/demo/catalog.ts:12,17`), and `infra/automation-flows/demo/demo.ts:15-17` imports the task/recorded-evidence modules directly. There is a single source of truth, so drift between app and infra is impossible unless someone copies the file. Field-level checks I did by inspection: `EMPTY_QUALITY` (`catalog.ts:11-15`) matches `AnalysisQuality` field-for-field (`packages/workflows-ui/src/model.ts:230-242`), and the fresh-catalog base (`catalog.ts:19-22`) satisfies every required `WorkflowAnalysis` field incl. the `schemaVersion: 5` literal (`model.ts:244-260`); the infra validator independently requires `schemaVersion === 5` (`infra/automation-flows/demo/catalog.ts:27-30`). Behavior covered by the infra suite: "creates a catalog the app loads, and reinstalls without touching other workflows" and "reset clears only the demo answers" — both pass. Note: `upsertTask` rewrites `rank` on every workflow in the user's real catalog (`catalog.ts:32`) — intended (demo task on top, relative order preserved), and the same reset/install path is what the existing coderabbit comment on `shortcuts.rs` already criticizes at the product level.

### 4. Evidence mapping (webp assets) — 9/9 exist, enforced by a test

`EVIDENCE_CAPTURES` (`demo-task/detected-task.ts:112-114`) references exactly 9 images (r1/r2/r3 × email/form/ticket). `ls apps/screenpipe-app-tauri/public/automation-flows/demo-evidence/` shows exactly those 9 `.webp` files; `git diff origin/main...HEAD --stat` shows all 9 as binary additions in this PR; `file r1-email.webp` confirms a real WebP (RIFF/WebP VP8 1280x687). Runtime paths agree: the app fetches `${EVIDENCE_PATH}/${image}.webp` with `EVIDENCE_PATH = "/automation-flows/demo-evidence"` (`detected-task.ts:16`, `find-automation.ts:70`), served from `public/`; the infra script joins the same `public` dir (`infra/automation-flows/demo/demo.ts:25,28`). The existence invariant is actively tested — `infra/automation-flows/demo/catalog.test.ts:30` reads every `EVIDENCE_IMAGES` entry from disk — and that test passed in my run.
