## What this slice is

`api.ts` is the self-declared "only seam between the Automation Flows UI and the rest of the app" (api.ts:5-8): a typed client (`flowsApi`) over the engine's `/automation-flows/*` routes, a typed error class (`FlowsApiError`, api.ts:247-255), the UI-credential plumbing (`activationKey`/`clickHeaders`/`notificationApiHeaders`, api.ts:219-245), and the small navigations the Flows screens need (open in n8n, chat prefill, timeline/task-page handoff, api.ts:370-455). It sits at the center of the PR's app layer: every component under `components/automation-flows/` consumes `flowsApi`, the notification "Retry" action borrows `notificationApiHeaders` (`lib/notifications/actions.ts:10,327`, `components/notification-handler.tsx:258`), and the browser dev loop has a parallel mock (`mock.ts`) exercised by the tests.

**Wire-shape parity** — checked field by field: engine `Flow`/`FlowSummary`/`FlowNode`/`SourceMoment`/`ActivationEvent` structs with `serde(rename_all = "camelCase")` (automation_flows.rs:327-353, 365-371) match the client types (api.ts:15-63); `FlowRun` (activity.rs:45-58) matches api.ts:69-80 including outcome values `ticket|ignored|abstained|failed|done` (activity.rs:121-136); `LastExecution.status` is exactly `success|running|error` (automation_flows.rs:801-806) matching api.ts:18; `derive_status` yields exactly `active|dismissed|draft|needs_review|paused` (automation_flows.rs:1146-1159) matching `FlowStatus` (api.ts:15); `HealthReport` fields `checkedAt/n8n/notified/pendingNotifications/deletedDrafts` (health.rs:111-127) match `FlowsHealth` (api.ts:86-95), and `n8n` values `reachable|unreachable|unauthorized|not_configured|failed|unknown` (health.rs:129,250,272-295) match api.ts:88 exactly.

**Error contract parity** — engine `FlowError::into_response` emits `{"error": code, "detail": ...}` (automation_flows.rs:481-585); `request()` parses exactly that (api.ts:267-274). All 12 engine codes reachable from client-called routes are in `SERVER_CODES` (api.ts:193-206): I checked each variant of the engine's `FlowError` enum against the list. Codes outside the list (`flow_not_found`, `run_not_found`, `task_not_found`, `invalid_workflow`, `internal`, …) fall to 404→`not_found` or `unknown` with the detail preserved — the intended degradation, and tested (`__tests__/api.test.ts:163-178`, including `404 flow_not_found → not_found`).

**Credential handling** — client header `x-screenpipe-flow-activation` (api.ts:209) equals engine `ACTIVATION_HEADER` (automation_flows.rs:138); engine compares with a constant-time-ish `key.matches` against the Tauri-held key (automation_flows.rs `from_user`; command at `src-tauri/src/automation_flows.rs:30`, binding at `lib/utils/tauri.ts:755`). `RETRY_PATH` (api.ts:235) matches the exact URL the engine writes into failure notifications (`failures.rs:268` `format!("/automation-flows/{flow_id}/runs/{execution_id}/retry")`); its `[A-Za-z0-9_-]` charset is *the same* charset the engine's own `valid_workflow_id` enforces (automation_flows.rs), and the `trigger-<millis>` fallback id also matches. Both notification consumers gate on `isLocalApiUrl(url)` before fetching (`actions.ts:321-329`, `notification-handler.tsx:252-260`), so the credential only ever rides to the local engine. This closes the leak angle of the already-posted coderabbit comment on notification provenance (that comment's core point stands; not duplicated here).

## Quality assessment

This file is in very good shape. Strengths: the error vocabulary is a closed, tested set that mirrors the engine enum; `encodeURIComponent` on every path id (api.ts:281,285,295,317,330,343,354,363); the `require_json` engine middleware is respected on every mutating call (verified per-call, incl. DELETE at :345); the mock/browser/real triple is exercised by tests that assert exact paths, headers, and bodies (api.test.ts:59-134); chat prefill never sends anything itself (api.test.ts:186-197,219-228).

Notable risks / things I could not fully verify:
- **`repetitions()` duplicates workflows-ui logic** (the one posted comment, P3): `stageCaptures`+`EMBEDDED_IMAGE` (api.ts:133-146) re-implement `stageScreenshots`+`isEmbeddedScreenshot` (`packages/workflows-ui/src/screenshots.ts:4-20`) because the package's exports map (`packages/workflows-ui/package.json`) doesn't expose `./screenshots`. Verified the copies are currently character-equivalent, including the `jpeg|png|webp` restriction (SVG fixture images are excluded by both).
- **`request()` resolves a 2xx with an unparseable body to `null as T`** (api.ts:264-265, P3): not reachable with today's engine (every 2xx handler returns `Json`), but the seam's type honesty has a hole.
- Deliberate degradations I verified and do **not** flag: `activationKey()` swallowing Tauri errors to `null` (api.ts:219-226 — the engine then refuses observably with `activation_requires_user`, tested at api.test.ts:149-161); the blanket `NEXT_PUBLIC_SCREENPIPE_WEB_DEV` check in `loadCapture` (api.ts:152) mirrors the app-wide `browserPreview` convention that omits screenshot loading in any web dev mode (`lib/workflows/desktop-platform.ts:132`); no client-side timeout on `retry` while the engine waits up to 180 s (`retry.rs:41`) — `localFetch` is plain fetch without timeout app-wide (`lib/api.ts:232-262`), so hanging is pre-existing behavior, and the UI has busy states.
- I did not run the engine's Rust test suite (out of my slice; the parity claims above are from reading the handlers, plus the client-side tests) and did not drive the real app.
