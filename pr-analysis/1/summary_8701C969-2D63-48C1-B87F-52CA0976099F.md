# Slice review: `chatgpt_proxy.rs` lines 1-470 — request validation & upstream auth (security lens)

## What this slice changes

`crates/screenpipe-engine/src/routes/chatgpt_proxy.rs` (new file) adds a `chatgpt/<model>[:<effort>]`
escape hatch on the existing local `/v1/chat/completions` proxy: instead of forwarding to
`api.screenpipe.com`, requests whose model name carries the `chatgpt/` prefix are translated to the
Codex Responses API (`https://chatgpt.com/backend-api/codex/responses`, line 32) and answered from the
user's personal ChatGPT sign-in. Lines 1-470 (my slice) cover:

- Model-name parsing and dispatch detection: `ChatGptModel::parse` (`chatgpt_proxy.rs:47-61`),
  `requested_model` (`chatgpt_proxy.rs:66-72`).
- Upstream auth material: OAuth token read/refresh via `spawn_blocking(screenpipe_core::pipes::read_chatgpt_oauth_token)`
  (`chatgpt_proxy.rs:78-82`) and extraction of the `chatgpt_account_id` claim from the JWT payload
  (`chatgpt_proxy.rs:115-127`), sent as `Authorization: Bearer` + `chatgpt-account-id` headers
  (`chatgpt_proxy.rs:152-160`).
- Request translation Chat Completions → Responses: `responses_request` (`chatgpt_proxy.rs:215-296`),
  `text_of` (300), `user_content` (319), `function_tool` (343), `text_format` (365), and the SSE
  reader `read_stream`/`failure` (397-441).

## How it fits the whole PR

Dispatch happens inside the pre-existing cloud proxy handler: `cloud_proxy.rs:34-35` calls
`requested_model(&body)` on every `/v1/chat/completions` body and routes ChatGPT-prefixed models to
this module. The route is mounted with a 50MB body limit (`server.rs:1271-1275`). The rest of the file
(443-934, other reviewer's slice) shapes the answer back into Chat Completions JSON/SSE.

## Security assessment (the slice's focus)

What I checked and consider sound:

- **No SSRF**: the upstream URL is a compile-time constant used unconditionally
  (`chatgpt_proxy.rs:32,97`); the parameterized URL exists only for tests (`chatgpt_proxy.rs:131-136`).
- **No header injection**: token and account id go through reqwest's `bearer_auth`/`header`, which
  validate header values; a hostile `chatgpt_account_id` string in the stored token cannot inject CRLF
  (`chatgpt_proxy.rs:154-155`).
- **Token exposure**: the bearer token only ever goes to the constant chatgpt.com URL; reqwest's
  default redirect policy strips sensitive headers on cross-host redirects, so the caller (local
  process) cannot redirect the credential anywhere.
- **JWT payload is decoded without signature verification** (`chatgpt_proxy.rs:115-127`) — acceptable:
  the token comes from the local secrets store, and chatgpt.com verifies the signature server-side;
  the claim is only used as a routing header. Empty/absent claim degrades to a clear 503
  (`chatgpt_proxy.rs:90-96`).
- **`store: false` is hardcoded** (`chatgpt_proxy.rs:269`) so conversations are not retained on the
  OpenAI side — good privacy default; `"stream": true` is forced and buffered server-side.
- **Caller identity**: the route adds zero authentication of its own; it inherits the engine's
  middleware — `api_auth` is off by default (`server.rs:424`), CORS is restricted to localhost origins
  (`server.rs:905-914`), and the desktop app wires LAN-access auth separately
  (`recording.rs:1613-1627`). So any local process can spend the user's ChatGPT subscription, but that
  is exactly the pre-existing trust model of the cloud proxy this file plugs into, and the module doc
  states it ("any OpenAI client on the machine", `chatgpt_proxy.rs:6-7`). Not a regression of this PR.
- Request-body size is bounded by the route limit (`server.rs:1274`), and upstream error bodies are
  clipped to 300 chars before being echoed (`chatgpt_proxy.rs:559-561`, second slice).

Findings posted (details in comments file): auth work (token read + possible ~35s refresh-lease wait)
runs before request validation, and a `spawn_blocking` JoinError is flattened into a misleading
"connect ChatGPT" 503 (`chatgpt_proxy.rs:78-89`, P2); unsupported `tool_choice`/`response_format`
values are silently dropped while unsupported roles/tools hard-error (`chatgpt_proxy.rs:276-294,365-385`, P3);
the body is fully JSON-parsed twice per ChatGPT request and once per cloud request just for dispatch
(`chatgpt_proxy.rs:66-72,137`, `cloud_proxy.rs:34`, P3). The missing upstream timeout
(`chatgpt_proxy.rs:152-160`) is already covered by coderabbitai on this PR — not re-posted.

## Quality / tests

- `cargo test -p screenpipe-engine --lib chatgpt_proxy` → **15 passed, 0 failed, 1781 filtered out**
  (ran this session; covers model parsing, effort suffix/override, account-id extraction, translation,
  streaming, upstream error mapping, cut stream, bad request never reaching upstream).
- Test gaps: `response_format: {"type": "json_object"}` path (`chatgpt_proxy.rs:368`) is untested, and
  the silent-drop behaviors (tool_choice, response_format) have no test pinning them.
- The slice is generally well written: small pure functions, honest error messages, behavior pinned by
  focused tests. The main maintainability smell is the inconsistent failure policy: unknown roles and
  non-function tools are rejected by name (`chatgpt_proxy.rs:256,344-346`), while unknown
  tool_choice/response_format/reasoning_effort values are silently ignored
  (`chatgpt_proxy.rs:279-284,383,291`).
