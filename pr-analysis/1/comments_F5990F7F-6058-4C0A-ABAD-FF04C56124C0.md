Four findings, none blocking:

**[P2] `crates/screenpipe-engine/tests/automation_flows_test.rs:4799-4802`** — The test name promises "…and sooner while n8n is down", but nothing asserts it. `wait_for_health` (:4769-4778) polls for up to 5 s, so the run would pass even if the engine never re-checked sooner than `every` (300 ms) while n8n was unreachable — or ignored the `retry` field (:4782-4785) entirely. The pacing logic itself is unit-tested (`health.rs:458-469`), so the behavior is not untested, but this integration test claims to prove something it does not measure, which misleads future maintainers about the suite's coverage. Either count `flow_list_reads` (the helper at :4748 already exists) across a bounded down window and assert reads land at roughly the retry period, or drop the clause from the name and leave that property to the unit test.

**[P3] `crates/screenpipe-engine/tests/automation_flows_test.rs:4536`** — "n8n down" is modeled as the hard-coded `http://127.0.0.1:9` (also at :4799), while the file already has `closed_port_url()` (:752-757, used at :807 and :1891), which binds an ephemeral port and drops it — a port guaranteed to refuse connections. Port 9 works on macOS/Linux today, but on a host where the discard port is silently filtered rather than refused, these two tests would stall on connect (until the engine's own timeout) instead of seeing the fast refusal the assertions expect. Using the existing helper here too makes "unreachable" deterministic everywhere in the file.

**[P3] `crates/screenpipe-engine/tests/automation_flows_test.rs:4716`** — `assert!(waited < Duration::from_millis(100))` puts an absolute 100 ms budget on an in-process HTTP round trip. The property is worth pinning (a failure report must not queue behind the switch-off's 300 ms write hold, which would cost ≥ ~180 ms here), and the test passed in this review's run — but on a loaded CI runner, scheduling jitter alone can push a non-queued call past 100 ms and flake it. A bound derived from the scenario (e.g. fail iff `waited` approaches the 300 ms deadline, say 150-200 ms) keeps the discrimination strict while tolerating load.

**[P3] `crates/screenpipe-engine/tests/automation_flows_test.rs:4426`** — `workflow["nodes"][1] = second_step()["nodes"][1].clone();` grafts the summary node into `chat_workflow()` by positional index into `second_step()`'s node array. If `second_step()` is ever reordered, this silently wires a different node and the `screenpipeApi` assertions below become confusing to debug. A small named helper (`fn summary_node() -> Value`) shared by `second_step()` (:4235-4252) and this test would make the coupling explicit and reorder-safe.
