## Spec review — `docs/pii-release-gate.md` @ origin/main (focus: consent model + never-leak guarantees)

**Never-leak guarantees: stated unambiguously — this half is in good shape.** The doc consistently scopes what it guarantees and names what it does not:
- Banner disclaimer: "This is not a universal product privacy guarantee." (`docs/pii-release-gate.md:3`)
- Receipt semantics bounded: "A completion receipt proves processing under that contract; it does not prove perfect detection recall." (`:20`)
- Transport boundary bounded: "Admission is the transport handoff boundary; it cannot retract bytes already sent or remove old cloud copies." (`:22`)
- Empty-result caveat: "An empty protected result must not be treated as proof that matching history does not exist." (`:36`)
- Bypass named outright: "An agent with unrestricted filesystem access can bypass an HTTP gate." (`:83`), with the covered/uncovered boundary list at `:82-83`.
This is the right shape for a privacy-gate spec: precise, falsifiable claims instead of a marketing "never leaks" promise.

**Consent model: absent — the substantive gap (P2).** The doc defines processing/admission mechanics but never states the consent story:
1. The enabling control is never named. The companion evidence screenshots show a Settings "PII Removal" toggle with Basic/Smart modes and an "Apply & restart" unsaved-changes bar (`components/settings/privacy-section.tsx` on origin/main; bar string at `privacy-section.tsx:1739`), but the spec never mentions the toggle, the default state, or the restart semantics.
2. OFF-state semantics are only implied: "including while protection is disabled" (`:28`) and "explicitly unavailable under protection" (`:82`) let a careful reader infer that disabling protection re-exposes every gated surface, but the pivotal fact is never stated.
3. Remote egress of private content is never stated — the most consent-relevant fact in the whole design. Cloud processing appears only obliquely: "configured backend" inside the policy identity (`:20`), "remote requests remain indivisible" (`:30`), and the exclusion of remote HTTP response bodies/URLs from logs "because they can echo private source data". Meanwhile the UI screenshot promises "your device verifies the open-source build before sending anything" — a consent-relevant claim (attested enclave, what is sent) that the spec neither owns nor defines. A spec governing admission of private data should say in one place: what leaves the device, under which mode, to which endpoint class, and which control turns it on. Suggested in the posted comment: a short "Enabling and consent" section.

**Minor (P3):** `x-screenpipe-privacy-completeness: unknown` (`:36`) shows one literal value without defining the header's value space — unclear whether `unknown` is a constant or one state among several.

**Minor (P3):** `<!-- doc-verified: c288183019 -->` (`:6`) references a commit that exists but is **not reachable from origin/main** (`git merge-base --is-ancestor c288183019 origin/main` → not ancestor; `git branch -r --contains c288183019` → only `origin/fix/pii-release-gate`).
