## What the slice changes

### pi.rs — chat-only `automation-flows` skill wiring

Four diff hunks (`git diff origin/main...HEAD -- crates/screenpipe-core/src/agents/pi.rs` shows hunks at
869, 907, 950, 4966):

1. **Baseline skill list** (pi.rs:872-877): adds `automation-flows` to the skills
   installed by `ensure_screenpipe_skill` (pi.rs:851), commented "Chat only
   (not pipes): read and change the user's Automation Flows; it never switches
   one on."
2. **New `skill_files` mechanism** (pi.rs:910-919): writes files a skill links
   to beside its `SKILL.md` ("Pi resolves a skill's relative links against that
   folder"). One entry: `n8n-guide.md` for `automation-flows`. This loop exists
   only in the unfiltered (chat) installer.
3. **`BASELINE_SKILL_NAMES` 6→7** (pi.rs:953-961): `automation-flows` added, so
   `sync_user_skills_from` skips any store entry of that name (pi.rs:1003-1005)
   and a user-imported skill can never shadow or get the baseline deleted.
4. **7 new tests** (pi.rs:4986-5160) asserting chat-only installation, the
   never-activate invariant, node lookup before use, draft step-by-step flow,
   delete-without-confirmation, guide shipping + link, no hardcoded
   `typeVersion`s, and the `CUSTOM.screenPipe*` node-type prefix (the latter
   cross-checks the demo workflow
   `infra/automation-flows/workflows/novadesk-support-tickets.json` via a
   repo-root-relative `include_str!`, pi.rs:5141-5144).

The pipe path is genuinely excluded: `ensure_screenpipe_skill_filtered`
(pi.rs:1086-1156) does not list `automation-flows` and has no `skill_files`
loop, and `automation_flows_skill_installs_in_chat_only_and_never_switches_a_flow_on`
asserts the pipe dir never contains the skill (pi.rs:5002-5003).

### pipes/mod.rs — visibility only, correct intent

`read_chatgpt_oauth_token` changes `fn` → `pub fn` (pipes/mod.rs:1697). This is
**visibility, not a permission change**, and it is required by this same PR:
the new 934-line `crates/screenpipe-engine/src/routes/chatgpt_proxy.rs` calls
`screenpipe_core::pipes::read_chatgpt_oauth_token` at chatgpt_proxy.rs:79 (also
verified: commit `7d8ee80a9` "hackathon(25): the user's ChatGPT subscription
answers every AI" touched pipes/mod.rs). `pub mod pipes;` at
crates/screenpipe-core/src/lib.rs:47 makes the exposure effective cross-crate.
The caller wraps the blocking read/refresh in `tokio::task::spawn_blocking`
(chatgpt_proxy.rs:78-81) — correct, since the function does blocking fs I/O and
may rewrite the legacy token file (pipes/mod.rs:1726-1730). The token is used
in-process to build `ChatGptAuth`; it is not returned to clients (the route
answers with 503 `chatgpt_not_connected` when absent, chatgpt_proxy.rs:82-87).

## Notable risks / quality issues

1. **P3 — `skill_files` loop depends on an undeclared invariant**
   (pi.rs:917-919). It writes into `skills_root.join(name)` without
   `create_dir_all`, silently relying on the parallel `skills` list containing
   the same name (the dir is created at pi.rs:906). If the two lists drift — a
   linked file added for a skill not in `skills`, or a name typo —
   `ensure_screenpipe_skill` hard-fails session setup (`?` at pi.rs:918) with a
   bare `NotFound`. A `create_dir_all` guard decouples the lists. Posted as the
   only PR comment.
2. **Already tracked on the PR (not duplicated):** coderabbitai's comment at
   pi.rs:960 — a pre-existing *mirrored* `automation-flows` dir keeps its
   `.screenpipe-managed` marker after the baseline overwrite, so the stale-mirror
   cleanup (pi.rs:1043-1050) deletes the freshly written baseline + guide on the
   next sync. I verified the mechanism while reading
   `sync_user_skills_from` (pi.rs:982-1055) and agree it is real; skip it here.
3. **Test-only cross-crate `include_str!`** (pi.rs:5141-5144): the
   `CUSTOM.screenPipe` test embeds
   `infra/automation-flows/workflows/novadesk-support-tickets.json` via a
   4×`../` path out of the crate. Legal (path-relative include, cfg(test) only,
   file exists) but couples screenpipe-core compilation to a file outside the
   crate root; moving the demo JSON breaks the core crate's tests. Not posted —
   acceptable in a monorepo, noted for the record.
4. **Dead clause in the typeVersion test** (pi.rs:5124-5135):
   `|| after.is_empty()` is redundant because `.all()` on an empty iterator is
   already `true`. Cosmetic; not posted.
5. The `automation-flows` skill asset itself (SKILL.md, n8n-guide.md) is outside
   this slice (other reviewers have line comments on it); I only verified the
   invariant this wiring depends on: the skill's own text says "Never activate."
   and forbids `/automation-flows/<id>/activate|deactivate` and direct n8n calls
   (assets/skills/automation-flows/SKILL.md:15-21), matching the test's
   forbidden-token sweep (pi.rs:5019-5023) and the "Chat only (not pipes)"
   comment at pi.rs:872-873.

## Verdict

Both changes are correct and minimal. The chat-only intent of the skill wiring
is enforced in code and pinned by tests; compaction is untouched and green; the
pipes/mod.rs change is a required visibility widening for the new ChatGPT
proxy, not a permission change. Nothing blocks; the one P3 nit was posted.
