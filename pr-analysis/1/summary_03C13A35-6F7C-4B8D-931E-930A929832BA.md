## Focus-area findings

### Tab switching / toggle (integrated-workflows.tsx)
No defects found on the changed lines. The changed file only supplies the platform and the source select; tab switching lives in home page and is coherent: `changeMode` refuses switching into Workflows when rollout is off (`home/page.tsx:187`); `ProductSwitcher` additionally renders null when disabled (`product-switcher.tsx:20-21`); when the flag is revoked mid-session, `workflowsAvailable`/`workflowsActive` (`home/page.tsx:366-367`) fail closed visually even though the workflows DOM stays mounted-hidden (`home/page.tsx:1766`).

### Product switcher persistence (product-switcher.tsx)
File unchanged by this PR. Persistence works: `changeMode` → `saveProductMode` into native store `workflows-entry.bin` (`entry-preference.ts:7-16`), restored on mount via `readProductMode` guarded by the `modeInteraction` ref, so a fast user toggle wins over a slow store read (`home/page.tsx:185-202`); safe default for any non-"workflows" value (`entry-preference.ts:10`). One pre-existing nit, not posted since neither file is in the diff: `saveProductMode` failure is silently swallowed (`home/page.tsx:190` `.catch(() => {})`), so a failed save reverts the workspace on relaunch with no user feedback.

### Rollout sync race (rollout-sync.tsx)
The changed line makes forced builds assert `enabled: true` from first mount — **before** PostHog resolves — and keeps asserting it every 30 s even when the remote flag resolves `false`. On a demo machine that is the point (`rollout.ts:8-12`) and it is tested (`rollout.test.tsx:100-115`). The genuine risk is structural, not current: the override is a build-time `NEXT_PUBLIC_*` env var with no dev/mock-build gate, so a release build produced with the var set would permanently override remote revocation with no Settings escape hatch. Today nothing in CI or release scripts sets it (verified above), so I posted this as P3 with a gate suggestion. I also traced the stale-response ordering concern and it is already mitigated within a component: the effect's cleanup aborts the in-flight `syncWorkflowsRollout` via the `AbortController` (`rollout-sync.tsx:18-22`), so an effect-triggered `sync(false)` cannot land after a newer `sync(true)` from the same mount; cross-window last-writer-wins flapping is pre-existing, documented design (`rollout-sync.tsx:9-10`). Not posted.
