# Slice review: AI Trigger node + ScreenPipe API credential (PR #1)

Reviewer slice: `packages/n8n-nodes-screenpipe/nodes/ScreenPipeAiTrigger/ScreenPipeAiTrigger.node.ts` (272 new lines) and
`packages/n8n-nodes-screenpipe/credentials/ScreenPipeApi.credentials.ts` (43 new lines). Both files are new in this PR

## What the slice changes and how it fits the PR

- **`ScreenPipeAiTrigger.node.ts`** is one of the three n8n nodes this PR adds (README.md, "Screenpipe nodes for n8n"
  table): a polling trigger (`description.polling: true`, node file line 38) that on each poll reads ScreenPipe's
  `/activity-summary` for a look-back window and asks ScreenPipe's local AI proxy (`/v1/chat/completions`) whether a
  user-written condition is met; on `met: true` it emits one item and records a cooldown in the node's static data
  (`poll()` at lines 80–127). Default model `chatgpt/gpt-5.6-luna:max` (line 21) rides the ChatGPT-subscription proxy
  (`crates/screenpipe-engine/src/routes/chatgpt_proxy.rs`); `auto` rides the cloud proxy
  (`crates/screenpipe-engine/src/routes/cloud_proxy.rs:30-38`), so the Model description (lines 74–75) is accurate.
- **`ScreenPipeApi.credentials.ts`** is the credential all three nodes share
  (`credentials: [{ name: "screenpipeApi", required: true }]`, AI trigger line 41; same in `ScreenPipeTrigger.node.ts:47`).

## Slice focus: abstain behavior surfaced to users

This is the strongest part of the node, with two real gaps.

Good:
- **Abstention never fires.** Any AI failure — transport, non-2xx, non-JSON, missing `met` — is caught at
  `ScreenPipeAiTrigger.node.ts:112-118`, logged with `logger.warn`, and returns `null`. "Not met" returns `null` too
  (lines 119–121). Neither starts the cooldown (tests: `screenpipe-ai-trigger.node.test.ts:275-287`, `351-363`).
- **Manual mode surfaces abstention.** "Fetch Test Event" throws `NodeOperationError` "The AI check failed" / "Condition
  not met" with the cause/reason as description (lines 115, 120) — the user sees *why* nothing fired, like n8n's own
  triggers. Tested (`screenpipe-ai-trigger.node.test.ts:181-230`).
- **Error messages never carry the API key**: catch blocks build messages from `(error as Error).message` only
  (lines 161-162, 207-209), and the test suite asserts logged warnings don't contain the key
  (`screenpipe-ai-trigger.node.test.ts:272`).
- **Prompt-injection defense is real and tested**: activity JSON escapes `<`/`>` (`activityJson`, lines 256-262) so
  captured screen text cannot close the `<activity>` block (test at `screenpipe-ai-trigger.node.test.ts:132-154`), and
  every string is clipped to 500 chars (lines 130-131, 264-272).

Gaps (posted as comments):
1. **P2 — persistent AI failure is invisible in an active workflow.** The same poll() throws `NodeApiError` for
   ScreenPipe-side failures (lines 163, 172 → failed executions, visible), but an AI-side persistent failure (ChatGPT
   signed out → 503, rotated key → 403, typo'd model) only writes a server-side `logger.warn` (line 116) — no execution,
   no error workflow, UI shows a trigger that looks healthy and never fires. Complementary to coderabbitai's existing
   timeout comment (they bound the call; I flag that the catch path hides persistent breakage).
2. **P3 — empty abstain reason** when the model returns a non-string `reason` (`parseDecision`, line 238 substitutes
   `""`): manual mode's "Condition not met" error shows an empty description; fired items can carry `reason: ""`.
3. **P3 — editing the condition keeps the old fire baseline.** `state.lastFiredAt` (lines 88-91, 102, 125) survives any
   parameter change, so a newly-edited condition is unevaluated for up to `cooldownMinutes` (default 60) and its first
   look-back starts at the old firing time. The sibling `ScreenPipeTrigger` deliberately resets state when parameters
   change ("A cursor belongs to what it watched", `ScreenPipeTrigger.node.ts:141-147` + `signature()` at 154-157).
   Fails safe (no wrong fires), but the user sees silence with no signal right after an edit.

## Credential file: slice focus satisfied

"Mark as password-type fields only" is satisfied: the only secret, `apiKey`, is `typeOptions: { password: true }`
(`ScreenPipeApi.credentials.ts:26`); `baseUrl` is a plain string (correct — not a secret, line 14-21). The
`authenticate` expression omits the Authorization header when the key is empty (line 36), matching node-side behavior
(`ScreenPipeAiTrigger.node.ts:95-96`, `ScreenPipeTrigger.node.ts:427`). The test request hits `/search?limit=1` with the
credential's baseUrl (line 40-42) — cheap and the endpoint exists (`crates/screenpipe-engine/src/server.rs` mounts
`/activity-summary` at 1052 and `/v1/chat/completions` at 1271-1273; `/search` is the long-standing API). Build copies
`screenpipe.png` next to the compiled credential (`scripts/build.ts:35-37`) and the file exists, so the `file:` icon
resolves. **Not verified at runtime**: the n8n credential "Test" button behavior (generic authenticate +
`ICredentialTestRequest` against a live n8n) — I checked it statically against the n8n-workflow 2.42.2 type
declarations only; no n8n instance was run.
