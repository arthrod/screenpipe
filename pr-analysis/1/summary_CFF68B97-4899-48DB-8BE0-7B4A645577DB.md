## Focus 1 & 2: can the mocks ship in production?

**Runtime: no — verified.** Import graph: the only non-test importer of both mock modules is `lib/dev/browser-runtime.ts` (grep over `*.ts`/`*.tsx` outside node_modules). `browser-runtime.ts` is imported solely by `app/layout.tsx:8` as a side-effect import — pre-existing on origin/main (`git show origin/main:apps/screenpipe-app-tauri/app/layout.tsx` shows line 8 unchanged). `installBrowserRuntime()` (`browser-runtime.ts:38-40`) returns before installing anything unless `process.env.NEXT_PUBLIC_SCREENPIPE_WEB_DEV` is `mock` or `live`; `installMockEngine` (fetch + WebSocket interception, which carries the flows dispatch) additionally only runs when `mode === "mock"` (`browser-runtime.ts:79`). The env var is set in exactly two places: `scripts/dev-web.ts:41` (local dev server) and `.github/workflows/test-frontend.yml:121` (the "Enterprise Workflows entry" job, which boots an ephemeral `next dev` for a screenshot eval and uploads artifacts — it produces no shipped bundle). No other workflow sets it (grep over `.github/workflows/` exited 1). Next.js inlines `NEXT_PUBLIC_*` at build time, so a release build without the var makes the runtime a no-op.

**Caveat (posted as P3): the gate is runtime-only, not bundle-level.** Because `app/layout.tsx:8` imports the runtime unconditionally, the new flows fixture/mock code is compiled into the production JS bundle as inert dead code. This is the pre-existing architecture the PR extends, not a new hole. The shipped constant key is harmless: the engine generates 244 random bits per process with a constant-time compare (`crates/screenpipe-engine/src/automation_flows.rs:153-175`), so `"browser-mock-flow-activation"` can never match a real engine.

## Findings

- **P3 — mock/live type divergence + missing live-branch test** (`browser-tauri-mock.ts:882`): in live browser mode the mock returns `null`, but the real command never returns null (`-> String`) and the binding types it `Promise<string>`. The sole caller absorbs it (`api.ts:222` `|| null`, `api.ts:223-225` catch → null; header omitted → engine refuses), and `api.test.ts:31` papers over it with `as string`. The mock branch (mode "mock") is exercised by `api.test.ts`'s `describe("browser mock")`; the live `: null` branch has no test. One assertion in `browser-runtime.test.ts` would pin both branches.
- **P3 — bundle-level shipping** (focus explicitly asks about shipping; see caveat above). Inert, pre-existing pattern; a dynamic `import()` inside the env-gated function would make the exclusion true at bundle level too.

No P0/P1/P2 found in this slice. Placement of the flows dispatch is correct: it sits after the `backend-error` 503 early-return (`browser-engine-mock.ts:204-209`, so that scenario 503s flows too, coherently) and before the method-agnostic catch-alls at `browser-engine-mock.ts:461-467` that would otherwise answer flows POSTs with a blanket `success: true`. No other handler claims `/automation-flows*`, so nothing is shadowed.
