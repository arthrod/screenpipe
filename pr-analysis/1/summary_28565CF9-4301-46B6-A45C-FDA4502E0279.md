## What this slice actually changes

- `apps/screenpipe-app-tauri/components/workflows/rollout.test.tsx` — **+17 lines**, one new test
  "opens Workflows without the flag only when the local build sets the override to 1"

The new test pins the PR's new rollout-override feature end to end at the user-visible boundary:

1. Fail-closed direction: env values `""`, `"0"`, `"true"` do **not** force the rollout —
   `isWorkflowsRolloutEnabled(false)` stays false (`rollout.test.tsx:102-105`).
2. Override direction: `NEXT_PUBLIC_SCREENPIPE_WORKFLOWS_ROLLOUT=1` makes
   `isWorkflowsRolloutEnabled` true even for `undefined`/`false` flags (`rollout.test.tsx:106-107`),
   the `ProductSwitcher` renders with `state.flag = false` (`rollout.test.tsx:108-110`), and
   `WorkflowsRolloutSync` posts `{ enabled: true }` to `/workflows/rollout`
   (`rollout.test.tsx:111-113`). Assertions are behavior-level (role/label queries, request bodies),
   not implementation details — matches the slice focus.

## Findings

1. **P2 — the "background AI tasks still need their explicit opt-in" half of the new contract is
   unpinned.** The doc comment added with the override (`rollout.ts:9-12`) promises the override
   "only shows the view". But the same PR change makes `requireWorkflowsRollout()`
   (`rollout.ts:23-27`) pass under the override, because it composes `isWorkflowsRolloutEnabled`
   (`rollout.ts:16-18`). The only remaining guard that stops a background pipeline is the
   pipe-enabled check inside `startWorkflowJob` (`scheduled-discovery.ts:196-200`); no test asserts
   it still holds when the override is set. Detail in comments file.
2. **P3 — the catalog smoke test never runs in CI or the default suite.** It is gated behind
   `it.skipIf(!process.env.WORKFLOW_CATALOG_TEST_PATH)` (`saved-catalog-smoke.test.tsx:12-13`;
   my run shows it skipped), and saved catalogs are loaded through an unchecked cast
   (`scheduled-discovery.ts:103`), so "catches schema drift in saved workflows" only holds on a
   machine where a developer remembers to point it at a real catalog.
3. **No issues found** in `integrated-workflows.test.tsx` for this PR: its 8 tests assert
   user-visible behavior only (roles, labels, dialogs, posthog events — e.g.
   `integrated-workflows.test.tsx:103-117, 162, 176`), and the PR's production changes to
   `integrated-workflows.tsx` are covered elsewhere (`task-page-create-flow.test.tsx`, new in this
   PR, outside my slice) or are pure CSS (`integrated-workflows.tsx:122`). The mocked platform in
   the test (`integrated-workflows.test.tsx:25-40`) omits the new automation-flow methods, which is
   safe: they are optional in the platform interface (`packages/workflows-ui/src/platform.ts:48-57`)
   and not present in the fixture platform either (grep of
   `packages/workflows-ui/src/fixture-platform.ts` found no matches).
4. **Traced, no product bug:** the override does relax `requireWorkflowsRollout`, but the only
   non-test callers of the task entry points are the explicit settings toggle
   (`workflow-tasks-prompt.tsx:18` → `enableWorkflowTask`) and the user-requested "Update now" path
   (`desktop-platform.ts:168` → `startWorkflowJob`), so the override opening those is the intended
   demo-machine behavior; the scheduled engine-side pipeline still requires explicitly enabled
   pipes. Verified by reading, not by running the engine.
