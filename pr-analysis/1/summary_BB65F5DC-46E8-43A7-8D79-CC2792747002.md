# Review: n8n-nodes-screenpipe test slice (AI trigger tests + test harness)

Reviewer slice: `packages/n8n-nodes-screenpipe/test/screenpipe-ai-trigger.node.test.ts` (364 lines, new) and
`packages/n8n-nodes-screenpipe/test/harness.ts` (193 lines, new). Both are new files in this PR; no prior
version exists on `origin/main` (`git diff origin/main...HEAD --stat` shows 557 insertions, 0 deletions).

## What this slice is

A shared test harness plus the test suite for the new `ScreenPipeAiTrigger` n8n node
(`nodes/ScreenPipeAiTrigger/ScreenPipeAiTrigger.node.ts`, also new in this PR, read for context only —
not my slice).

- `harness.ts` stands up a **real local HTTP server** (`Bun.serve` on `127.0.0.1:0`, harness.ts:34-54) that
  plays ScreenPipe's API and its AI proxy, and re-implements n8n's `helpers.httpRequest` semantics on top of
  real `fetch` (harness.ts:162-185). It also builds minimal `IExecuteFunctions`/`IPollFunctions` contexts
  (harness.ts:74-105, 120-160).
- `screenpipe-ai-trigger.node.test.ts` runs the node's `poll()` outside-in against that server: AI met/not-met
  branches, prompt-injection hardening, manual (editor test) mode, ScreenPipe and AI error handling, and the
  cooldown/window-clamp state machine.

## How it fits the whole PR

This is the test layer for one of the PR's three new n8n nodes. It shares `fakeScreenpipe` and
`executeContext` with two sibling suites (`test/screenpipe-trigger.test.ts:13`,
`test/screenpipe.node.test.ts:14`), so harness quality propagates to them. The AI trigger node is what the
engine's flows and the demo workflows rely on for the "AI judges the condition" step, so the decision-branch
coverage here protects the PR's headline feature.

## Verification I ran

- `bun test` in `packages/n8n-nodes-screenpipe`: **56 pass, 0 fail** (214 expect calls, 365 ms) — includes
  all 20 AI-trigger tests and the two sibling suites that consume the harness.
- `bun run typecheck` (`tsc --noEmit -p tsconfig.json`): **exit 0**.
- Verified the harness's claimed n8n fidelity against the installed `n8n-workflow` **2.42.2** types:
  `IPollFunctions.getNodeParameter(parameterName, fallbackValue?, options?)` is genuinely two-arg in 2.42.2
  (`node_modules/n8n-workflow/dist/esm/interfaces.d.ts:1052`), so `pollContext`'s signature (harness.ts:135)
  and the node's `getNodeParameter("lookbackMinutes", 15)` calls are correct — I initially suspected a
  mismatch and the installed types disproved it. `executeContext`'s three-arg form matches
  `GetNodeParameterFn` (interfaces.d.ts:556-565).
- Verified the icon test's premise: `scripts/build.ts:35-37` copies `screenpipe.png` to
  `dist/nodes/ScreenPipe/`, which is where the AI trigger's `file:../ScreenPipe/screenpipe.png` resolves
  after build.
- The harness's focus question ("mocks must not fake away network errors") largely holds: the transport is
  real. "when ScreenPipe is not running" (test:248-256) exercises a genuine connection-refused through real
  fetch, and HTTP status handling is implemented by the node itself because the shim honors
  `ignoreHttpStatusErrors: true` (harness.ts:176-183) rather than pre-digesting status codes.

## Quality assessment

Strong suite. Highlights: the prompt-injection test (test:132-154) pins the `\u003c`/`\u003e` escaping of the
activity block and proves captured text cannot close it; the API-key no-leak assertion on warnings
(test:272); the boundary-inclusive cooldown expiry at exactly 60:00 (test:301-307); window clamping to the
last firing and back to the full look-back (test:310-334, 336-349); "not met" and "AI error" proven not to
write cooldown state (test:275-287, 351-363); deterministic time via `setSystemTime` with cleanup
(test:20-24). The met/not-met decision ("confidence-threshold") branches are covered for: fire, not-met in
both modes, non-JSON answer, non-boolean `met`, missing `choices`, HTTP 403/500 from the proxy, code-fenced
answers, and error-does-not-arm-cooldown.

## Risks and issues found

1. **P2 — the AI-call transport-error branch is untestable and untested.** `executeContext` accepts an
   `httpRequest` override (harness.ts:69-70, harness.ts:102) precisely to simulate unreachable hosts, but
   `PollOptions` has no such option and `pollContext.helpers` hardcodes the shim (harness.ts:157). So
   `askAi`'s transport catch (node:207-210) — whose message construction deliberately drops the raw client
   error because it "can carry request headers (the API key)" (node:208) — and `poll`'s
   error-as-not-met warn path (node:112-118) are reached only via HTTP-status/parse errors in the tests
   (test:260-273), never via a real network failure. The one transport-level test in the file is for
   ScreenPipe's summary call (test:248-256). The API-key no-leak property of that one message site is
   therefore unregression-tested. This is the one place the harness's design fakes away a network error: not
   by stubbing it, but by making it impossible to inject.
2. **P3 — the http shim silently ignores request options it doesn't implement** (harness.ts:162-185):
   `timeout` (`IHttpRequestOptions` interfaces.d.ts:425), `maxRedirects`/`disableFollowRedirect`
   (interfaces.d.ts:410-411), and 2.42.2's object form of `ignoreHttpStatusErrors`
   (`boolean | IgnoreStatusErrorConfig`, interfaces.d.ts:415). `fetch` follows redirects unconditionally and
   never times out. No current node call uses these options, but silent ignoring invites false-green tests —
   and directly interacts with the already-posted coderabbitai suggestion to add a `timeout` to `askAi`
   (ScreenPipeAiTrigger.node.ts:198-206): once added, the shim would ignore it and no test could exercise it.
3. **P3 — two tail branches of the decision logic are unpinned** (test:260ff): the `from >= now` guard
   (node:103) — reachable with `cooldownMinutes: 0` firing again in the same millisecond, or a negative
   `lookbackMinutes` supplied via expression (the node only guards via UI `minValue`, node:57) — and
   `parseDecision`'s non-string-`reason` fallback (node:238), where `{"met": true}` fires with
   `reason: ""` untested.

Not posted (below the bar): manual mode's `if (!manual) state.lastFiredAt` (node:125) is not pinned by the
"every test asks the AI, without cooldown" test (test:169-179) — that test passes whether or not manual mode
writes state, because manual mode also skips the cooldown read (node:91); pinning it would need the harness
to expose `staticData`. Also, `pollContext` persists `staticData` in memory across polls unconditionally
(harness.ts:114-149) — I could not verify n8n 2.42.2's exact persistence-on-failure semantics, and the node
only writes state immediately before returning items (node:125), so it is immaterial today; flagging for
awareness only.

## What I did not check

- The real `@n8n/backend-network` axios request that the shim's header comment (harness.ts:4-8) claims to
  mirror is **not installed** in this package (`node_modules/@n8n` contains only constants, errors,
  expression-runtime, tournament, utils), so the shim's fidelity to n8n 2.42.2's actual helper (redirect
  limits, error shape details, `statusMessage` casing) could only be checked against the `IHttpRequestOptions`
  interface, not the implementation.
- Did not run the engine/Rust or app test suites; out of slice.
- Did not review `ScreenPipeAiTrigger.node.ts` itself (context only); the timeout issue on it is already
  posted by coderabbitai.
