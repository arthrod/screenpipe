## Review of `docs/pii-release-gate.md` and `docs/pr-assets/pii-release-gate/README.md`

**Provenance note first:** neither file is changed by this PR. PR #1's diff is 234 files (verified against GitHub's file list and `git diff origin/main...HEAD` — the lists are identical), and it contains no `pii-release-gate` or `pr-assets` paths. Both files exist only on the base branch (`arthrod/screenpipe@main` @ d75ccaed), added by 5ce7edfcd ("Gate captured data on PII completion receipts (#7634)", a squash of upstream #7634) after this PR's branch diverged. The findings below therefore apply to base-branch content and are not actionable within this PR; they are recorded here because these files were assigned for review.

---

**[P2] `docs/pii-release-gate.md` — the consent model is never stated.** The doc delivers its processing/admission contract precisely, but a reader learns nothing about consent: (1) the enabling control is never named — the Settings "PII Removal" toggle with Basic/Smart modes and the "Apply & restart" bar shown in the companion evidence (`privacy-section.tsx`) is absent from the spec, as are the default state and restart semantics; (2) the OFF state is only implied — "including while protection is disabled" (`docs/pii-release-gate.md:28`) and "explicitly unavailable under protection" (`docs/pii-release-gate.md:82`) let a careful reader infer that disabling protection re-exposes every gated surface, but that pivotal fact is never said; (3) most importantly, remote egress of private content is never stated — cloud processing appears only obliquely via "configured backend" in the policy identity (`:20`), "remote requests remain indivisible" (`:30`), and the log-exclusion note that remote request URLs "can echo private source data", while the companion UI promises "your device verifies the open-source build before sending anything" — a consent-relevant claim the spec neither owns nor defines. A spec governing admission of private data should state in one place what leaves the device, under which mode, to which endpoint class, and which control turns that on. Suggest a short "Enabling and consent" section.

**[P3] `docs/pii-release-gate.md:36` — the value space of `x-screenpipe-privacy-completeness` is undefined.** The doc shows the literal `unknown` but never enumerates the possible values or their meanings; a client implementer cannot tell whether `unknown` is a constant or one state among several (and the neighboring text says caches use the completion epoch, not this header, for freshness — so what the header *is* for is also unstated).

**[P3] `docs/pii-release-gate.md:6` — `doc-verified: c288183019` is unreachable from `main`.** The commit exists (subject: "fix: rediscover generated IDs after privacy trigger migration") but `git merge-base --is-ancestor` shows it is not an ancestor of `main`; `git branch -r --contains` finds it only on `origin/fix/pii-release-gate`. Upstream #7634 landed as squash 5ce7edfcd, so the marker dangles for any reader or tooling resolving it from main history. (I did not run `check-doc-freshness`; the docs are absent from this PR-head checkout — the unreachability is my own check, not the checker's verdict.)

**[P3] `docs/pr-assets/pii-release-gate/README.md:5` — the cited `before` commit `ae26753f7` is also unreachable from `main`** (same cause; reachable only from `origin/fix/pii-release-gate`). Consider citing the squash commit that actually carries these assets.

**[P3] `docs/pr-assets/pii-release-gate/README.md` — the five `*.png` assets are JPEG data.** `file` reports "JPEG image data, JFIF standard 1.01 … 1280x720" for all five; other repo `.png` assets (e.g. `docs/benchmarks/pii-release-gate/capture-latency.png`) are genuine PNGs, so these are outliers. Rename to `.jpg` or re-encode.
