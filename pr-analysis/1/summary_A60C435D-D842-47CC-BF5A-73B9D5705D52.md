per node (name + three lines of its one-sentence explanation, popover for the whole sentence),

(`flow-review.tsx:30,171`), which passes `flow.nodes`/`flow.edges` verbatim

## How it fits the whole PR

This is the "How it works" section of the Automation Flows Review Screen — the surface the design
rules make load-bearing: the user reads the graph and then clicks "Turn on". Its data contract is
the engine's `/automation-flows/:id` payload: `FlowNode = {id, name, type, position, sentence}`
(api.ts:29-35), `Flow.edges = {from, to}[]` (api.ts:58). The engine builds that with
`review_graph` (`crates/screenpipe-engine/src/automation_flows.rs:1161-1215`): it keeps every
node except `n8n-nodes-base.stickyNote` (`STICKY_NOTE` at automation_flows.rs:66, filter at
:1165), takes `notes` as the sentence (:1178-1183), and builds edges from n8n's connections keyed
by node name, skipping unknown endpoints and de-duplicating identical from→to pairs
(:1186-1213). A fixture drift test (`__tests__/api.test.ts`, referenced from fixtures.ts:5-8)
keeps the browser-mock fixture in sync with the engine output.

## Focus 1: only real n8n nodes/edges are drawn

Mostly yes, with two gaps:

- Sticky notes never reach the UI (engine filter, automation_flows.rs:1165). Dangling edges are
  dropped twice: engine-side (automation_flows.rs:1197,1205) and defensively client-side
  (flow-graph.tsx:229-231: `if (!source || !target) return []`). Duplicate edges are deduped
  engine-side (automation_flows.rs:1208-1211).
- **Gap (P2): a disabled n8n node is drawn exactly like an active step.** n8n skips
  `disabled: true` nodes at execution, but nothing in this pipeline marks them: the engine's
  `review_graph` reads only type/name/position/notes (automation_flows.rs:1164-1191);
  `disabled` appears exactly once in the engine — in the n8n-API key allowlist
  (automation_flows.rs:101; grep over `flow_checks.rs`, `n8n_nodes.rs`, `automation_flows.rs`
  finds no other reference); `FlowNode` has no disabled field (api.ts:29-35); and `StepCard`
  renders every node identically (flow-graph.tsx:65-109). So the graph the user reviews before
  "Turn on" can show a step that will silently never run. Not covered by any test.
- Minor, not posted: the engine collapses an IF node's true and false branches when both target
  the same node into one edge (dedupe at automation_flows.rs:1208-1211), so the graph shows one
  arrow where n8n has two — an acceptable simplification for a review picture. A self-loop edge
  would render degenerately via the last `route()` branch (both handles bottom-center,
  flow-graph.tsx:227), but the n8n editor does not offer self-connections; not posted.

## Focus 2: layout degrades on narrow viewports

Degrades functionally, by design: `fitView` with `{padding: 0.08, maxZoom: 1}`
(flow-graph.tsx:71) on init (:294-295) and on every frame resize via ResizeObserver
(:279-284); `minZoom={0.2}` (:296); zoom controls with aria labels (:113-118);
pan on drag and wheel-scrolls-the-page preserved (:298-299). For the demo workflow the world is
≈2062×1000 px (9 step columns × 234 px `COLUMN` at flow-graph.tsx:56-57; 3 step rows × 432 px
`rowStride` at :190), so an ~800×420 px frame fits it at ~0.36 zoom — names unreadable at fit
zoom, recovered by zoom/pan and by the click-for-full-sentence popover (:90-106). Below
`minZoom` headroom the graph crops until panned; acceptable. I did **not** verify actual
rendering in a real browser — the vitest run is jsdom (no real layout), so the fit/zoom math
above is arithmetic from the constants, not observation.

- **P3: every frame resize resets the user's zoom/pan** (:281 calls `fitView` on any ResizeObserver
  tick — a scrollbar appearing or a sidebar animating is enough), with no user-interaction guard.

## Finding with the strongest evidence (P2)

**Level-2 context chains land exactly on the next step row.** `rowStride` reserves exactly one
216 px context row per step row (:190), but level-2 context nodes (context→context, e.g. n8n's
"auto-fixing output parser": chat model → auto-fixing parser → agent) are placed a further
`ROW_HEIGHT` below their parent (:209) — exactly the next step row's y (rows sit `2*ROW_HEIGHT`
apart when context nodes exist, :190,193). I reproduced it by copying `groups`,
`contextParents`, and `layout` verbatim out of flow-graph.tsx into `/tmp/repro-flow-layout.ts`
and running `bun /tmp/repro-flow-layout.ts`; output:
`OVERLAPS: error-step (234,432) <-> chat-model (234,432)` — a 100 % card overlap. The
"No two cards overlap" test (flow-graph.test.tsx:224-230) only runs on `fixtureFlow`, whose
context nodes are single-level, so it cannot catch this.
