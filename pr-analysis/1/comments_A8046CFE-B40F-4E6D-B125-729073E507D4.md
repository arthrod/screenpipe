## Review: `crates/screenpipe-engine/tests/automation_flows_test.rs` (lines 2035–3051 — chat modify/create and switching-off tests)

All 21 tests in this range pass locally: `cargo test -p screenpipe-engine --test automation_flows_test -- --exact <21 names>` → 21 passed, 0 failed, 1.46s. The suite is genuinely good — refusals assert both the error *and* that nothing changed in n8n. Three gaps worth addressing:

---

**[`crates/screenpipe-engine/tests/automation_flows_test.rs:2424`](https://github.com/arthrod/screenpipe/blob/HEAD/crates/screenpipe-engine/tests/automation_flows_test.rs#L2424)** — **P2 (test gap, security-adjacent)**

`chat_update_keeps_the_users_credentials_and_never_takes_the_chats` covers a PUT where the chat **swaps or drops** credentials on nodes that keep their name and type, and `chat_create_cannot_wire_the_users_n8n_credentials` (line 2801) covers create — but nothing covers **PUT with a brand-new node that carries a chat-supplied credential id** (e.g. push a new "Create the Jira ticket"-like node naming `spNovaJira000001`). That is the exact case the rule "the chat never picks n8n credentials" exists to close on the update path. The implementation is right today — `keep_user_credentials` (`automation_flows.rs:976`) strips credentials from unmatched nodes before `check_and_wire` re-wires from what n8n holds — but a future regression that lets the request's `credentials` through on new nodes would ship with no failing test. Please add the case: new node + chat-named credential id → expect the stored workflow to hold either the credential n8n wires or none, never the chat's pick.

---

**[`crates/screenpipe-engine/tests/automation_flows_test.rs:2025`](https://github.com/arthrod/screenpipe/blob/HEAD/crates/screenpipe-engine/tests/automation_flows_test.rs#L2025)** — **P3**

`state_changing_routes_take_only_json_requests` samples only the ticket-04-era routes (create, from-task, PUT, activate, deactivate). The guard is a single `.layer(middleware::from_fn(require_json))` placed at the end of the router builder (`automation_flows.rs:294`), which is correct — but in axum a route appended *after* that `.layer(...)` call, or added on a different router, silently bypasses the guard and this test stays green (retry/dismiss/restore were all added later than the routes sampled here). Adding one of the newest POST routes — `POST /:id/runs/:run/retry` is the natural pick — to the loop pins the middleware over routes added late in the PR's life and catches any accidental layer reordering.

---

**[`crates/screenpipe-engine/tests/automation_flows_test.rs:2160`](https://github.com/arthrod/screenpipe/blob/HEAD/crates/screenpipe-engine/tests/automation_flows_test.rs#L2160)** — **P3**

`add_auto_label` sets the sentence « Chaque ticket créé reçoit aussi l'étiquette auto. » and `parameters.labels` on the **Gmail trigger** node ("New support email", the first non-sticky node of the demo workflow). A trigger that receives email neither creates tickets nor applies labels, and `labels` is not a parameter the committed `novadesk-support-tickets.json` gives that node. `flow_checks` doesn't validate parameter keys so the fixture passes, but it normalizes a node-sentence that misdescribes its node — precisely what the Review Screen's per-node sentence model (design rule: each node gets its one-sentence explanation that matches the node) forbids, and this helper is the template future edit tests will copy. Pointing the edit at the "Create the Jira ticket" node (labels in the Jira create call) or rewording the sentence to what the trigger does would keep the fixture honest.

---

Nothing else in this range blocked me: media-type enforcement, headless activation refusal, credential restore, guide-example validation, and the no-orphaning switch-off tests are all correct as written and match the engine's behavior (`require_json` middleware, `keep_user_credentials`, the execution-status mapping at `automation_flows.rs:802-810`).
