Three out-of-diff observations, posted here only because the slice was assigned against this PR — none of them are introduced by this PR:

**[P3] `crates/screenpipe-a11y/src/platform/macos/clipboard_delivery.rs:31`** — `capture_and_deliver` returns a bare `bool` that conflates four outcomes: delivered and stale-duplicate-skipped (both `true`) versus stopped, consumer-disconnected, and focus-turned-excluded mid-read (all `false`). The only caller signal is the single `debug!("clipboard snapshot unavailable or worker stopped before delivery")` in `spawn_clipboard_worker_thread` (origin/main `macos.rs:573`), so a routine "user copied inside an excluded app" (benign, frequent) is indistinguishable from a permanent consumer disconnect that silently ends clipboard delivery until restart. Behavior is correct — this is an observability nit: a `trace!`/counter distinguishing the disconnect case would make field diagnosis of "clipboard events stopped" trivial.

**[P3] `crates/screenpipe-a11y/src/platform/macos/input_focus.rs:41`** — the post-read `Arc::ptr_eq` re-check also discards a fully valid capture when the focus was merely *re-published* (new `Arc`, same app/window — e.g. a routine AX notification) during the 50 ms delayed clipboard read (`KEY_C` maps to `delay_ms = 50` in the tap handler, origin/main `macos.rs:1344`). The conservative direction is the right one for privacy (it loses captures, never leaks them), but it is an occasional, silent clipboard-event loss; if missed copies show up in practice, this is the first place to look. No change requested — worth a comment in the code noting that identity re-publication is an accepted loss case.

**[P3] `crates/screenpipe-a11y/src/platform/macos/text_buffer.rs:53-61`** — `chars` has no length cap: `capture`'s `capacity` (line 135) bounds only the burst-transition `pending` queue, and continuous same-app typing never satisfies the time-based `should_flush` (lines 172-176), so an uninterrupted typing session accumulates the whole session in one `String` and flushes it as a single giant event. At human typing rates this is a few KB, and growth happens via amortized `push` on the tap thread, so this is hygiene rather than a hot-path/battery risk — but since this file sits on the input tap (the repo's declared critical path), a max-length forced flush would make the bound structural rather than behavioral.

One scope note: the stated focus "memory safety with AXCF refs (release on all paths)" does not apply to `text_buffer.rs` — it contains no native calls (its header declares "No native calls"). The `cidre`/`AutoreleasePoolPage` reference handling lives in `macos.rs` (e.g. `clipboard_snapshot` and `get_clipboard_change_count`), which is outside this slice and was not audited here.
