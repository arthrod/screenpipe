**[P2] `docs/benchmarks/pii-release-gate/MERGE-READINESS.md:1-3` — newest measurement set has no reproducible environment record.**
The Oct-16 M1 Max measurements (receipt-format comparison, gate-absent control, ONNX scheduling) record their environment only in prose ("M1 Max (10 CPU cores, 32 GiB), macOS 26.4… normal Cargo test/debug profile", lines 3, 7): the file contains no source revision and no benchmark-binary hash, and `machine.json` — which sets the standard for the earlier run with `binary_sha256`, `source_base`, staged binary hashes and per-file timed-prefix hashes (machine.json:12-28) — was not extended to cover it. `DERIVED-UPLOADS.md:5` records its source revision (`b40eda11d…`) but also no binary hash. Without at least a source SHA + binary hash for the M1 Max runs, the strongest tables in the pack (e.g. the 7.3× broad-FTS improvement) cannot be tied to a reproducible build, which is the standard the rest of the pack holds itself to.

**[P3] `docs/benchmarks/pii-release-gate/run.py:12` — harness-written machine.json under-records the environment.**
The runner writes only `platform`, `cpu_count`, `started_utc` and the `--binary` path. No git revision, no binary hash, no profile label. The committed `machine.json` is far richer, so it was evidently enriched by hand afterwards; anyone re-running the harness per README.md:16-20 gets a machine.json that cannot later distinguish runs. Recording `git rev-parse HEAD` and a `sha256` of the binary at run.py:12 would make the raw artifact self-sufficient.

**[P3] `docs/benchmarks/pii-release-gate/run.py:24-25` — unknown test name crashes the runner instead of failing one case.**
The `expected` phase map is keyed by test name (`[test]`); passing a binary whose test name is not in the map raises `KeyError`, aborting the whole suite and skipping the `results.jsonl` append at run.py:26, so that case's record is lost (the `.log` survives). Similarly, a malformed `PRIVACY_METRIC` line raises inside the parse loop at run.py:22-23 before the record is written. Wrapping per-case parsing in try/except and writing the record (with `exit='harness_error'`) before validation would preserve the run-continuation guarantee the comment at run.py:29 promises ("Preserve failures and continue independent cases"). The success gate `'1 passed; 0 failed' in path.read_text()` (run.py:25) is also brittle to libtest summary-format changes, and `expected.issubset(...)` checks phase presence but not per-phase sample counts.

**[P3] `docs/benchmarks/pii-release-gate/run.py:14-27` — no warmup phase at the harness level.**
Each case runs in a fresh subprocess with no discarded warmup iteration; ordering effects are mitigated by alternating case order between repeats (run.py:33), and the docs honestly disclose that filesystem caches are not forced cold (README.md:28, RESULTS.md:11) and that capture comparisons equalize reader work. However, nothing in the committed files shows whether the Rust benchmark performs its own in-process warmup before timing; that part of the timing methodology could not be verified from this slice and should be stated in README.md if it exists.

**[P3] `docs/benchmarks/pii-release-gate/merge-readiness-metrics.json` (sparse `concurrent_latest`) — p95 quoted from n=4 samples.**
The "Concurrent latest-page reader" 701.43 ms cell in MERGE-READINESS.md:29 corresponds to `concurrent_latest.p95_ms` with `n: 4` in the raw record (off has n=93, ready n=115). MERGE-READINESS.md:17 discloses that five-observation read p95s are maxima, but the reader column's sample count is far smaller in the sparse case and is only visible in the JSON. One sentence noting the reader's n per case (or an asterisk on that cell) would prevent the 701.43 ms figure being read as a stable tail.

**[P3] `docs/benchmarks/pii-release-gate/plot.py:13,27-28` — empty selections fail with opaque errors.**
If a mode/history filter selects no rows (line 13) or a case name is missing from `model-results.jsonl` (line 27), `statistics.median([])` / `next()` raise bare `StatisticsError`/`StopIteration`. A manual tool, so low impact, but a one-line guard with "no rows for mode X" would make regeneration failures diagnosable.

**[P3, verified real but pre-existing on the base branch] `docs/benchmarks/pii-release-gate/DERIVED-UPLOADS.md:65` — the disclosed 52-vs-49-byte contradiction is still unfixed on main.**
Confirmed at `origin/main`: `apps/screenpipe-app-tauri/src-tauri/src/overlay_health.rs:43-44` defines `MANUAL_SCREEN_CAPTURE_RECOVERY_DETAIL` as "quit and reopen screenpipe to restore screen capture" (52 bytes) while `overlay_failure_details_are_brief_specific_and_privacy_safe` asserts `expected.len() <= 49` (`apps/screenpipe-app-tauri/src-tauri/src/health.rs`, test at :3074, assertion ~:3157) — the test can never pass as written. The doc discloses this honestly (including that the follow-up didn't touch those files), but the underlying `health.rs`/`overlay_health.rs` contradiction remains open on the base branch and should be fixed (shorten the constant or raise the bound) rather than only documented.
