**[P2] `crates/screenpipe-engine/tests/automation_flows_test.rs:3783` — a failing trigger is notified with a fresh id every time, so nothing can dedupe it, and no test pins that.**

For a trigger failure (`executionId: null`) the notice id becomes `automation-flow-failure:{flow}:trigger-{now_ms}` (`src/automation_flows/failures.rs:253-255`), and the health ledger that makes runs once-only is keyed on execution ids only (`src/automation_flows/health.rs:232`, `:405`), so neither the notification server's repeat-drop nor the engine can recognize the second report of the same broken trigger. The demo's Gmail trigger polls every 5 s, so credentials that fail at poll time would raise one notification per poll until the user fixes them — while the comment on the passing-run test (3754-3755) promises "One notification per failed run". Suggested: give trigger failures a stable id (e.g. `…:trigger:{flow_id}`), and extend this test to report the same trigger failure twice and assert the second comes back `notified: false, reason: "already notified"` (or is otherwise gated), mirroring what `a_run_the_error_workflow_reported_is_not_notified_again_and_vice_versa` (4629) already proves for runs.
