## Review — `chatgpt_proxy.rs` lines 1-470 (request validation & upstream auth)

**[P2] `crates/screenpipe-engine/src/routes/chatgpt_proxy.rs:78-89` — the OAuth token is read (and possibly refreshed) before the request is validated, and a failed token-read task is reported as "not connected".**
`chat_completions` calls `spawn_blocking(read_chatgpt_oauth_token)` first and only then parses the body (`chatgpt_proxy.rs:137-146`) or rejects bad roles/tools (`chatgpt_proxy.rs:256,344`). The read is not always cheap: when the token is expired, `read_chatgpt_token_from_secrets` acquires a refresh lease and can wait up to ~35s (140 × 250 ms, `screenpipe-core/src/pipes/mod.rs:1785-1799`) before this handler even looks at the request. So a stream of malformed local requests (this route has no auth of its own when `api_auth` is off, `server.rs:424`) makes the engine repeatedly open the secrets store and join refresh contention for work that a parse would have rejected in microseconds. Validate the body first (move the parse to the caller or reorder), and read the token only for requests that got past validation. Separately, `spawn_blocking(...).await.ok().flatten()` (`chatgpt_proxy.rs:79-82`) maps a `JoinError` — i.e. a panic inside the token path, e.g. `block_in_place` on a single-threaded runtime (`pipes/mod.rs:1758`) — into the same 503 "connect ChatGPT in screenpipe (Settings → AI → ChatGPT)" a signed-out user gets, which will send whoever debugs this chasing a login problem that does not exist. JoinError deserves a 500 with the panic logged.

**[P3] `crates/screenpipe-engine/src/routes/chatgpt_proxy.rs:276-284,288-290` — unsupported `tool_choice` and `response_format` are silently dropped while everything else unsupported is a named 400.**
Unknown message roles and non-function tools hard-error with the offending value in the message (`chatgpt_proxy.rs:256,344-346`), but `tool_choice: {"type": "allowed_tools", ...}` or any object without `/function/name` falls through the `if let Some(name)` with no else (`chatgpt_proxy.rs:279-284`), and an unrecognized `response_format` type returns `None` (`chatgpt_proxy.rs:383`) — in both cases the request ships without the constraint the caller asked for. For the n8n automation flows this proxy exists for, that is the worst failure mode: the AI node silently gets free-form prose instead of the demanded JSON/tool choice, and the workflow proceeds on unvalidated output instead of failing loudly. Please reject these like the other unsupported features (400 `invalid_request` naming the field). Same for a non-string `reasoning_effort` (`chatgpt_proxy.rs:291`), which silently falls back to the model suffix. While there, the `json_object` branch of `text_format` (`chatgpt_proxy.rs:368`) has no test — the new errors (or the pinned silent behavior, if you keep it) should come with one.

**[P3] `crates/screenpipe-engine/src/routes/chatgpt_proxy.rs:66-72,137` — the request body is fully JSON-parsed twice per ChatGPT call, and once per cloud call, just for dispatch.**
`requested_model` (`chatgpt_proxy.rs:66-72`) runs on every `/v1/chat/completions` body in `cloud_proxy.rs:34-35` — including requests that go to api.screenpipe.com, which previously forwarded bytes untouched — and for `chatgpt/` models the body is parsed again into a `serde_json::Value` at `chatgpt_proxy.rs:137`. Both parses are synchronous CPU work on the async worker, and the route allows bodies up to 50MB specifically because they embed base64 audio/images (`server.rs:1267-1274`); a multimodal request near that limit means scanning ~50MB twice and materializing a `Value` tree several times its size before the upstream call even starts. For the typical few-KB n8n payload this is noise, so not blocking, but consider having `requested_model` return the parsed `Value` (or at least documenting the double parse), or doing the dispatch parse in `spawn_blocking` like the token read. Not run: no benchmark — this is reasoned from the parse cost and the 50MB bound, not measured.
