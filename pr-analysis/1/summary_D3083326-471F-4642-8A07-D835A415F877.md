# Review slice: `crates/screenpipe-engine/tests/automation_flows_test.rs` lines 1–1017

Reviewer slice of PR #1 (focus: setup realism and assertion quality).

## What this slice is

Lines 1–1017 are the foundation of the new 5085-line integration test file for the
`/automation-flows` engine routes (the whole file is new in this PR):

- **Fake n8n** (`crates/screenpipe-engine/tests/automation_flows_test.rs:35-514`): a
  stateful wiremock `Respond` impl modeling an n8n 2.x public API — workflows CRUD
  with read-only-body rejection (`:301-316`), version-on-update with
  `publishIfActive` republish (`:300-342`), `publish`/`unpublish` endpoints
  (`:367-400`), executions with a poll-countdown for finishing runs (`:461-500`),
  retries with `retrySuccessId` bookkeeping (`:415-450`), tags, credentials, and
  API-key auth on every route (`:198-205`).
- **App harness** (`:520-705`): builds a real `SCServer` router on an in-memory
  SQLite DB with audio disabled, scaled `RunningWait` (10 ms/300 ms vs production
  1 s/90 s — `:589-593` vs `automation_flows.rs:200-207`), a fake notify server, and
  helpers `call`/`ui_call` distinguishing local-caller vs Review-Screen requests.
- **First 8 tests** (`:763-1019`): config-error discrimination (412 `n8n_not_configured`,
  502 `n8n_unreachable`, 412 `n8n_unauthorized` w/ "401" detail, 502 `n8n_failed` w/
  upstream message) and create-from-task semantics (switched-off + tagged, idempotent
  second create, adoption of the import-script copy, auto-unpublish of a left-on copy).

  SecretStore exists (`crates/screenpipe-connect/src/connections/mod.rs:502-520`) —
  so the harness's write-`connections.json`-after-router-creation pattern
  (`:624-637`) exercises the real fallback path, and the comment at `:622-623` is
  accurate.
- SCServer pub fields the harness pokes (`server.rs:232-333`) all exist; the
  positional booleans in `SCServer::new` are
  `vision_disabled=true, audio_disabled=true, use_pii_removal=false`
  (`server.rs:392-400`).
- Engine pagination follows `nextCursor` opaquely with a 40×250 bound
  (`automation_flows.rs:669-684`), so the fake's `after-<n>` offset cursor (`:253-258`)
  is a fair model. Engine `is_running` polls `/executions?workflowId=…&status=running&limit=1`
  (`automation_flows.rs:843-855`), matching the fake's newest-first `insert(0, …)` (`:140-147`).
- The fake's retry refusal (`finished == true` → 409, `:426-431`) is consistent with
  the engine's client-side `retryable` gate (`automation_flows/retry.rs:75-81`), and the
  fake's default retry success sets `retrySuccessId` on the original (`:444-447`),
  which the engine's gate reads.

## Assessment

Assertion quality is high: precise status + error-code pairs with useful failure
messages (`:788`, `:840-845`, `:887-893`), negative assertions that pin behavior
(create POST must not carry `active` — `:913`, and the fake would 400 if it did —
`:264-270`; no `publish` posts after auto-unpublish — `:1019`; `activationLog` stays
empty — `:1006-1010`), and `create_adopts_the_workflow_already_imported_by_the_import_script`
(`:950-981`) loads the real bundled workflow via `include_str!`, tying the test to the
shipped artifact. Setup hermeticity is good (tempdir + in-memory SQLite + audio
disabled + closed-port URL for the unreachable case, `:752-757`).

## Risks / quality issues (also posted as review comments)

1. **Fake encodes "finished" two ways.** Executions completed via the poll countdown
   get `status: "success"` + `stoppedAt` but no `finished` field (`:471-474`), while
   the retry refusal keys only on `finished == true` (`:426`). A regression that made
   the engine retry an already-finished run would get a 200 from the fake instead of
   the modeled 409, so the suite could not catch it. (P3)
2. **Fake under-models request payloads on the two safety-critical endpoints.**
   `publish` accepts any `versionId` without checking it exists (`:373-378`), and
   `retry` ignores the `{"loadWorkflow": …}` body the engine sends
   (`automation_flows/retry.rs:95`). Wrong-version-publish or wrong-loadWorkflow bugs
   would pass unnoticed. (P3)
3. **Positional booleans** in `SCServer::new(db, addr, dir, true, true, …, false,
   "balanced")` (`:576-585`) are unreadable without the signature. (P3)
4. **Stale/confusing doc comment** on `App::new` — "local API auth off (as in the
   tests above)" (`:533`) — there are no tests above the helper's definition. (P3)

## Noted but not posted (would duplicate existing PR feedback or out of scope)

- French "Connexions" in a test comment (`:820`) — same root pattern CodeRabbit
  already flagged on `crates/screenpipe-core/assets/skills/automation-flows/SKILL.md`;
  here it is a code comment, not user-facing text.
- Line 3 of the header ("…add this header to every source file you create or edit
  (even outside screenpipe repo)") conflicts with AGENTS.md ("Do not add the header
  outside this repository"), but it is a pre-existing repo-wide convention (1736 files
  on `origin/main` carry it; this PR adds ~17), not introduced by this PR.
- The countdown-on-GET design (`:465-477`) advances *all* finishing executions on any
  `status=running` poll, regardless of `workflowId` — deterministic and documented, but
  a multi-workflow test could surprise. No current test in this slice is affected.

## What I could not verify

- Fidelity of the modeled n8n 2.x semantics (`publish`/`unpublish` endpoints,
  read-only body keys, update-requires-name/nodes/connections/settings, "n8n refuses
  a finished execution" retry rule): the fake's rules mirror the engine code's own
  comments, so the suite is internally consistent but **cannot** detect a mis-modeled
  real n8n — this circularity is inherent to contract tests against a fake and is the
  main residual risk of this slice. I had no real n8n instance to check against.
- Whether CI actually runs this test target (AGENTS.md says `cargo test --workspace
  --exclude screenpipe-rfdetr-mlx` does; I did not inspect the workflow files).
- wiremock's `received_requests()` retention bound (all assertions that read request
  history rely on it); not checked against the wiremock version in the lockfile.
