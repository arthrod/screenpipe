## Review — Workflows view integration, product switcher, rollout sync

**[`apps/screenpipe-app-tauri/components/workflows/rollout-sync.tsx:15`](https://github.com/arthrod/screenpipe/pull/1/files#diff-)** — **P3** — The forced-local override now silently outranks a remote revocation, with no structural gate.

With `enabled = isWorkflowsRolloutForcedLocally() || flag`, a build that sets `NEXT_PUBLIC_SCREENPIPE_WORKFLOWS_ROLLOUT=1` starts syncing `{ enabled: true }` to the engine on first mount — before PostHog resolves — and keeps re-asserting it every 30 s (`rollout-sync.tsx:19-21`) even after the remote flag resolves `false`. That is the documented intent for the hackathon demo machine (`lib/workflows/rollout.ts:8-12`) and it is covered by `rollout.test.tsx:100-115`, so this is not a behavior bug. The gap is that the override is a build-time `NEXT_PUBLIC_*` env var with no dev/mock-build guard: a packaged build produced with the var set (e.g., inherited from a developer shell) would permanently override remote revocation for every user, with no Settings escape hatch. Today nothing sets it in CI or release scripts — I checked `.github/`, package scripts, and the repo, and it appears only in `rollout.ts`, its test, and three hackathon docs. Since the guarantee is currently procedural, consider making it structural, e.g. `process.env.NODE_ENV !== "production" && process.env.NEXT_PUBLIC_SCREENPIPE_WORKFLOWS_ROLLOUT === "1"`, or asserting the var is unset in the release build path.
