## Content review — `focus_aware_controller.rs` (PR head version = merge-base version)

Focus asked: "pause/resume must never drop authorized recordings." Verdict: **the
invariant holds** in this code, by fail-open construction. Not a PR change — recorded here
so the lead knows the slice's substance was actually reviewed.

- The only two throttle states are bounded. Warm keeps a ~5s visual-diff cadence and
  **falls through to a full capture when the diff crosses threshold**
  (`crates/screenpipe-engine/src/event_driven_capture.rs:1512-1521`). Cold releases the
  SCK stream once on entering Cold (`event_driven_capture.rs:1439-1446`) but the loop
  re-checks state every ≤5s via a 5s backstop select
  (`event_driven_capture.rs:1560-1572`), and every focus/unknown event wakes all Cold
  loops (`focus_aware_controller.rs:179,191,336-342`).
- Three independent fail-open paths prevent a wedged focus source from pausing capture
  forever: Unknown focus → all Active (`focus_aware_controller.rs:288-290`); no focus
  event for 30s → all Active (`focus_aware_controller.rs:270-278`); no tokio runtime /
  Null tracker → subscriber skipped, all Active (`focus_aware_controller.rs:119-125`).
- Resume after pause invalidates persistent stream handles so the first post-pause frame
  is fresh (`event_driven_capture.rs:1577+`), and triggers drained while Cold are
  reported as dropped to the linker rather than TTL-evicted silently
  (`event_driven_capture.rs:1544-1559`).
- Pre-existing nits (not posted; not PR changes):
  - Doc comment promises "or a 5s backstop fires" (`focus_aware_controller.rs:24-25`) but
    the backstop lives in the consumer (`event_driven_capture.rs:1568-1571`), not here.
  - `Drop` sets `stop_flag` but never calls `tracker.stop()`
    (`focus_aware_controller.rs:407-411`); without an explicit `shutdown()` the
    subscriber task stays blocked in `rx.recv().await` holding an `Arc` to the controller,
    leaking it (only `Closed`/stop-flag-before-recv break the loop,
    `focus_aware_controller.rs:127-149`).
  - Mixed mutex-poison strategy: `.expect("... poisoned")` panics on `current_focus` /
    `last_focus_time` / `monitor_notifies` (hot-path queries called every capture
    iteration), while `touch_last_event` / `wake_all_monitors` / `shutdown` silently skip
    on poison (`focus_aware_controller.rs:194-198,337,353`). A poisoned `current_focus`
    would turn every `state_for_monitor` call into a panic — fail-loud, but on the
    recording hot path.

## Content review — `macos_run_loop.rs` (exists only at origin/main; not at PR head)

Focus asked: "thread safety and no busy-waiting." Verdict: **sound**, and irrelevant to
this PR (base-side file, 82 lines, read via `git show origin/main:...`).

- Thread safety: `CompletionSource` is `unsafe impl Send` for a `cf::RunLoopSrc` created
  on the main thread and `signal()`-ed from the worker; CF documents
  `CFRunLoopSourceSignal`/`CFRunLoopWakeUp` as callable from any thread, and the comment
  states that justification. Ordering is safe: worker does `send(result)` **before**
  `completion.signal()`, and the main loop only reads via `try_recv` after
  `run_in_mode` returns from handling the source.
- No busy-wait: the main thread alternates `receive.try_recv()` with
  `cf::RunLoop::run_in_mode(mode, 3600.0, true)`, which blocks when nothing is ready; the
  (deliberately empty) `completion_ready` perform callback is wakeup-only, so there is no
  empty spin. The 3600s timeout path just re-enters the loop.
- Panic discipline: worker runs under `catch_unwind(AssertUnwindSafe(work))`, result is
  re-raised on the main thread via `resume_unwind`; main-thread requirement enforced with
  `pthread_main_np()`.
