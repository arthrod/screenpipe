**[P2] `apps/screenpipe-app-tauri/lib/automation-flows/demo-shortcut.test.ts:38` — the native↔web event-name contract is enforced only by comments; pin it with a test.**
`DEMO_SHORTCUT_EVENT` (`demo-shortcut.ts:17`) must equal `DEMO_SHORTCUT_EVENT` in `src-tauri/src/shortcuts.rs:28`, and today the only guards are mirrored "keep in sync" comments on both sides. The listener test can't catch a drift: it mocks the entire `demo-shortcut` module with a hardcoded literal (`demo-shortcut-listener.test.tsx:45-48`) and then emits that same literal (`:73`, `:79`), so if the TS constant were renamed, all 10 tests in this area still pass while the real native press becomes a silent no-op — `emit_to` succeeds, no listener matches, nothing logs in the UI. Since the chord parsing itself lives in Rust (`parse_shortcut`, tested at `shortcuts.rs:643-652`), this event name is the one contract this test file can actually pin: import the real `DEMO_SHORTCUT_EVENT` from `./demo-shortcut` (not the mock) and assert `expect(DEMO_SHORTCUT_EVENT).toBe("shortcut-automation-flows-demo")`, ideally next to a comment pointing at the Rust constant.

**[P3] `apps/screenpipe-app-tauri/lib/automation-flows/demo-shortcut.ts:4` — the "⌃⌥⌘D" notation is macOS-only; the registered chord is different on Windows/Linux.**
The native registration is `"Control+Alt+Super+D"` (`shortcuts.rs:26`) and `parse_shortcut` maps `SUPER`/`CMD`/`COMMAND` all to `Modifiers::META` (`shortcuts.rs:567`). On macOS META is ⌘ (the Rust test `demo_shortcut_is_control_option_command_d` at `shortcuts.rs:643` confirms the intent), but on Windows and Linux META is the Win/Super key, so the chord a presenter there must press is Ctrl+Alt+Win+D — and every doc comment in this slice says "⌃⌥⌘D" (`demo-shortcut.ts:4`, `find-automation.ts:4`, `demo-task/detected-task.ts:10`, also `reset-demo-flows.ts:4` and the listener). A one-line "⌃⌥⌘D on macOS / Ctrl+Alt+Win+D elsewhere" in the header comment of `demo-shortcut.ts` would stop a Windows presenter from concluding the shortcut is broken. (The bigger issue that this chord is registered in every build is already covered by an existing review thread on `shortcuts.rs:527`; not repeated here.)

**[P3] `apps/screenpipe-app-tauri/lib/automation-flows/demo-shortcut.ts:59-62` — an `openTask` failure after a successful notification reports "Demo not started", and no test covers this path.**
When `findAutomation` returns `notified: true` but the follow-up `await deps.openTask()` rejects (`demo-shortcut.ts:61`), the rejection propagates to the listener's catch (`demo-shortcut-listener.tsx:37`), which toasts "Demo not started" with the error. That message is wrong in this case — the demo did start, the task was installed and the notification is out; only opening the Task Page failed — so a presenter would re-run the whole reset for nothing. Either catch `openTask` here and tell something accurate ("the task did not open — open it from the notification"), or add a test asserting the intended behavior; today the edge is untested in `demo-shortcut.test.ts` (all 8 tests either succeed at `openTask` or never reach it).
