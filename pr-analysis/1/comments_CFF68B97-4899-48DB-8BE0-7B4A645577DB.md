## Review: dev mocks + `getFlowActivationKey` binding

Reviewed `lib/dev/browser-engine-mock.ts`, `lib/dev/browser-tauri-mock.ts` (dev-only gating) and `lib/utils/tauri.ts` (binding vs Rust command). The production gate checks out at runtime: the mocks install only when `NEXT_PUBLIC_SCREENPIPE_WEB_DEV` is `mock`/`live` (`lib/dev/browser-runtime.ts:39-40`, engine mock additionally only in mock mode at `browser-runtime.ts:79`), and that var is set only by `scripts/dev-web.ts:41` and the ephemeral `next dev` eval job in `test-frontend.yml:121` — no release workflow sets it. The binding matches `get_flow_activation_key() -> String` (`src-tauri/src/automation_flows.rs:30`). `bun x vitest run --config vitest.config.ts lib/dev/browser-runtime.test.ts components/automation-flows/__tests__/api.test.ts` passes 48/48; `bun run typecheck` passes. Two nits below, no blockers.

**[P3] `apps/screenpipe-app-tauri/lib/dev/browser-tauri-mock.ts:882` — the live-mode `null` diverges from the command contract and is the untested branch.** The real command always returns a `String` (`automation_flows.rs:30`) and the generated binding types it `Promise<string>` (`lib/utils/tauri.ts:755`), but the mock resolves `null` when `mode === "live"`. Today that is absorbed by the only caller — `api.ts:222` does `(await commands.getFlowActivationKey()) || null` inside a try/catch — and the ticket-14 rationale (a browser has no desktop key, so activation is refused) is sound. But `api.test.ts:31` bridges the mock with `invoke("get_flow_activation_key") as string`, hiding the mismatch from the type system, and `browser-runtime.test.ts` has no coverage of either branch of this case. A two-line addition there — `createBrowserIpcMock({ mode: "mock", ... })("get_flow_activation_key")` equals `BROWSER_MOCK_FLOW_ACTIVATION_KEY`, and the same with `mode: "live"` equals `null` — would pin the documented divergence so a future caller that trusts `Promise<string>` can't silently trip over `null` in browser-live mode.

**[P3] `apps/screenpipe-app-tauri/lib/dev/browser-engine-mock.ts:211` — "cannot ship in production" holds at runtime but not at bundle level.** The env gate is a runtime no-op guard, yet `app/layout.tsx:8` imports `lib/dev/browser-runtime` as an unconditional side-effect import (pre-existing on main), so this PR's new flows fixture and mock code — plus the fixed activation-key string from `components/automation-flows/mock.ts:20` — compile into the production JS bundle as dead code. It is inert: the engine generates 244 random bits per process and compares in constant time (`crates/screenpipe-engine/src/automation_flows.rs:153-175`), so the mock key can never activate a Flow against a real engine. Since the focus of this review is production shipping, worth recording that the exclusion is behavioral only; converting the two static imports in `browser-runtime.ts:11-18` to dynamic `await import(...)` calls issued after the env-var check would give true bundle-level exclusion without changing the `bun run dev:web` loop.
