## Review of `crates/screenpipe-engine/src/automation_flows.rs` (final third: activation, pause/shutdown, event emission)

**P2 — `crates/screenpipe-engine/src/automation_flows.rs:1554` — the shutdown wait only sees executions with n8n status `running`.**
`deactivate_flow`, `delete_flow` and `update_flow` all rely on `N8nApi::unpublish` → `is_running`, which polls n8n with a `status=running` filter (`automation_flows.rs:846–849`). Yet the file's own `last_execution` maps `"running" | "new" | "waiting"` to running (`automation_flows.rs:804`), i.e. it acknowledges executions that are mid-flight without status `running` — notably an execution parked on a Wait node (`waiting`) or taken-but-not-yet-started (`new`). If n8n reports such a status while a trigger message is in flight, `unpublish` sees "nothing running", unpublishes immediately, and that message is lost — the exact loss `RunningWait` exists to prevent (module doc at `automation_flows.rs:186–194`). The integration suite's fake n8n only ever creates `status: "running"` executions (`tests/automation_flows_test.rs:137–148`), so this path is untested. Suggestion: query without the status filter (or with `status=new,waiting,running` as n8n accepts) and reuse the same status mapping as `last_execution`. I could not verify real n8n's status taxonomy from this checkout, so this may be theoretical — but the inconsistency between the file's two status mappings is real either way.

**P2 — `crates/screenpipe-engine/src/automation_flows.rs:1519` — activation records whatever n8n published as the reviewed version, without asserting it is the version the user read.**
`published_version` comes from the publish response's `activeVersionId` (1515–1518) and is stored as `reviewed_version_id` (1519–1520) and logged, with no check that it equals `version`, the id the user reviewed and that passed the check at 1490. If the n8n workflow changes between `load_flow` (1485) and `switch("publish")` (1512) — an edit saved in the n8n editor in that window — whatever n8n actually publishes gets recorded as user-reviewed, silently defeating the invariant the whole design rests on ("only the version the user read goes live"). Whether n8n's publish endpoint refuses a stale `versionId` I could not verify from here; a three-line local guard makes the invariant hold regardless: if `published_version != version`, return `FlowError::VersionChanged` instead of recording it.

**P2 — `crates/screenpipe-engine/src/automation_flows.rs:1545` — the global `write_lock` is held across the unpublish polling wait (up to ~90 s), freezing every other mutating route.**
`deactivate_flow` (lock 1545, `unpublish` 1554), `delete_flow` (1584, 1604) and `update_flow` (1675, 1692) hold the single `write_lock` while `unpublish` polls every 1 s up to the 90 s deadline (plus up to 20 s per reqwest call, `automation_flows.rs:256–260`; `RunningWait` defaults via `server.rs:435`). During one Flow's `flow_running` wait, every state-changing route is blocked — including activating a different Flow, creating, and draft steps — and there is no request timeout on these routes nor in the app's flow API client, so callers hang with no bound. Since the lock only needs to serialize store reads/writes and n8n mutations, consider scoping it per operation (re-read the store under the lock after the wait) or keying it per Flow id, so one stuck execution cannot freeze the whole Flows UI.

**P3 — `crates/screenpipe-engine/src/automation_flows.rs:1501` — the already-running early return leaves `dismissed` set.**
The idempotency path at 1501–1505 returns before `record.dismissed = false` (1521–1522), so the "Turned on: no longer set aside" rule only applies on the publishing path. Reachable state: a reviewed Flow is dismissed (allowed while off), then switched on from the n8n editor at the same version, then the user clicks « Turn on » — the click returns early, `dismissed` stays true, and once the Flow is paused again `derive_status` (1146–1159) reports `dismissed` instead of `paused`. Clearing the flag before the early return keeps the two paths consistent.

**P3 — `crates/screenpipe-engine/src/automation_flows.rs:1696` — every chat modification is logged as `by: "chat"`, whoever the caller is.**
`update_flow` takes no activation credential and cannot tell the chat from a pipe or an MCP client, yet both log entries (1694–1696 and 1727) hardcode `"chat"`. The `ActivationEvent` doc (1087–1089) promises `"api"` for "a deactivation by any other local caller" — `deactivate_flow` honors that via `from_user`, but modifications misattribute non-chat callers. Either attribute unknown callers as `"api"` (like deactivation does for non-user clicks) or fix the doc; the current audit log says the chat made changes no chat made.
