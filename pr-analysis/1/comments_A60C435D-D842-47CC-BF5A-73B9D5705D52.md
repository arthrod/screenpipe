## Review: `flow-graph.tsx` (graph rendering)

Checked with the graph's own test file (16/16 passing: `bun x vitest run --config vitest.config.ts components/automation-flows/__tests__/flow-graph.test.tsx`), a clean `bun run typecheck`, and a repro of the layout math. The real-nodes/edges contract holds (sticky notes filtered engine-side, dangling edges dropped both sides), and the fit/pan/zoom degradation on narrow frames is sound. Three findings:

---

**[P2] `apps/screenpipe-app-tauri/components/automation-flows/flow-graph.tsx:190` — a context chain two levels deep lands exactly on the next row of step cards.**

`rowStride` reserves exactly one 216 px context row per step row (`2 * ROW_HEIGHT`, line 190), but a context node whose parent is itself a context node is placed a further `ROW_HEIGHT` below it (line 209). Since step rows sit `2 * ROW_HEIGHT` apart when any context node exists (line 190), a level-2 context node lands at `parentStepY + 2 * ROW_HEIGHT` — precisely the next step row's y — and overlaps it whenever their columns coincide. This is the standard n8n "auto-fixing output parser" wiring (chat model → auto-fixing parser → agent) over a workflow with a lower branch row, which the demo workflow itself has ("Let Jira index" under "Ticket already created?"). Reproduced by running the `groups`/`contextParents`/`layout` functions copied verbatim from this file on such a fixture: the chat model and the lower step both land at (234, 432) — full card overlap, hiding a step the reviewer needs to read. The "No two cards overlap" test (`__tests__/flow-graph.test.tsx:224-230`) only covers the single-level fixture, so it cannot catch this. Suggested fix: derive the context depth per row (or globally) and size `rowStride` as `(1 + maxDepth) * ROW_HEIGHT`, and add a two-level fixture to the overlap test.

---

**[P2] `apps/screenpipe-app-tauri/components/automation-flows/flow-graph.tsx:65` — a disabled n8n node renders exactly like an active step.**

`StepCard` gives every node the same card, and nothing upstream marks disabled nodes: the engine's `review_graph` reads only type/name/position/notes (`crates/screenpipe-engine/src/automation_flows.rs:1164-1191`, sticky notes are the only filter at :1165), `disabled` is otherwise referenced just once in the engine — the n8n-API key allowlist (`automation_flows.rs:101`) — and `FlowNode` carries no flag (`components/automation-flows/api.ts:29-35`). n8n skips disabled nodes during execution, so on the screen whose purpose is "read what will run, then Turn on", a step the user disabled in n8n looks live and reviewed. Suggested fix: carry `disabled` through `FlowNode` and render the card dimmed/"disabled" the way n8n's canvas does; a test asserting the treatment would close both halves of the gap.

---

**[P3] `apps/screenpipe-app-tauri/components/automation-flows/flow-graph.tsx:281` — any frame resize throws away the reviewer's zoom and pan.**

The ResizeObserver refits the view on every observation tick, and the comment makes keeping the picture centred an explicit goal — but `fitView` also resets zoom and pan, so a scrollbar appearing or the window being nudged snaps a reviewer who had zoomed into one branch back to the whole graph. Cheap guard: set a flag in `onMoveStart` and skip the refit once the user has moved the view themselves (keep refitting until then).
