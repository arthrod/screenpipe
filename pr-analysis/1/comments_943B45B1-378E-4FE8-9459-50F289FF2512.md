## Review: `flows-tab.test.tsx` lines 1–600 — assertion quality & fixture realism

Three findings, all P3 (no blockers in this slice). The suite is high quality overall — exact ordering assertions, role-based queries, and negative invariants ("nothing activates without a click", flows-tab.test.tsx:343) are exactly right.

---

**P3 | `apps/screenpipe-app-tauri/components/automation-flows/__tests__/flows-tab.test.tsx:390` — `FlowRun` fixtures omit the required `retried` field**

The four runs in the D18 Activity test (`flows-tab.test.tsx:390-395`) and the `run()` helper at `flows-tab.test.tsx:423-430` are annotated `FlowRun` but omit `retried`, which the type requires (`api.ts:79`). The retry-suite fixtures right below do set it (`flows-tab.test.tsx:465, 474`), so the file is internally inconsistent. There is no runtime failure — `flow-activity.tsx:103` treats `undefined` as falsy, so failed run e4 still gets its Retry button — but that also means the fixtures under-specify the scenario: the list they describe contains a failed, not-yet-retried run whose Retry button the test silently ignores. Root cause worth fixing once, PR-wide: `tsconfig.json` excludes `**/__tests__/**` and `**/*.test.tsx` from `typecheck`, so every type annotation in this file is unchecked (vitest does not typecheck either). Adding `retried: false` keeps the annotations honest; longer term, including tests in a separate `tsc` pass would have caught this and any future drift.

**P3 | `apps/screenpipe-app-tauri/components/automation-flows/__tests__/flows-tab.test.tsx:249` — recovery from "n8n is unreachable" never asserts the banner is gone**

The test asserts the row reappears and `calls === 2` after "Try again", but never asserts the error alert was removed. If a regression kept the "Could not reach n8n" alert mounted over the recovered list, this test would still pass. One line fixes it: `expect(screen.queryByRole("alert")).toBeNull()` after the row is found (the Health-banner suite already uses this `queryByText(BANNER)` pattern for its own banner, so the file's conventions support it).

**P3 | `apps/screenpipe-app-tauri/components/automation-flows/__tests__/flows-tab.test.tsx:281` — hard-coded calendar dates make these assertions machine-timezone-dependent**

`^Last run: Sat, Oct 17, \d{2}:\d{2} [AP]M · succeeded$` (also :419, :592) hard-codes the fixture date and only tolerates the hour. The guard comment at :280 scopes it to UTC−9…UTC+14, which holds for the `09:0xZ`/`12:0xZ` fixtures used here — but the identical pattern broke in this very file at :790 (the `02:05Z` fixtures render as "Oct 16" on any UTC≤−3 machine; verified: 69/70 pass with `TZ=EDT`, 70/70 with `TZ=UTC`). Deriving the expected local date from the fixture timestamp (e.g. build the regex from `new Date(run.startedAt)` in the test's own locale) removes the whole failure class instead of relying on each site remembering its safe band.
