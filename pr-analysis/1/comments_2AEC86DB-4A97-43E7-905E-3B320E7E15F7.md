## Slice review: `lib/workflows` — rollout, desktop-platform, timeline

Two findings from reviewing this slice (assistant-prompt.ts and runtime.ts are unchanged in this PR — verified with `git diff origin/main...HEAD` — so nothing to raise on them).

---

**[P2] `apps/screenpipe-app-tauri/lib/workflows/rollout.ts:13-17` — the local rollout override is a build-time constant with no production guard.**

`NEXT_PUBLIC_SCREENPIPE_WORKFLOWS_ROLLOUT` is inlined into the JS bundle at build time, so `isWorkflowsRolloutForcedLocally()` is baked into whatever bundle was last built on that machine. The comment says this is for a local hackathon demo build, but nothing enforces that: if a production/distributed bundle is ever built on a machine or CI runner that happens to export the var, every user of that build permanently bypasses the PostHog `workflows` gate — and `WorkflowsRolloutSync` (mounted in every non-overlay window, `app/providers.tsx:199`) will then re-assert `{ enabled: true }` to the engine every 30 s (`components/workflows/rollout-sync.tsx:19-21`). The fail-closed default itself is good (strict `=== "1"`, and `rollout.test.tsx:100-105` proves `""`/`"0"`/`"true"` stay off — I ran that suite, 11/11 pass), and the "background AI still needs explicit opt-in" claim holds on the frontend (`scheduled-discovery.ts:22-25`, `:59-76`). But the release-safety currently rests purely on the build machine's env hygiene. Consider guarding the override to non-production builds (e.g. refuse when `NODE_ENV === "production"`), or at least logging a loud warning when it is active, so a demo affordance can't silently ship as a flag bypass.

**[P3] `apps/screenpipe-app-tauri/lib/workflows/desktop-platform.ts:163-166` — the four automation-flow methods skip the file's `!browserPreview` gating convention.**

Every neighboring native capability in this object is added via `...(!browserPreview ? { ... } : {})` (`:132`, `:133`, `:145`, `:155`, `:167`), but `createAutomationFlow`, `canCreateAutomationFlow`, `findAutomationFlow` and `openAutomationFlow` are added unconditionally. They are internally browser-tolerant (pure Set lookup at `automation-flows.ts:40-41`, try/catch-guarded localStorage at `:72-76`, web-dev branches in `components/automation-flows/api.ts:121` and `:373`), so this may be deliberate — but in `WEB_DEV=mock` the enabled `canCreateAutomationFlow` (demo task in `CREATABLE_TASK_IDS`, `automation-flows.ts:38`) offers a "Create automation" click whose `localFetch` call cannot succeed in the mock loop, so the user gets the generic "Could not create the automation" message instead of a mock outcome. If the mock loop is meant to exercise the create path, it needs a mock; if not, these four belong under the same `!browserPreview` gate as the rest for consistency.
