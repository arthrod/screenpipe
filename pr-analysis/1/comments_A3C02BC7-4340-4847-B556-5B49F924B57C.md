**Review slice: failure reporting (`crates/screenpipe-engine/src/automation_flows/failures.rs`) and retry (`crates/screenpipe-engine/src/automation_flows/retry.rs`)**

---

**P1 · `crates/screenpipe-engine/src/automation_flows/failures.rs:332` — A failure notification suppressed by quiet hours or a pause is recorded as delivered and never retried, so the failure is reported nowhere.**

`notify()` classifies every 2xx answer whose `message` is not exactly "Notification sent successfully" as `Undelivered::Gated`, and `health::notify_once` records Gated runs in the ledger as notified (`crates/screenpipe-engine/src/automation_flows/health.rs:240-244`), after which `report_failed_runs` skips them forever (`health.rs:405-407`). But the app's `/notify` suppression paths — quiet hours/snooze/master-off (`apps/screenpipe-app-tauri/src-tauri/src/notifications/routes.rs:300-318`), the "Pipe notifications" toggle (`routes.rs:349-369`), per-pipe mute (`routes.rs:392-406`) — all return *before* the history write at `routes.rs:457` (the comment at `routes.rs:294-299` states suppressed alerts "never write history either"), and this notice is `type: "pipe"` (`failures.rs:277`) with no critical-type or VIP punch-through (`gate.rs:10-19`, `gate.rs:82-110`). Net effect: a run that fails while quiet hours, snooze, or a pause is active produces no panel, no history row, and a ledger entry that forbids any retry — the D16 promise ("A failed Flow run is reported", `failures.rs:5`; "shows each failed run once", `failures.rs:227-228") silently fails for the most common miss. `Delivery::Gated` is documented as "handled, never retried" (`health.rs:202-203`), but "handled" is the false premise here: nothing survives the suppression. Suggested fix: classify the pause/disable/mute answers as retryable (return `Unreachable`-style so the ledger stays unmarked and the D19 check re-delivers once the pause lifts — the backoff in `health.rs:75-87` already handles this), reserving terminal treatment for "duplicate notification suppressed" / "Notification already sent", which do mean the user saw it. Related fragility in the same lines: success is recognized by exact English copy — the app's own client repeats the string (`apps/screenpipe-app-tauri/lib/automation-flows/find-automation.ts:57`) and `ApiResponse.success` is `true` on every 200 including suppressions, so a wording change on either side reclassifies outcomes; a machine-readable outcome field would be safer.

**P2 · `crates/screenpipe-engine/src/automation_flows/retry.rs:75-81` — `retryable()` and `health::failed()` classify the same execution differently when n8n omits `status`.**

`retryable()` treats a missing `status` as "ended" (`!matches!(None, Some(..))` is `true`), so an execution with no `status` and no `stoppedAt` — i.e. possibly still running, on an n8n whose public API omits `status` — then only needs `finished != true` and a null `retrySuccessId` to be sent to n8n's retry endpoint, which answers with an error the route surfaces as 502 `n8n_failed` instead of the intended 409 `run_not_failed`. The health check's own classifier handles this shape defensively: `failed()` requires `finished == false` *and* a present `stoppedAt` when `status` is absent (`crates/screenpipe-engine/src/automation_flows/health.rs:447-452`). Since both decide "did this run fail/need a retry" over the same n8n payloads, extracting one shared classifier (or at minimum requiring `stoppedAt` here as `failed()` does) removes the drift before more call sites copy one or the other.

**P2 · `crates/screenpipe-engine/src/automation_flows/failures.rs:289` — the retryable-vs-terminal decision logic has no tests.**

`retryable()` (retry.rs:75-81), `handled_email()` (failures.rs:289-308), `failure_notice()` (failures.rs:229-283) and `notify()`'s status×message matrix (failures.rs:330-337) are pure functions over JSON — exactly the classification logic that decides whether a failure is retried, re-delivered, or dropped — and none has a unit test: `cargo test -p screenpipe-engine automation_flows` runs 5 tests, all in `automation_flows::tests` and `health::tests` (pacing only). JSON fixtures for these four (a Gmail-shaped `from: {value, text}`, an IMAP-shaped string `from`, a `retrySuccessId`-bearing run, each `/notify` answer variant) would pin the wire contract against n8n and the notification server far more cheaply than the integration paths that currently cover them: nothing does.

**P3 · `crates/screenpipe-engine/src/automation_flows/retry.rs:67-69` — in n8n queue mode the retry is reported as failed although it started.**

The module assumes "n8n answers once the retried run has finished" (retry.rs:24-26), and the 180 s wait plus the timeout→`RetryStillRunning` mapping (retry.rs:98-104) match regular-mode behavior. In queue mode, n8n's public retry endpoint answers immediately with the new execution still in `new`/`running`; `flow_run` then returns `None` (`activity.rs:87`) and the route answers 502 "n8n answered the retry without its run" even though the retry is underway. The user recovers via Activity, and I could not verify the bundled n8n's execution mode from this repo — but a `None` from `flow_run` on a 2xx could map to `RetryStillRunning` (still running, outcome in Activity) instead of `N8nFailed`, which is true in both modes.
