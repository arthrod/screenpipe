Slice: `apps/screenpipe-app-tauri/lib/notifications/actions.ts` (focus: action dispatch, id validation, unknown-action handling), `lib/notifications/actions.test.ts` (unit tests), `lib/__tests__/notification-actions.test.ts` (integration-level tests). Diff base `origin/main...HEAD`: +91/−1 across the three files (`git diff origin/main...HEAD --stat`).

## What this slice changes

1. **`windowForDeeplink` gains a Flow Review Screen branch** (actions.ts:103-105): a `screenpipe://flows/<id>` deeplink now resolves to `{ Home: { page: "pipes&tab=flows&flow=<id>" } }` via the new helpers `flowIdFromReviewLink` / `flowReviewPage` (lib/workflows/automation-flows.ts:102-115). Placed after the `workflowReviewLink` check and before artifact/meeting/activity; no overlap with those hosts ("flows" vs "view"/"meeting"/"activity"/"artifact"), so no existing route is shadowed.
2. **`routeNotificationDeeplink` returns early for flow links** (actions.ts:203-205): after `showWindowActivated`, it skips the meeting retry loop and the generic `deep-link-received` event. I verified this is sound: for an already-running Home, the Rust `show()` emits its own `navigate` event with `?section=pipes&tab=flows&flow=<id>` (src-tauri/src/window/show.rs:651-660), consumed by `followFlowsNavigation` (lib/workflows/automation-flows.ts:172-178); a cold Home is created directly on that URL (show.rs:1612-1613, `home_navigation_url` at 2189-2194). `screenpipe://flows` does not exist on origin/main at all (`git grep -n "screenpipe://flows" origin/main` → empty), so no pre-existing handler is suppressed.
3. **`api` actions get their headers from `notificationApiHeaders(action.url)`** (actions.ts:327, components/automation-flows/api.ts:243-245): only URLs matching `RETRY_PATH = /^\/automation-flows\/[A-Za-z0-9_-]+\/runs\/[A-Za-z0-9_-]+\/retry$/` receive the `x-screenpipe-flow-activation` UI credential (`clickHeaders`, api.ts:229-232); everything else gets plain JSON headers. Non-retry actions do no IPC at all (the regex fails before `activationKey()` runs), so there is no per-action Tauri roundtrip cost.

## How it fits the PR

This implements the app half of D16/D17. The engine's error workflow reports a failed run to `POST /automation-flows/:id/failures`, and `failure_notice` builds the notification with a `View Flow` deeplink (`screenpipe://flows/<id>`) and a « Retry » `api` action pointing at the relative retry path with `deeplink_url` set (crates/screenpipe-engine/src/automation_flows/failures.rs:256-272). On click, this slice routes the deeplink to the Review Screen and — for retry-shaped URLs only — attaches the webview-only credential so the engine's `retry_requires_user` gate (crates/screenpipe-engine/src/automation_flows.rs:531-532) treats it as the user's click. The three new integration tests mirror that contract end-to-end at the fetch boundary: retry sends the credential then opens the Review Screen; other actions (including a dot-segment traversal attempt `.../retry/../../../activate`) never carry it; a 409 `run_not_failed` throws and navigates nowhere (notification-actions.test.ts:81-142).

## Quality notes (positive)

- `flowIdFromReviewLink` (automation-flows.ts:102-110) parses in a try/catch (malformed `%` sequences → null), requires `host === "flows"`, and the id is re-encoded by `flowReviewPage` with `encodeURIComponent` (automation-flows.ts:113-115), so a decoded id containing `&`, `#`, or `/` cannot inject query params into the Home page payload; the Rust side round-trips it as `?section=pipes&tab=flows&flow=<encoded>` (show.rs:2189-2194).
- `RETRY_PATH` is strict and fail-closed: the id charset `[A-Za-z0-9_-]+` excludes `.`, `%`, `?`, `#`, and `/`, so a credential-bearing URL can neither contain a dot-segment nor be re-normalized to a different route server-side, and any query string or trailing garbage forfeits the credential. The unit test covers the traversal case (notification-actions.test.ts:117).
- Outside the desktop app (`bun run dev:web:live`), `activationKey()` returns null and `clickHeaders` degrades to plain JSON headers (api.ts:219-232), so the engine correctly refuses — behavior preserved.

## Risks / findings (details in the posted comments)

- **P3** — Header gating is URL-form-dependent: `RETRY_PATH` matches only relative paths, while `isLocalApiUrl` (lib/api.ts:266-281) and `localFetch` (lib/api.ts:238-240) accept absolute `http://127.0.0.1:<port>/automation-flows/.../retry`. An absolute-form retry action goes out bearer-authenticated but without the activation credential and dies on `retry_requires_user`. Fail-closed (not a security hole), and the only first-party producer sends the relative form (failures.rs:268).
- **P3** — The flow-review path ignores `shown.status === "error"` (actions.ts:203), unlike the calendar (actions.ts:170-171) and workflows (actions.ts:182-183) branches; since the bell removes the row whenever the executor resolves (components/notification-bell.tsx:254-270), a failed Home show makes a "View Flow"/« Retry » click vanish silently. Same gap as the pre-existing meeting path.
- **P3 (pre-existing, in-focus)** — `executeNotificationAction`'s switch has no `default` (actions.ts:256-432): an unknown/undefined `action.type` resolves successfully, and the bell then clears the entry as handled although nothing ran — contradicting the function's own contract comment at actions.ts:246-248 ("Throws on failure so callers can keep the row + report"). More consequential now that `api` dispatch is credential-bearing.
- **P3** — notification-actions.test.ts:82-83 claims the action is "exactly as the engine's failure notice sends it", but the engine's label is `"Retry"` (failures.rs:265), not `"Relancer"`. Behaviorally irrelevant today (the executor ignores the label), but the comment invites diffing against failures.rs.
- **P2 context, already on the PR** — coderabbitai[bot] flagged (on notification-actions.test.ts:110-125) that gating the credential on URL shape alone lets any local sender (pipe/chat agent) craft a retry action that spends the UI credential — a provenance problem. I verified their description against api.ts:243-245 and actions.ts:320-327 and did not re-post it; my absolute-URL finding above is the complementary, fail-closed direction and is distinct.
