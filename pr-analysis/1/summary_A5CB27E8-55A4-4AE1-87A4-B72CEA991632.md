## State of the slice at the PR head (context read, full files read; no PR changes to judge)

Both focus properties exist as pre-existing code, identical on both sides of the merge base:

- **Reader snapshot isolation** (`reader.rs`): reads take a revisioned `StorageReadToken` (`crates/screenpipe-db/src/storage/reader.rs:27-78`) whose `admit()` re-checks `storage_metadata.revision` / `_storage_revocation.revision` after decode and errors with "read revision changed" on mismatch; `consistent_read` retries within a budget (`reader.rs:81-104`); the read itself runs on a snapshot (`reader.rs:362-363`) with a final admission gate before returning (`reader.rs:509-511`). Staged rows come from SQLite inside the snapshot; sealed rows are decoded from checksum-verified parquet with per-row generation equality checks (`reader.rs:470-478`), so a file being replaced cannot yield a torn mix of old/new rows. This matches the focus; it is not PR work.
- **Seal-step crash recovery** (`sealing.rs`): a durable `payload_files` row in state `'encoding'` is committed before any file bytes are written (`crates/screenpipe-db/src/storage/sealing.rs:370-374`); encoded files are fs-synced up the directory chain before publish (`sealing.rs:413-424`); the publish transaction re-validates every row's generation/state/policy and retires the file pair on any mismatch (`sealing.rs:428-453`); fault checkpoints bracket the commit (`sealing.rs:480-483`). A crash between reservation and commit leaves an orphaned `'encoding'`/`'dirty'` row that `reclaim_once` retires once no `frame_payloads` row references it (`sealing.rs:513-517`) — and since `frames` text columns are only NULLed inside the same transaction that marks rows `'sealed'` (`sealing.rs:459-466`), data stays readable in SQLite until the commit lands. One test covers stale-member retirement (`sealing.rs:564-602`); I did not find a test in either file that kills the process between seal steps (fault-injection harness exists at `crates/screenpipe-db/src/storage/faults.rs`, used only via `checkpoint`, `sealing.rs:375,424,480,483,534,548`).
