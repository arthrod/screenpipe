# Reviewer summary — owned browser origin checks (`owned_browser.rs`)

Slice: `apps/screenpipe-app-tauri/src-tauri/src/owned_browser.rs` (139 added, 6 changed of the file's 2856 lines). Focus: app-origin blocking rule from issue #20. Comments file: `comments_A7A33547-040F-4C75-815F-D2522501F88C.md` in this directory.

## What the slice changes

Adds `is_app_origin()` (owned_browser.rs:1609-1627) and enforces it at two of the three navigation entry surfaces into the agent's owned browser:

1. **Agent-requested navigations** — `normalize_url()` now rejects app origins with an explanatory, agent-facing error ("the agent browser never loads app pages. Give the user a screenpipe:// link instead.", owned_browser.rs:1592-1597). This covers all four callers: `TauriOwnedHandle::eval_inner` (owned_browser.rs:809), `TauriOwnedHandle::navigate` (owned_browser.rs:1074), and the `owned_browser_navigate` / `owned_browser_tab_navigate` commands (owned_browser.rs:1871, 1905).
2. **Page-driven navigations** — the webview's `on_navigation` callback (owned_browser.rs:584-594) returns `false` to cancel any navigation to an app origin, so a visited page's links, redirects, JS `location` writes, or iframe top-level navigations cannot steer the agent browser into the app. Blocked navigations are logged (`warn!`) and intentionally do not emit the loading state event.
3. History back/forward (owned_browser.rs:1959-1981) and the cold-start `pending_url` path (owned_browser.rs:1256, only ever filled post-`normalize_url`) are transitively covered; all child webviews are created at `about:blank` (owned_browser.rs:1223-1232, 1291-1300, 1459-1468).

`is_app_origin` matches: schemes `tauri`/`ipc`/`asset`; `blob:` by recursing into the inner URL parsed from `url.path()`; `http(s)` hosts `tauri.localhost`/`ipc.localhost`/`asset.localhost` (trailing dot trimmed, case-insensitive via `url` normalization); plus, only in dev builds (`tauri::is_dev()` injected as a parameter for testability), loopback hosts on port 1420. The rule is over-inclusive by design (e.g. `http://tauri.localhost:8080` blocked, tested).

## How it fits the PR and why it matters

The PR adds Automation Flows including the `get_flow_activation_key` command cited in the new doc comment (owned_browser.rs:1605-1608). The threat model is real and verified, not theoretical: `src-tauri/capabilities/main.json:5-7` grants `"windows": ["*"]` with `"local": true` — so the owned-browser webview labels (`owned-browser`, `owned-browser-tab-*`) match, and an app page loaded inside the agent browser would get IPC with high-value permissions: `fs:allow-read-file` scoped `$HOME/**`, `shell:allow-execute` sidecar with `args: true`, `http:default` for all URLs (capabilities/main.json:42-46, 155, 334-344, 485-560). The module doc (owned_browser.rs:20-24) claims remote pages are rejected "only because no capability lists remote URLs" — that claim is exactly why app-origin pages are dangerous here: app origins are local, and local is allowed.

## Findings (details in comments file)

- **P1 — Windows subframe bypass.** wry 0.55.1 wires `on_navigation` to WebView2 `add_NavigationStarting` only and never registers `FrameNavigationStarting` (verified in `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/wry-0.55.1/src/webview2/mod.rs:674-698`; `grep -c FrameNavigationStarting` in that file = 0). A page can therefore embed `<iframe src="http://tauri.localhost/">` on Windows and the check at owned_browser.rs:587 never runs for that frame. Tauri's IPC init script runs in child frames on WebView2 (Microsoft `AddScriptToExecuteOnDocumentCreated` docs, fetched this session: "runs on all top-level document and child frame page navigations"), and the ACL above would match the frame's local origin. Caveat stated honestly: whether the frame's invoke reaches tauri's `on_message` with a frame-derived origin (tauri-2.11.2 `src/webview/mod.rs:1743` uses `request.url`) could not be exercised from macOS — recommend Windows verification. Structural fix: stop granting sensitive capabilities to `windows: ["*"]`. macOS iframes are covered (repo comment owned_browser.rs:595-597 cites wry#1593), and `window.open` is denied by default on WebView2 (wry webview2/mod.rs:786 `SetHandled(true)` when no handler).
- **P3 — dev-server block misses IPv4-mapped IPv6.** `LOOPBACK` is `["localhost", "127.0.0.1", "[::1]"]` (owned_browser.rs:1620); `http://[::ffff:127.0.0.1]:1420/` canonicalizes to `[::ffff:7f00:1]`/`[::ffff:127.0.0.1]` (verified via Node WHATWG check) and matches neither. Dev-builds-only exposure.
- **P3 — silent block for humans.** Page-initiated navigations to the app are refused with only a `warn!` (owned_browser.rs:588); the user sees a dead link. The agent path gets the explanatory error; consider a sidebar notice for the human path.
