## Migration review (origin/main copy of the SQL)

**Idempotency on upgrade: sound.** Migrations here are SQLx migrations (`sqlx::migrate!("./src/migrations")`, `crates/screenpipe-db/src/db/setup.rs:682` on origin/main); `crates/screenpipe-db/src/migrations/README.md` (origin/main) states "SQLx applies only pending files and owns their transactions, checksums, and completion records" and "Conversion preserves `_sqlx_migrations`" — so one-shot, transactional application, and no `IF NOT EXISTS` is needed; the file matches sibling convention (e.g. `20261002190000_starred_sessions.sql` also uses plain `CREATE TABLE`). Ordering is safe on both fresh installs and upgrades: `20261016210000` sorts after `20261002190000`, which creates `starred_sessions` (its lines 4-10: `id TEXT PRIMARY KEY NOT NULL`, `start TEXT NOT NULL`, `revision INTEGER NOT NULL DEFAULT 1`). The backfill (migration lines 13-14) references only existing columns (`id`, `start`), runs before trigger creation so triggers never fire on the backfill, and the whole file commits atomically inside SQLx's per-migration transaction.

**Index correctness: correct.** `UNIQUE(session_id)` (line 10) serves both the triggers' `DELETE ... WHERE session_id = NEW.id` lookups (lines 16, 22) and the consumer JOIN; the AUTOINCREMENT PK (line 9) serves the feed scan. AUTOINCREMENT is not decorative here: the sole consumer is a sequence-cursor keyset query — `SELECT c.sequence, ... FROM _starred_session_sync c JOIN starred_sessions s ON s.id = c.session_id WHERE c.sequence > ?1 ... ORDER BY c.sequence LIMIT ?3` (`crates/screenpipe-db/src/db/starred.rs:29`, origin/main) — and without AUTOINCREMENT, SQLite could reuse a deleted max rowid, silently skipping rows for consumers already past that cursor. The trigger guard `WHEN NEW.revision <> OLD.revision` (line 21) cannot be bypassed by NULLs (`revision` is NOT NULL), and the only writer, `save_starred_session` (starred.rs, origin/main, ~lines 76-114), bumps `revision` on every real change via `ON CONFLICT(id) DO UPDATE SET ... revision=starred_sessions.revision+1` and short-circuits true no-ops in Rust before reaching SQL — so the feed emits exactly once per real edit.

**Two design notes (P3, not bugs today):**

1. **Delete cleanup is FK-cascade-only.** There is no `AFTER DELETE` trigger; cleanup relies on sqlx's default `PRAGMA foreign_keys = ON` (relied upon repo-wide, documented at `crates/screenpipe-db/src/db/mod.rs:417`, origin/main). Production code currently never deletes `starred_sessions` rows (only tests do, via raw SQL: `crates/screenpipe-db/tests/hybrid_storage.rs:1218` and `evals/coding-agent/graders/compressed-sqlx-upgrade.rs:177`, both origin/main), so no live dangling-row path exists. But the consumer's INNER JOIN (`starred.rs:29`) means deletions can never be echoed to the enterprise feed — a future unstar feature would silently disappear from sync output. Flag for the enterprise-sync owners' intent.
2. **Mixed timestamp semantics.** Backfill rows get `timestamp = session start` (line 14); trigger rows get wall-clock `'now'` (lines 18, 24). Harmless today (the cursor is `sequence`, timestamp is informational in the tuple returned at `starred.rs:23-28`), but a trap if anyone ever filters on `timestamp`.

## Disk-full VM test review (origin/main copy)

**Focus verdict — asserts recovery, not rejection: PASS.** The test asserts both halves honestly. Mid-fault (physics, not policy): at real ENOSPC it asserts a write error surfaces (`assert!(failed, "writes must stop at real capacity exhaustion")`, line 60), the writer hard-faulted (`write_queue_health().is_hard_faulted()`, 61-64), and the coordinator registered SQLITE_FULL=13 (`registered_sqlite_hard_fault(&path) == Some(13)`, 65-69). Recovery: space is freed (70-71), the faulted manager is closed (72; `close()` returns `()` per `crates/screenpipe-db/src/db/setup.rs:642`, origin/main, so bare awaits are correct), a reopened manager writes a NEW row successfully (73-79), and durability is proven across an *additional* independent reopen for both the pre-fault row `/fixture/before-full` (82-89) and the post-recovery row (90-94). This complies with AGENTS.md hot-path rules: the test does not bless dropping authorized recordings for processing-budget reasons — at physical capacity exhaustion bytes cannot be written; what it proves is pre-fault data retention and durable resumption after capacity returns, which is exactly the required semantics.

**Safety rails are solid** (lines 3-5, 11, 13-19, 30-46): `#[ignore]` gate, `SCREENPIPE_ISOLATED_VM_TEST=1` env assert, exact mount path + `.screenpipe-disposable-volume` marker file, tempdir confined to the fixture, 256 MiB write cap (256 × 1 MiB), refusal to proceed if the volume isn't genuinely small (43-46), and an assert that the filler failure is genuinely errno 28 / ENOSPC (34-38). It cannot touch a user volume. Freeing space *before* `close()` (70-72) is the correct order — a flush on a still-full disk could itself fail.

**Gaps:**

- **P2 (product, not test bug): recovery is restart-only.** The test proves a *new* DatabaseManager recovers; nothing asserts the running app resumes recording when space frees. I grepped origin/main for hard-fault handling and found latch/report paths (`crates/screenpipe-db/src/db/mod.rs:143-156`, `crates/screenpipe-db/src/db/maintenance.rs:55,1604-1608`) but no un-latch or auto-probe path. If that is the design, a user whose disk filled and then freed keeps a dead recorder until app restart. The owners of `b1266c89f` should either confirm intent or add an auto-recovery probe plus a test.
- **P3:** the byte-inflation trick — a 128 KiB synthetic path string per insert to force real bytes through the batched writer (line 50) — is uncommented.
- **P3:** magic number `13` for SQLITE_FULL (line 67) deserves a named constant in the coordinator.
- **P3 (brittleness, self-protecting):** `assert!(failed, ...)` (line 60) requires `insert_audio_chunk` to surface an Err synchronously within ≤16 attempts of 128 KiB each; if writer batching ever grows past ~2 MiB of tolerated backlog, the assert fires even though behavior is fine. Fails loud, but coupled to writer internals.

**Coverage context:** automated hard-fault coverage exists only as fault injection (`crates/screenpipe-db/tests/quarantine_self_heal_test.rs:340,428` latches a fault via `latch_sqlite_hard_fault(&path, 10)`, origin/main). The physical ENOSPC → recovery path is proven only by this manual VM test. Its commit message ("verify disk-full recovery") suggests it was run by its author; I could not verify that, and I did not run it — it requires a disposable macOS VM with the fixture volume mounted, which this environment does not have (and the file is not in this checkout).
