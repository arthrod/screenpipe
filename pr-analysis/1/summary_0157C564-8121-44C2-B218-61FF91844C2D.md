## What this slice changes

Two new files (541 insertions, no other files touched in this slice):

- **`infra/automation-flows/demo/reset.ts` (245 lines)** — the demo-machine reset
  tool. Library function `resetDemo()` plus a `bun`-runnable CLI entry
  (`import.meta.main`, reset.ts:227-245). It: (1) deletes from n8n every workflow
  recorded in `<dataDir>/automation-flows.json` with
  `sourceTaskId === "wf-novadesk-support-tickets"` (reset.ts:153-155) plus the
  fixed-id pre-imported copy `spNovaFlow000001` taken from the bundled workflow
  JSON (reset.ts:33-35, 169); (2) removes exactly those records from the store via
  tmp-write + rename (reset.ts:191-203); (3) clears the demo task's Task Page
  answers in the catalog (reset.ts:119-127, 205); (4) lists other
  `screenpipe-flow`-tagged workflows as "left untouched" (reset.ts:179-189). CLI
  prints progress, exits 1 with every failure reason, and never prints the API key.
- **`infra/automation-flows/demo/reset.test.ts` (296 lines)** — 13 tests: 10 unit
  tests against an in-process fake n8n (`Bun.serve` on 127.0.0.1:0,
  reset.test.ts:19-65) and 3 CLI tests spawning a real `bun` child with a fresh
  cwd/HOME/env so the operator's root `.env` key cannot leak in
  (reset.test.ts:243-254).

## Tests quality

Strong for an infra script: the fake n8n models the refusal paths reset relies
on (401, delete-while-active 400, archive-required 400, 409-while-unpublishing,
arbitrary refusals), the CLI tests spawn real child processes with sanitized
env and assert the key never appears in stdout+stderr (reset.test.ts:269) and
that no inbox/unread step sneaks back in (reset.test.ts:268). Failure-path tests
assert the conservative direction every time (records kept when n8n refused,
store untouched when unreadable, other flows intact).

## Risks / quality issues found (details in comments file)

1. **P3 — n8n DELETE/archive semantics contradict the engine's own docs.**
   reset.ts:94 says "n8n 2.x deletes only archived workflows" (and the test fake's
   `strictArchive` encodes it, reset.test.ts:57), while the engine's
   `delete_workflow` says the opposite: "n8n's public `DELETE` removes it, it does
   not archive it" (automation_flows.rs:874-881). Reset's order (DELETE → on
   refusal archive → DELETE, reset.ts:92-99) is safe under both, but one of the
   two claims about n8n 2.x is wrong and should be reconciled.
2. **P3 — `loadStore` accepts a JSON array** (reset.ts:111-112): `typeof [] ===
   "object"` and `flows === undefined` both pass, and the records step would then
   spread the array into an object (reset.ts:199), silently rewriting a malformed
   store instead of leaving it untouched as the same function promises.
3. **P3 — unpublish does not wait for running executions**: the engine waits
   (`RunningWait`, automation_flows.rs:857-879) so an in-flight run finishes;
   reset.ts:87-91 unpublishes immediately. Resetting mid-execution can cut a run
   and leave partial side effects (e.g. a half-created Jira ticket) that pollute
   the next rehearsal — the exact state this script exists to prevent.
4. **P3 — post-delete verification GET can spuriously fail the step**
   (reset.ts:101-102): a transient error there reports failure and keeps the
   record though the workflow is gone; self-heals on rerun (GET → 404 → record
   removed) but turns a successful reset into exit 1.

Not posted (below the bar, noted here only): the 409 retry loop treats any 409
as still-unpublishing (~10 s wasted on a permanent 409, reset.ts:68-75); store
write race with a concurrently-running engine is last-writer-wins on both sides
(engine `FlowStore::save` uses no lock either, automation_flows.rs:1129-1136) and
a resurrected stale record self-heals on the next reset — also reset's write
lacks the engine's fsync despite the parity comment (reset.ts:197 vs
atomic_file.rs:60-71); module-load `readFileSync`/parse of the bundled workflow
(reset.ts:33) breaks import with a raw stack if the file is missing, including
under `bun test`; the "other Flows" listing reads a single page of 250
(reset.ts:182) while the engine paginates (automation_flows.rs:1387) —
informational only.
