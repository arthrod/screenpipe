## Review: browser evals in `apps/screenpipe-workflows-web/scripts/` (sop-chat, video-chat, source-preview)

Context for all three comments: this PR does not modify these eval scripts (`git diff origin/main...HEAD` on the three files is empty), but it rewrites large parts of the `packages/workflows-ui` code they drive (12 files, e.g. `workflows-app.tsx`, `workflow-questions.tsx`, `screenshots.ts`). I ran all three evals at this PR's HEAD and at the merge base (`35ed62162`, via a worktree with the package swapped), using the documented setup (`bun run dev` in `apps/screenpipe-workflows-web`, then `node scripts/eval-<name>.cjs` against `localhost:1431/preview`).

**[P2] `apps/screenpipe-workflows-web/scripts/eval-sop-chat.cjs:36`** — This eval fails at HEAD, identically to the merge base, so its "reopen without generation" promise (the PASS banner at line 49) is currently enforced by a selector the product no longer serves. After `reload()` (line 34), the first workflow's guide button is labeled "Open SOP", not "Create SOP" — `packages/workflows-ui/src/workflows-app.tsx:730` renders `hasGuide ? "Open SOP" : "Create SOP"`, and `hasGuide` is set from `platform.guides.load` (`workflows-app.tsx:661-665`), which finds the guide saved in the first pass. My probe after reload showed `Create SOP=0, Open SOP=1`, and the eval times out waiting for "Create SOP" (12 s). Consequence: the actual reopen path — "Open SOP" should show "Before you start" without re-generating (no "Stop answer", lines 37-41) — is never tested. Since this PR changes the surrounding Task Page code (`workflows-app.tsx` +65) without fixing or flagging this, please either update the eval to click "Open SOP" after reload and assert no regeneration there, or reset the fixture's saved-guide state before the second pass. Note it was already broken when this branch forked, so this is not a merge blocker introduced by the PR — but AGENTS.md asks for eval commands and results in the PR body, and the body currently has none while two of the three relevant evals are red.

**[P2] `apps/screenpipe-workflows-web/scripts/eval-video-chat.cjs:25`** — This eval fails at HEAD (and identically at the merge base) with a strict-mode violation before reaching any of its video or streaming coverage: `getByRole('button', { name: 'Heading', exact: true })` resolves to 4 elements — the block-picker insert option (`packages/workflows-ui/src/document-block-editor.tsx:193`) plus the per-step "Heading" formatting buttons (`packages/workflows-ui/src/rich-text.tsx:165`) inside the "Step 1/2/3 text block" regions. As a result, this eval's unique streaming/cancel coverage (lines 68-71: "Create new video" → "Creating narration" → "Stop answer" → button restored) never runs, so a cancel-path regression would not be caught by the one eval documented as covering it (`docs/pr-assets/desktop-video-sop/blocks/README.md:8`). I drove that cancel sequence manually at HEAD and it currently works ("Stop answer" during "Creating narration" restores "Create new video"), so the behavior is fine — the guard is dead. Please scope the locator to the insert menu opened from "Add block after Guide summary" (e.g. resolve the menu container first, then click "Heading" inside it) so the rest of the eval runs again.

**[P3] `apps/screenpipe-workflows-web/scripts/eval-source-preview.cjs:20`** — The failure-state assertion is vacuous: it asserts count 0 of `"Screenshot will load from the recording"`, a string that exists nowhere in the UI source at HEAD or on origin/main (last touched by commit `4b8e082c6`, 2026-10-01, before this branch's merge base; verified with `git log -S` and `git grep`). The real failure texts are "Loading screenshot…" / "No captured screenshot available for this step." (`packages/workflows-ui/src/source-sop-screenshot.tsx:17`) and "Screenshot unavailable" / "This screenshot is no longer available." (`packages/workflows-ui/src/sop-screenshot.tsx:42,54`). The image-loading half of the eval is genuine and passes at HEAD — including with this PR's `screenshots.ts` change (embedded negative-frameId screenshots), which this fixture doesn't exercise since it resolves sources via `loadSourceScreenshot` (`apps/screenpipe-workflows-web/app/preview/page.tsx:31-34`), a loader that never fails. Suggest asserting against a live failure string and adding a fixture mode whose `loadSourceScreenshot` rejects, so the "no captured screenshot available" + retry path is actually covered.
