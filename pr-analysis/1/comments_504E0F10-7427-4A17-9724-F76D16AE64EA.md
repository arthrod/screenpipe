## Review — redact adapters slice (`rfdetr_mlx.rs`, `tinfoil.rs`, `tinfoil_image.rs`)

**[P1] `crates/screenpipe-redact/src/adapters/tinfoil.rs:1` — this PR does not actually modify these three adapters, and the branch is missing a base-side privacy commit that does.** `git diff origin/main...HEAD` is empty for all three files and their blob hashes are identical to the merge base (35ed6216) — the differences visible against the `main` tip are entirely commit `5ce7edfcd` "Gate captured data on PII completion receipts (#7634)", which lives on origin/main and is not in this branch. That commit rewrites the `Redactor` trait surface of exactly these adapters (adds `redact_required`/`provides_model_detection`, makes the version constants `pub(crate)`), so the branch is 41 commits behind main on privacy-critical code. The branch is 315 commits ahead, GitHub can't even render this PR's diff (HTTP 406, >20k lines), and whatever CI ran on this head never saw `5ce7edfcd`. A merge commit would resolve these files automatically, but please merge `origin/main` into this branch before merging the PR so tests run on the combined tree — especially since the missing commit is the one gating captured data on PII completion receipts.

**[P2] `crates/screenpipe-redact/src/adapters/tinfoil_image.rs:243` — `DetectRequest` derives `Debug` including `image_b64`, so one accidental debug log dumps a full screenshot.** The struct carries the base64 of the entire frame, and `#[derive(Debug, Serialize)]` means any future `tracing::debug!(request = ?req)` writes the whole image into local logs. The text adapter clearly got this right: `FilterRequest` derives only `Serialize` (`tinfoil.rs:127-137`). Drop `Debug` here (or hand-implement it eliding `image_b64`); `DetectResponse`/`RawDetection` can keep theirs since detections are not sensitive.

**[P2] `crates/screenpipe-redact/src/adapters/tinfoil_image.rs:309-313` — the full non-success response body is embedded into `RedactError::HttpStatus` and can carry the image (or OCR text) into logs.** On a non-2xx the whole body is read and stored (`tinfoil_image.rs:311`, same pattern in `tinfoil.rs:404`), and `RedactError`'s `Display` interpolates it (`error.rs:14-18`), so reconciliation-worker logs receive it verbatim. FastAPI/Pydantic 422 responses echo the offending `input` value — for `/image/detect` that can be the entire base64 screenshot (and for `/filter`, the OCR text), i.e. the exact data this pipeline exists to scrub gets persisted into error logs unbounded. Defense-in-depth fix: truncate the body (e.g. 1–2 KB) before embedding it in the error. Doesn't change the attested-transport story, just keeps failure paths from re-materializing payloads.

**[P2] `crates/screenpipe-redact/src/adapters/rfdetr_mlx.rs:223` — the `mlx-mac` feature-on path is never compiled by CI; only the stub is.** CI tests run with default features (`ci.yml:121`, `--exclude screenpipe-rfdetr-mlx`) and clippy likewise (`style.yml:101-107`), so the ~200-line `imp` module compiles only inside release builds (`release-app.yml:200`, `release-cli.yml:146`) which run no tests. For what it's worth, this reviewer also could not compile-check it locally: `cargo check -p screenpipe-redact --features mlx-mac` fails in `mlx-sys`'s build script ("cannot execute tool 'metal' due to missing Metal Toolchain") — meaning a syntax error in `imp` would first surface in a release build. The cfg gates themselves are correct (mutually exclusive on/off paths, `Unavailable` stub fallback, engine only attempts MLX under `SCREENPIPE_ENABLE_EXPERIMENTAL_RFDETR_MLX` with clean fall-through to ONNX at `screenpipe-engine.rs:2352-2407`). Suggestion: a macOS-aarch64 CI (or pre-release) job running `cargo check -p screenpipe-redact --features mlx-mac` so the guarded build is at least compile-verified somewhere automated.

**[P3] `crates/screenpipe-redact/src/adapters/rfdetr_mlx.rs:162-166` — the 108 MB weights download has no timeout and runs inline in engine startup.** `reqwest::Client::new().get(...)` has no request timeout; `ensure_model_present().await` is awaited inline in the engine's image-PII setup (`screenpipe-engine.rs:2363`), which sits before the supervision `tokio::select!` — a wedged TLS connection to HuggingFace (connects, then stalls) would leave the engine's main task hung before it starts processing stop requests or database-failure notifications. Recording itself has already started at that point, so this is a resilience nit rather than a capture-path risk — and it faithfully mirrors the existing ONNX adapter (`rfdetr.rs:241`), so fixing both together would be the clean move.
