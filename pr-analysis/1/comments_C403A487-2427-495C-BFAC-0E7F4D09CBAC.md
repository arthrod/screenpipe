# Review comments — workflows-ui guide slice (reviewer-wui-guide)

Note on anchoring: none of the four files in my slice (`guide.ts`, `guide-video-panel.tsx`, `workflow-guide.tsx`, `workflow-guide.module.css`) are changed by this PR (their blobs are identical at merge-base `35ed62162` and head `0b6c5f9d1`), so these are review-level comments with textual `path:line` anchors. The bugs are introduced by this PR through data flow from the changed `stageScreenshots()` in `packages/workflows-ui/src/screenshots.ts:8-20` into unchanged guide code; the fixes belong in this PR.

---

**[P1] `packages/workflows-ui/src/guide.ts:68-71` — embedded screenshots (negative `frameId`) cannot be saved into a guide: every save then fails with a misleading error.**

This PR admits embedded fixture screenshots with negative frameIds into `stageScreenshots()` (`screenshots.ts:8-20`), so they now flow out of `guideScreenshot`/`guideSourceImages` (`guide.ts:147-162`; the default finder at `guide.ts:161` auto-selects them because the demo evidence marks them `visualVerified: true`, produced by `demo-task/detected-task.ts:136-168`). But `parseGuide` still requires `s.imageReview.frameId >= 0` (`guide.ts:69-70`). Picking such a screenshot in the SOP editor ("Use screenshot", `workflow-guide.tsx:574-591`, reachable on demo stages which have 3 sources) — or reconnecting sources through `reconnectGuideSources` (`guide-video.ts:88-92`, wired at `guide-video-panel.tsx:150`) — writes `imageReview: {frameId: -1, …}` into the draft. Desktop persistence validates with `parseGuide` before every write (`apps/screenpipe-app-tauri/lib/workflows/disk-storage.ts:161-166`), so that save throws "The guide draft was incomplete…" and every later edit shows "Could not save. Retry before leaving." Nothing is corrupted (the throw is pre-write, so existing saved guides stay valid), but recovery is poor: "Remove screenshot" (`workflow-guide.tsx:550-562`) sets `includeImage:false/imageExcluded:true` **without clearing `imageReview`**, so the draft remains unsavable until the user picks a positive-frameId screenshot or deletes the step. Suggested fix: extend the `imageReview` rule to accept a negative frameId when it pairs with an embedded data URL (mirroring `isEmbeddedScreenshot`), or strip `imageReview` at save time when `frameId < 0`. This is the schema-compatibility gap for the PR's own demo data: existing saved guides are unaffected (schema v1 and `parseGuide` are unchanged), but new references to embedded screenshots cannot round-trip.

**[P2] `packages/workflows-ui/src/workflow-guide.tsx:539-549` — the SOP editor shows "This screenshot is no longer available." for embedded screenshots instead of their pixels.**

With the PR's `stageScreenshots` change, a demo SOP step auto-displays the embedded capture (`guide.ts:159-161` default pick; no user action needed). The editor renders it via `SopScreenshot source={image} loadSource={…}` → `ExactSopScreenshot` (`sop-screenshot.tsx:57-63`) → `useSourceScreenshot`, which always calls the platform loader with the negative frameId (`use-source-screenshot.ts:49-53`, no data-URL short-circuit) → the desktop host returns `null` for `frameId <= 0` (`apps/screenpipe-app-tauri/lib/workflows/source-screenshot.ts:15`, guard predates this PR) → the user sees "This screenshot is no longer available." even though `source.dataUrl` holds the pixels this PR explicitly preserves ("persistence keeps these pixels", `screenshots.ts:5-7`). The PR already solves this exact problem for task evidence — `workflow-step-evidence.tsx:114`: `load = resolved || isEmbeddedScreenshot(capture) ? undefined : platform.loadWorkflowScreenshot` — but applied no equivalent in the guide paths. Please render `source.dataUrl` (skip the loader) when `isEmbeddedScreenshot(image)`.

**[P2] `packages/workflows-ui/src/guide-video-panel.tsx:167-171` — every embedded scene screenshot fires a loader call that cannot succeed and shows a spurious error message.**

Scenes built from the SOP now carry both a valid embedded data URL and a negative `imageFrameId` (truthy, so it is spread in at `guide-video.ts:26` and `:35`) — a combination that did not exist before this PR, because `stageScreenshots` used to filter `frameId > 0`. The ternary here passes `load={loadScreenshot}` whenever `imageFrameId` is truthy, so `LegacySopScreenshot` calls `load(-1)` when visible (`sop-screenshot.tsx:21-35`); the desktop implementation throws "Invalid screenshot reference." for `frameId <= 0` (`apps/screenpipe-app-tauri/lib/workflows/original-screenshot.ts:2-3`), setting `failed` and rendering "Original screenshot unavailable. Showing the saved preview." under each embedded scene image, plus a wasted host call per visible scene. The image itself still renders via the `original || src` fallback, so this is noise rather than breakage — but it is guaranteed noise on the PR's demo path. Suggested fix: gate the `load` prop on `!isEmbeddedScreenshot(...)` (the scene already carries the data URL), matching what `workflow-step-evidence.tsx:114` does.
