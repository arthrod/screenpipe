# Slice review: Flows tab in pipe store — navigation/data-fetch + its test file

PR #1 (arthrod/screenpipe), diff base `origin/main`, checkout is PR head.
Slice: `apps/screenpipe-app-tauri/components/pipe-store.tsx` and `apps/screenpipe-app-tauri/components/__tests__/pipe-store-flows-tab.test.tsx` (+56/-5 and +151 new lines respectively, per `git diff origin/main...HEAD --stat`).

## What the slice changes

**`pipe-store.tsx`** — the Automations ("pipe store") view gains a third tab, `flows`:

- `PipesTab` union extended to `"discover" | "my-pipes" | "flows"` (pipe-store.tsx:338); tab bar gets a "Flows" entry (pipe-store.tsx:424).
- New `showFlows(flow)` (pipe-store.tsx:362-374): sets tab + `flowId`, bumps a `flowVisit` counter, and writes `?tab=flows&flow=<id>` into the URL with `history.replaceState`. The comment at pipe-store.tsx:365-367 states the intent: **every navigation is an explicit fresh load**, even to the Flow already on screen (the chat's "Review Screen" link after a change), so that "Activer" publishes the version shown.
- `FlowsTab` is mounted with `key={flowVisit}` (pipe-store.tsx:465), so every `showFlows` call remounts the whole tab — the remount is the freshness mechanism.
- `selectTab` (pipe-store.tsx:376-387) routes "flows" through `showFlows(null)` and strips `tab`/`flow` from the URL when leaving the Flows tab (only if the URL currently says `tab=flows`).
- The `switch-pipes-tab` listener (pipe-store.tsx:390-394) now carries an optional `flow` in the event detail; verified the only "flows" emitter is `lib/workflows/automation-flows.ts:183` which sends `{ tab: "flows", flow: flowId ?? undefined }` — contract matches.
- Mount effect (pipe-store.tsx:398-411) restores `?tab=flows&flow=<id>` on load and, unlike discover/my-pipes, keeps the Flows params in the URL (deep-linkable Review Screen). Tab subtitle copy added for flows (pipe-store.tsx:432-433).

**`pipe-store-flows-tab.test.tsx`** (new) — 5 integration tests rendering the real `PipeStoreView` with `@/lib/api`'s `localFetch` mocked: list + URL round-trip through tab clicks (66-80); re-open of the same Flow via the `switch-pipes-tab` event reloads it afresh and shows no "a changé depuis…" notice (82-103); the creation deep-link shows "Loading the Flow…" and reads the Flow exactly once (105-127); deep-link `?tab=flows&flow=<id>` opens the Review Screen (129-136); no demo control is visible (138-150).

## How it fits the PR

This is the entry point that makes Automation Flows addressable inside the app: the chat skill's "Review Screen" links, notification deep links, and the demo path all land here (`lib/workflows/automation-flows.ts:183` dispatches `switch-pipes-tab`; the mount effect reads the URL). The `flowVisit` remount is what makes "Activer publishes what's on screen" work — test 2 pins exactly that.

## Stale-cache focus — verified sound

- Flows data never touches `apiCache`: `flowsApi.list()` is a direct `localFetch("/automation-flows")` (api.ts:278); the `@/lib/cache` mock in the test exists only for `pipe-store.tsx`'s other imports.
- Every entry into the tab (tab click, event, deep link, row click, back) bumps `flowVisit` → full remount → `useFlowsLoad` foreground read (common.tsx:78-84). While parked, background refresh covers focus/visibility plus a 15 s interval (common.tsx:86-98,113), and stale answers are dropped via the `latest` ref (common.tsx:48,57-60).
- Cost: every row click / back click refetches the list **and** `/automation-flows/health` (flows-tab.tsx:37 mounts the banner; health-banner.tsx:18-21). Deliberate per the comment at pipe-store.tsx:365-367; data is local and small. No finding.
- Listener staleness: `useEventListener` keeps the handler in a ref (lib/hooks/use-event-listener.ts:58-59), and `showFlows`/`selectTab` are stable `useCallback`s — no stale closure.

## Security / error handling

- `flow` URL param flows into `flowsApi.get(id)` which `encodeURIComponent`s it (api.ts:281) against a local engine route; URL writes go through `URLSearchParams` (encoded). No injection path found.
- Error handling lives below the tab: `useFlowsLoad` error state → `FlowsErrorMessage` (common.tsx:234-300), and the banner swallows its own failures (health-banner.tsx:19-21). `pipe-store.tsx`'s own `/pipes` fetch has a `.catch` (pipe-store.tsx:346-353). No unhandled-rejection path found.

## Findings (details in comments file)

1. **P2 — the test file's declared focus is unmet**: no test covers the error or permission-denied states of the Flows tab through `PipeStoreView`. The list-level states exist only at component level with a fake api (`automation-flows/__tests__/flows-tab.test.tsx:170-193,237-247`); the wire-error→UI chain (`api.ts:257-275` mapping → `FlowsErrorMessage`) is unit-tested only in `api.test.ts:166-168`. The review-screen `not_found` state ("This Flow no longer exists in n8n", common.tsx:280-281, rendered at flow-review.tsx:60-62) is tested **nowhere** — `grep -rn "no longer exists\|not_found"` over both flows-tab test files returns nothing.
2. **P3 — clicking the already-active "Flows" tab remounts the tab and, when a Review Screen is open, silently drops the user back to the list and deletes `flow=` from the URL** (pipe-store.tsx:378 → 362-374 → 465). Clicking active "Discover"/"My tasks" is a true no-op. Inconsistent and lossy.
3. **P3 — every test in the new file silently violates its own strict mock**: `FlowsTab` always fetches `/automation-flows/health` (flows-tab.tsx:37), which the "unexpected request" mock (test lines 52-57, and narrower overrides at 87-90, 109-117) never handles; the rejection is swallowed by the banner's error state. Works, but the mock contract is quietly broken in all 5 tests.
