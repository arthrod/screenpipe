# Review: `crates/screenpipe-engine/src/routes/cloud_proxy.rs` (+277/−3)

Slice focus: **destination validation — no SSRF via user-supplied URLs.**

## What this slice changes

Four things in `cloud_proxy.rs`, on top of the pre-existing local proxy that forwards
`localhost:3030/v1/chat/completions` to `api.screenpipe.com` with the user's cloud JWT:

1. **ChatGPT routing hook** (`cloud_proxy.rs:34-36`): before proxying to the cloud, the
   handler parses the request body for `model` and, if it starts with `chatgpt/`, hands the
   request to the new `chatgpt_proxy` module instead. This couples the two files; the
   ChatGPT side is a separate slice (`chatgpt_proxy.rs`, 934 lines — I read only the parts
   this file calls: `requested_model` at `chatgpt_proxy.rs:66-72`, `chat_completions` at
   `:76-98`, `chat_completions_with` at `:131-171`).
2. **Test-parameterized base URL** (`cloud_proxy.rs:43-47`): the proxy core moves into
   private `chat_completions_with_base(token, body, base_url)` so wiremock tests can point
   it at a fake upstream (`cloud_proxy.rs:185-190`). Production passes only the compile-time
   constant `CLOUD_BASE_URL` (`cloud_proxy.rs:28`, `:38`).
3. **Buffered response path + tool-call normalization** (`cloud_proxy.rs:83-102`,
   `:123-160`): successful (`status.is_success()`), non-streaming (`Content-Type:
   application/json`, `is_json` at `:109-115`) upstream answers are now fully buffered and
   run through `normalize_tool_calls`, which gives Anthropic-style `tool_use` calls an
   OpenAI-shaped `id` (`call_<uuid>`) + `type: "function"` and fills a missing
   `finish_reason` with `"tool_calls"`. Everything else (errors, SSE streams, non-JSON)
   streams through byte-for-byte as before. Motivation is documented in the doc comment
   (`cloud_proxy.rs:117-122`): n8n's AI Agent round-trips tool results with the id it got,
   and the upstream rejects `tool_call_id: ""`.
4. **Six wiremock integration tests** (`cloud_proxy.rs:162-341`) covering id/type/finish_reason
   normalization, preservation of existing ids, and byte-for-byte passthrough for plain
   JSON, errors, and SSE.

Fits the PR's Automation Flows theme: n8n AI Agent nodes drive this proxy, so its answers
must be OpenAI-shaped.

## Slice-focus verdict: SSRF — pass (no user-supplied URL becomes a destination)

- The cloud destination is the constant `https://api.screenpipe.com` (`cloud_proxy.rs:28`);
  `base_url` is a private-function parameter fed only that constant or a test URI.
- The user-supplied `model` string only selects between two constant destinations. It is
  prefix-matched against `"chatgpt/"` (`chatgpt_proxy.rs:31, 48`), never interpolated into a
  URL; the ChatGPT destination is the constant `CODEX_URL`
  (`chatgpt_proxy.rs:32`, used at `:97` → `:135` → `:153`). Malformed bodies return `None`
  and fall through to the cloud path (`chatgpt_proxy.rs:71`).
- Redirects: `reqwest::Client::new()` follows up to 10 redirects by default, so the
  destination can change post-authorization. I verified in the vendored source that reqwest
  0.12.28 strips `Authorization`/`Cookie`/`Proxy-Authorization` on cross-host redirects
  (`redirect.rs:239-253`, applied at `redirect.rs:338`), so a malicious redirect cannot
  forward the cloud JWT to a third party. Residual risk is credential-free, first-party-only.
- Route exposure context (pre-existing): mounted at `server.rs:1272-1274` with a 50MB request
  body limit; when `api_auth` is on, non-localhost requests require the local API key
  (`server.rs:1612-1618`).

## Risks / quality issues found (details in comments)

- **P2 — unbounded response buffering** (`cloud_proxy.rs:86-96`): the new path buffers the
  entire successful-JSON upstream body in memory with no size cap. The request side is
  capped at 50MB (`server.rs:1273`), the response side is not. Old code streamed.
- **P2 — no timeouts, per-request client** (`cloud_proxy.rs:57`): pre-existing on main for
  the send, but the new buffered read (`:86`) adds a second unbounded wait (slow-body
  trickle hangs the handler forever). Same class of issue as the existing PR comment on
  `chatgpt_proxy.rs:152` — my comment scopes the fix to this file and references that one.
- **P3 — hand-built JSON error bodies** (`cloud_proxy.rs:71`, `:92`): a reqwest error's
  `Display` text is interpolated raw into a `format!`-built JSON string; quotes in the error
  text produce an unparseable body. `:92` is new code copying the pre-existing `:71` pattern.
- **P3 — silent fallback on serialization failure** (`cloud_proxy.rs:156-159`): if
  `serde_json::to_vec` ever failed, the original un-normalized (broken) body would be
  returned with no log — the exact failure the function exists to prevent. Practically
  infallible for a parsed `Value`, but deserves a `warn!`.
- **P3 — uncovered branch**: upstream 200 + `application/json` with an invalid JSON body
  passes through byte-for-byte (`normalize_tool_calls` bails at `cloud_proxy.rs:124`), a
  deliberate and good fallback, but no test covers it.
- Summary-only note: `requested_model(&body)` fully parses every request body — up to the
  50MB limit — on each call just to read one field (`chatgpt_proxy.rs:71`). O(n) scan with
  little allocation, dwarfed by the upstream round-trip; acceptable, but it is on the agent
  media-analysis hot path.
