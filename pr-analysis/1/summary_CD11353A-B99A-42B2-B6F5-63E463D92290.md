# Slice review: `crates/screenpipe-engine/src/n8n_nodes.rs` (337 new lines)

Focus: **verify no invented nodes — catalog must only contain real node types.**

## What this slice changes

New module `crates/screenpipe-engine/src/n8n_nodes.rs`: the "browsing layer" of the n8n
node catalog that the chat searches before building a Flow. Two entry points
(`search`, `card`, plus `add_credential_state`) are served over HTTP by
`automation_flows.rs:1341-1378` (`GET /nodes?q=` and `GET /nodes/card?type=&resource=&operation=`).
The node list is not hand-written: the module embeds
`infra/automation-flows/n8n-nodes.json.gz` via `include_bytes!`
(n8n_nodes.rs:26), generated by `infra/automation-flows/n8n-catalog.ts`.

## Focus verdict: PASS — no invented nodes found

Every claim below was verified by running the command or reading the file named.

1. **Provenance is a real n8n image, not human-authored text.** The generator
   `n8n-catalog.ts` reads the running container's own node manifests
   (`docker exec … find … dist/types/nodes.json`, n8n-catalog.ts:242-247), n8n's own
   `NODES_EXCLUDE`/default-exclude config (n8n-catalog.ts:249-254), and the repo's
   real ScreenPipe node packages (n8n-catalog.ts:227-237). No node type is ever
   typed by hand.
2. **Catalog contents.** Decompressed the embedded gz
   (`gunzip -c infra/automation-flows/n8n-nodes.json.gz`): n8n **2.42.2**, **843** index
   entries = 707 `n8n-nodes-base.*` + 132 `@n8n/n8n-nodes-langchain.*` + 4 `CUSTOM.*`.
   Only 3 entries flagged `off`: `executeCommand`, `executeCommandTool`,
   `localFileTrigger` — matching the doc comment at n8n_nodes.rs:12-13, and these are
   real n8n built-ins (`executeCommand`'s description in the data: "Executes a command
   on the host").
3. **The 4 CUSTOM types are real repo code.** 3 directories exist in
   `packages/n8n-nodes-screenpipe/nodes/` (ScreenPipe, ScreenPipeAiTrigger,
   ScreenPipeTrigger); the 4th, `CUSTOM.screenPipeTool`, is the `usableAsTool` twin the
   generator derives from `ScreenPipe.node.ts:28` (`name: "screenPipe"`) and `:37`
   (`usableAsTool: true`) via n8n-catalog.ts:234. No twin for the two triggers, which
   don't declare `usableAsTool` — consistent.
4. **Spot-check for realness/typosquats.** 12/12 well-known types present
   (httpRequest, webhook, gmail, gmailTrigger, jira, slack, code, if, set, langchain
   `agent`, `lmChatOpenAi`, plus executeCommand); a grep for typo variants
   (`httprequests?`, `webhooks?`, `gmaill`, `jiraa`, …) matched only the exact real names.
5. **Browsing layer ⇄ check layer agree exactly.** Extracted both type sets:
   browsing index (843) == check-layer `nodes` keys (840) ∪ `excluded` (3), with
   **zero** difference in either direction
   (`comm` on `jq -r '.index[].type'` vs `jq -r '.nodes | keys[]'` + `.excluded[]`
   from `infra/automation-flows/n8n-catalog.json`). This verifies the doc claim
   "what the chat finds is what the check accepts" (n8n_nodes.rs:11-12) on the data.
6. **Card-count reconciliation is exact.** `details` has 570 keys and exactly 570
   one-line cards (awk line-start key count = 570) — the invariant `detail()`'s
   string scan relies on (n8n_nodes.rs:131-137). 843 = 570 base cards + 271 `toolOf`
   twins + 3 off (executeCommandTool is both off and a twin). The only `toolOf`
   target without a card is `executeCommand` (off) — unreachable because `card()`
   early-returns for off entries before reading details (n8n_nodes.rs:179-181).
7. **Ran the module's test:** `cargo test -p screenpipe-engine --lib n8n_nodes` →
   `every_usable_type_has_a_card_and_a_skeleton_the_check_knows ... ok` (1 passed,
   1795 filtered). This asserts every non-off type has a card findable by `detail()`
   and is known to the check layer's `skeleton_parameters`.
8. **Not run:** a comparison against the live n8n container's manifest — the
   `automation-flows-n8n-1` container is not running in this environment
   (`docker ps` returned no containers). Provenance rests on the generator code plus
   the internal cross-checks above, not a fresh live diff.

Defense in depth even if the embedded data were tampered with: `flow_checks.rs:190-202`
(`inspect_node`) rejects any workflow node type not in the check layer's 840 types
("never invent one"), and off types are absent from that map — so a fabricated entry in
the browsing layer could at worst mislead the chat, and would be refused at Flow save.

## Code quality of the module itself

Overall high: precise doc comments, no allocation in any hot path (this is a chat/HTTP
handler, not recording), errors are descriptive strings surfaced as HTTP 400 by the
router (`automation_flows.rs:1345`, `:1375`), and the `chosen` map is constrained by the
router to `resource`/`operation` only (`automation_flows.rs:1366-1370`), so
`narrow()`'s unknown-key error cannot misfire. The per-call ~5 MiB decompression in
`unpacked()` (n8n_nodes.rs:114-120) is an explicitly documented trade-off
(n8n_nodes.rs:15-17), acceptable at the stated call rate. Version matching uses f64 but
both layers parse the same decimal text and `skeleton_parameters` compares with a 1e-9
tolerance (flow_checks.rs:270).

Two P3 findings posted (see comments file):

- `narrow()`'s offered-value check unions options across all resource groups, so a
  choice valid only under another resource passes (verified against the real gmail
  card: 4 `operation` groups for draft/label/message/thread).
- No unit tests for `narrow()`, `search()` ranking, or `add_credential_state()` — the
  file's only test is catalog consistency.

## PR context

This module is the discovery half of the Flow-building loop introduced by the PR
(chat searches real nodes here → builds a workflow → check layer `flow_checks.rs`
refuses anything not in the same n8n image). The two layers are generated together by
one script from one container read, which is what makes the "no invented nodes" goal
structural rather than aspirational.
