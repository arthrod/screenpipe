# Slice review: `api.test.ts` — failure-path coverage of `api.ts`

**Focus question:** Do the tests cover api.ts failure paths (network, 4xx/5xx, malformed JSON), not just happy paths?

**Answer: 4xx/5xx with well-formed JSON bodies — yes, well covered. Network failures — not at all. Malformed JSON — not at all.** One exported credential-routing function (`notificationApiHeaders`) has no test coverage anywhere in the repo, and the regex it is built on demonstrably disagrees with the URL shapes `flowsApi.retry` itself produces.

## What this slice is

Both files are new in this PR (411 + 477 lines, `git diff origin/main...HEAD --stat`):
`apps/screenpipe-app-tauri/components/automation-flows/__tests__/api.test.ts` and
`apps/screenpipe-app-tauri/components/automation-flows/api.ts`. `api.ts` is the
self-declared "only seam between the Automation Flows UI and the rest of the app"
(api.ts:5-8): a typed client over the engine's `/automation-flows/*` routes with a
`FlowsApiError` error taxonomy (api.ts:167-206, 247-255) plus chat/timeline/n8n
navigations. `api.test.ts` is its first unit-level test suite (35 tests) and also
exercises the browser mock (`mock.ts`) end-to-end.

## How it fits the PR

Every Flows screen consumes this seam: `useFlowsLoad` funnels every failure into a
`{ state: "error", error: FlowsApiError }` state and normalizes anything else with
`asFlowsError` (common.tsx:24-27, 73), so the typed codes are load-bearing for the
Review Screen, Flows tab, and health banner. The suite also pins the UI-credential
contract (`x-screenpipe-flow-activation`, api.ts:209) that the engine's
activation/retry authorization depends on.

## Failure paths: covered vs not

Covered well (api.test.ts):
- Typed 4xx/5xx mapping for well-formed JSON error bodies: 9-case `it.each`
  (api.test.ts:163-173) plus retry-specific 403/409/404 (128-132), delete 409
  `flow_running` (145), activate-without-credential 403 (149-160, also asserts the
  header is absent when `getFlowActivationKey` rejects), `detail` preservation
  (180-183). 10 of the 12 `SERVER_CODES` (api.ts:193-206) are exercised.
- Browser-mock negative paths: `not_found`, `run_not_failed`, `version_changed`,
  `n8n_not_configured`, `n8n_unreachable` (api.test.ts:246-361).

Not covered — these are the posted findings:
1. **Network failure** (fetch rejects): wrapped as `FlowsApiError("unknown")` at
   api.ts:259-263 — no test ever rejects `localFetch`; the only rejection stubbed is
   `getFlowActivationKey` (api.test.ts:149-152), which exercises `activationKey()`'s
   catch (api.ts:219-226), a different path.
2. **200 + malformed JSON silently resolves `null as T`** (api.ts:264-265): the
   `json().catch(() => null)` result is returned as-is on `response.ok`. No test
   feeds a non-JSON 2xx body.
3. **`notificationApiHeaders` untested repo-wide**, and its `RETRY_PATH` regex
   (api.ts:235) rejects the percent-encoded URLs `flowsApi.retry` builds
   (api.ts:293-297) whenever an id needs encoding — verified with the node probe
   above; the fixture ids in this very file ("wf/1", "e/4") are such ids. Whether
   engine-notification URLs hit this depends on n8n id format, which I could not
   verify from this slice (failures.rs:268 shows no encoding; n8n execution-id
   alphabet not checked).
4. **Non-JSON/empty error bodies** fall back to `not_found`/`unknown` with detail
   `HTTP ${status}` (api.ts:267-274) — the parse-failure branch and that detail
   string are never taken/asserted.
5. **`flow_active` and `retry_still_running`** are the two uncovered `SERVER_CODES`;
   trivial `it.each` additions. Relatedly, `dismiss`/`restore` transport shape
   (they send `clickHeaders()` + body `"{}"`, api.ts:353-368) is unasserted here —
   UI-level coverage exists in flows-tab.test.tsx:47-48, 217-227 but with a fully
   mocked `api`.

## Quality notes (not posted)

- Good: the suite pins the wire format with a local `ACTIVATION_HEADER` literal
  (api.test.ts:39) rather than importing the constant — deliberate drift detection.
- Good: URL-encoding of ids is asserted (`wf%2F1`, `e%2F4` in paths).
- No security issues in the test file itself ("ui-key" is a fixture; no real secrets).
- `withCreationPrompt` is fully tested (api.test.ts:395-411); `dismiss`/`restore`
  and `repetitions()` happy paths are the untested exported surface, minor.

## What I did not check

- The full frontend suite and CI — not in scope for this slice; single-file run only.
- n8n's execution-id alphabet (relevant to finding 3's real-world reach).
- Whether any production caller relies on the `null as T` behavior of finding 2 —
  `flowsApi.list()` call sites I found are all in tests; production loading goes
  through `useFlowsLoad` callbacks whose `load` implementations I did not enumerate.
