## Test coverage of `api.ts` failure paths (network, 4xx/5xx, malformed JSON)

Answering the question this suite should settle: **4xx/5xx with well-formed JSON bodies are well covered; network failures and malformed JSON are not covered at all.** Everything below was verified by reading `api.ts` in full and running the suite (`bun x vitest run --config vitest.config.ts components/automation-flows/__tests__/api.test.ts` → 35/35 passed).

---

**[P2] `__tests__/api.test.ts:149` — the network-failure path of `request()` is never tested.**
`request()` wraps a `localFetch` rejection as `FlowsApiError("unknown", String(error))` (`api.ts:259-263`), and that is the most common real-world failure: the engine is a local sidecar, and engine-down is exactly what `useFlowsLoad`'s error state and the health banner exist for (`common.tsx:24-27,73`). No test in this file rejects `localFetch` — the only rejection stubbed is `getFlowActivationKey` (line 149-152), which exercises `activationKey()`'s own catch (`api.ts:219-226`), a different path. Add one case: `localFetch.mockRejectedValue(new TypeError("Failed to fetch"))` → `FlowsApiError` with code `"unknown"`. Today, if someone deletes that try/catch, all 35 tests stay green.

**[P2] `api.ts:264-265` — a 2xx with a malformed JSON body silently resolves `null as T`, and no test pins it.**
`const body = await response.json().catch(() => null); if (response.ok) return body as T;` means a truncated or non-JSON 200 (crashed handler, interrupted stream) makes `flowsApi.list()` resolve `null`; the failure then surfaces as a `TypeError` in whatever renders the list — far from this seam and outside `useFlowsLoad`'s typed error state. Either tighten `request()` to throw `FlowsApiError("unknown", ...)` when `response.ok` but the body failed to parse (keeping in mind `delete()` ignores the body), or at minimum add a test that pins the current behavior so it is a decision rather than an accident. Same gap, error branch: a non-JSON/empty body on a 4xx/5xx (proxy HTML page, empty 500) takes the `.catch(() => null)` path and falls back to `not_found`/`unknown` with detail `HTTP ${status}` (`api.ts:267-274`) — that fallback detail string is asserted nowhere.

**[P2] `api.ts:243-245` — `notificationApiHeaders` has zero test coverage in the repo, and its regex rejects the URLs `flowsApi.retry` itself builds.**
`rg -ln "notificationApiHeaders" apps/screenpipe-app-tauri --glob '*test*'` returns nothing, yet this function decides which requests carry the UI activation credential. `RETRY_PATH` (`api.ts:235`) matches only `[A-Za-z0-9_-]` segments, while `flowsApi.retry` percent-encodes its ids (`api.ts:293-297`): I verified with a node probe that `/automation-flows/wf%2F1/runs/e%2F4/retry` does **not** match — and `"wf/1"`/`"e/4"` are the fixture ids this very test file uses. For such ids the credential is silently dropped and the user's « Retry » click is refused with `retry_requires_user`. Whether engine notification URLs hit this depends on n8n's id alphabet (I could not verify that from this slice; `failures.rs:268` interpolates ids raw), which is exactly why a unit test belongs here: assert the credential for the plain shape and for the encoded shape `flowsApi.retry` produces. This complements the existing review comment on `notification-actions.test.ts` (which flags the provenance gating); this one asks for coverage of the function itself.

**[P3] `__tests__/api.test.ts:163-173` — `flow_active` and `retry_still_running` are the two `SERVER_CODES` the typed-error table never exercises.**
`SERVER_CODES` has 12 entries (`api.ts:193-206`); 10 are covered across the `it.each` table, the retry test (lines 128-132) and the outside-the-desktop-app test (lines 149-160). `flow_active` (dismiss of an active Flow) and `retry_still_running` are only reachable codes with real UI handling, and they are one-line additions to the existing table. Relatedly, `dismiss`/`restore` transport shape is unasserted in this file while `activate`/`deactivate`/`retry`/`delete` all get shape assertions: both send `clickHeaders()` + body `"{}"` (`api.ts:353-368`), i.e. they do carry the UI credential, and nothing pins that. (`flows-tab.test.tsx:47-48,217-227` covers their UI behavior with a fully mocked `api`, so this is a transport-only gap.)
