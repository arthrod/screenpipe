## Review — Flows tab in pipe store (navigation/data-fetch) and its test file

Scope: `apps/screenpipe-app-tauri/components/pipe-store.tsx` and `apps/screenpipe-app-tauri/components/__tests__/pipe-store-flows-tab.test.tsx`. Verified: `useFlowsLoad` foreground-reads on mount and refreshes every 15 s (common.tsx:78-98,113), flows data never touches `apiCache` (api.ts:278), and every navigation remounts the tab via `key={flowVisit}` (pipe-store.tsx:362-374,465) — the no-stale-cache goal is met structurally. All 5 tests in the new file pass (`bun x vitest run --config vitest.config.ts components/__tests__/pipe-store-flows-tab.test.tsx`). Three findings, none duplicated from existing PR feedback:

---

**[P2] `apps/screenpipe-app-tauri/components/__tests__/pipe-store-flows-tab.test.tsx:50` — the file covers no error and no permission-denied state of the Flows tab, which is its declared purpose.**

All 5 tests are happy-path (plus one loading state). Missing, each easy to add against the existing `localFetch` mock: (1) `GET /automation-flows` answering `412 {"error":"n8n_not_configured"}` should render the "n8n is not set up" alert with "Open Connections" (common.tsx:243-256), and `n8n_unauthorized` the "n8n refused the API key" one with "Try again" (common.tsx:257-276); (2) a plain failure (500/network throw) should render "The Flows could not be loaded" with "Try again" (common.tsx:277-299); (3) the deep link `?tab=flows&flow=<id>` whose Flow read 404s should render "This Flow no longer exists in n8n" (common.tsx:280-281, flow-review.tsx:60-62) and its back button must still return to the list. These states are covered only at component level with a fake api (`automation-flows/__tests__/flows-tab.test.tsx:170-193,237-247`), so the integration chain this file uniquely exercises — engine error body → `FlowsApiError` mapping (api.ts:257-275) → `FlowsErrorMessage` inside the app's real tab — is untested; the `not_found` review-screen state is tested in no file at all. `grep -rn "no longer exists\|not_found"` over both flows-tab test files returns nothing.

---

**[P3] `apps/screenpipe-app-tauri/components/pipe-store.tsx:378` — clicking the already-active "Flows" tab remounts the tab and, when a Flow's Review Screen is open, silently returns to the list.**

`selectTab("flows")` unconditionally calls `showFlows(null)`, which bumps `flowVisit` (pipe-store.tsx:368) and therefore remounts `FlowsTab` via its `key` (pipe-store.tsx:465) with `flowId` reset to null — and `params.delete("flow")` at :372 erases `flow=` from the URL. For the other two tabs, clicking the active tab is a true no-op (no remount, no URL change), so the Flows tab is inconsistent: a user clicking the active tab to refocus (or double-clicking) loses their place in the Review Screen and their deep link. Consider guarding `selectTab` with `if (tab === activeTab) return;` (keeping `showFlows` for genuine navigation from events/rows), or remounting only when the target actually differs.

---

**[P3] `apps/screenpipe-app-tauri/components/__tests__/pipe-store-flows-tab.test.tsx:52-57` — every test silently violates the mock's own "unexpected request" contract because of the health banner.**

`FlowsTab` always renders `FlowsHealthBanner`, which fetches `/automation-flows/health` on mount (flows-tab.tsx:37, health-banner.tsx:18-21). The strict mock (beforeEach at :52-57, and the narrower overrides at :87-90 and :109-117) never handles that URL, so all 5 tests run with a deliberately-thrown "unexpected request: /automation-flows/health" rejection that is swallowed by the banner's error state (health-banner.tsx:19-21). It passes today, but the suite's loud-failure contract is broken on every test: if the banner ever starts rendering errors, or someone adds a "no unexpected requests" assertion, the failure will be confusing. Handle the health route in `beforeEach` (e.g. `jsonResponse({ checkedAt: null, n8n: "reachable", notified: [], pendingNotifications: [], deletedDrafts: [] })`) so requests stay explicit.
