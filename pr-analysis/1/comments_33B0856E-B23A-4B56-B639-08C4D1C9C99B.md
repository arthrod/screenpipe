## Review — ScreenPipe AI Trigger node + ScreenPipe API credential

Slice: `packages/n8n-nodes-screenpipe/nodes/ScreenPipeAiTrigger/ScreenPipeAiTrigger.node.ts` and
`packages/n8n-nodes-screenpipe/credentials/ScreenPipeApi.credentials.ts` (both new). Ran `bun run typecheck` (clean)
and `bun test` in `packages/n8n-nodes-screenpipe` (56 pass / 0 fail). The abstain UX in manual mode ("Condition not
met" / "The AI check failed" with the AI's reason) and the prompt-injection fence around `<activity>` are well done and
well tested; the credential file correctly marks `apiKey` as password-type and leaves `baseUrl` plain. Three findings:

---

**[P2] `packages/n8n-nodes-screenpipe/nodes/ScreenPipeAiTrigger/ScreenPipeAiTrigger.node.ts:112-118` — a persistent AI failure leaves the active trigger silently dead; only a server-side log line records it.**

In automatic mode every AI-side failure (proxy unreachable, ChatGPT signed out → HTTP 503, rotated API key → HTTP 403, typo'd model name) is swallowed here: `logger.warn` + `return null`. That is the right *firing* policy — the trigger must never fire on a guess, and abstention must not start a cooldown — but it conflates "don't fire" with "don't tell anyone": n8n records nothing, no error workflow runs, and the UI shows a healthy-looking trigger that never fires again. The inconsistency is visible in the same `poll()`: a ScreenPipe-side failure throws `NodeApiError` (lines 163, 172) and surfaces as a failed execution, while a broken ChatGPT connection — just as persistent — does not. Since these failures are typically persistent (sign-out, key rotation), the user finds out only when the automation silently didn't happen. Suggestion: track a consecutive-failure count in the node's static data (the cooldown already lives there) and rethrow the error once it crosses a small threshold (e.g. 5 polls ≈ 5 minutes at the default schedule), resetting on any success — transient blips stay quiet, sustained breakage shows up as a failed execution like every other node. (Complementary to the separate timeout comment already raised on `askAi` at lines 198-206: that bounds a stalled call, this is about the catch path being invisible.)

**[P3] `packages/n8n-nodes-screenpipe/nodes/ScreenPipeAiTrigger/ScreenPipeAiTrigger.node.ts:238` — an abstain reason is silently dropped when the model returns a non-string `reason`, so the user sees "Condition not met" with an empty description.**

`parseDecision` accepts a missing/non-string `reason` and substitutes `""` (`reason: typeof reason === "string" ? reason : ""`). In manual mode that empty string becomes the `NodeOperationError` description at line 120 — the "Fetch Test Event" UX promises the AI's reason and the user gets nothing — and a fired item can carry `reason: ""` for downstream nodes. The model's full answer is already in hand and the file already has a clip helper used for exactly this kind of surfacing (lines 234, 237). Falling back to `clip(content)` (e.g. `reason || clip(content)`) keeps the abstain reason informative in both paths.

**[P3] `packages/n8n-nodes-screenpipe/nodes/ScreenPipeAiTrigger/ScreenPipeAiTrigger.node.ts:88-91` — editing the condition keeps the old `lastFiredAt`, so a freshly edited trigger can stay silent for up to the whole cooldown with no signal.**

`state.lastFiredAt` survives any parameter change: after the user changes the condition (or the model, or the windows), line 91 still suppresses polling until the previous firing's cooldown expires (default 60 minutes), and line 102 still floors the look-back window at the old firing time — so the *new* condition is neither asked about the full window nor asked at all for a while. It fails safe (no wrong fires), but the editor-visible behavior is "I changed my trigger and nothing happened". The sibling `ScreenPipeTrigger` solves the same problem explicitly — "A cursor belongs to what it watched: after the user edits the trigger, start over" (`ScreenPipeTrigger.node.ts:141-147`, with the sorted-parameter `signature()` at lines 154-157). Storing and comparing a parameter signature before honoring `lastFiredAt` would make edits start over the same way.
