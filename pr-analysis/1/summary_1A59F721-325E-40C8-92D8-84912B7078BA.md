## What this slice does

**`automation_flows.rs`** — a process-local activation credential. `activation_key()`
(automation_flows.rs:21-24) lazily generates a `FlowActivationKey` in a `OnceLock`;
`get_flow_activation_key` (automation_flows.rs:28-32) is a Tauri command that hands the
key to the webview. The engine refuses `POST /automation-flows/:id/activate` and
`.../retry` unless the request carries this key in `x-screenpipe-flow-activation`
(engine `crates/screenpipe-engine/src/automation_flows.rs:136-138`, check at
`:1458-1465`). Rationale: chat agent (Pi), pipes, and MCP clients share the local API
key over HTTP but cannot invoke Tauri commands, so a Flow can only be activated from
the desktop UI. This is the security spine of the whole Flows feature.

**`main.rs`** — the only change is `mod automation_flows;` (main.rs:46). A module
declaration is inert at runtime: **no startup ordering regression is possible from this
line**, verified by the diff containing nothing else for this file. Command
registration is not done here — commands are auto-collected by the external
`tauri-helper` macros (`Cargo.toml:23`), invoked at `main.rs:1229`
(`tauri_helper::tauri_collect_commands!()`) with a compile-time non-empty-registry
guard (main.rs:432-437). The specta binding `getFlowActivationKey` exists in the
generated `lib/utils/tauri.ts:755`, which proves the command is in both the invoke
handler and the TS bindings.

**`server_core.rs`** — `server.flow_activation_key = Some(activation_key())`
(server_core.rs:652) runs on the `SCServer` right after construction (server_core.rs:641)
and **before** `server.try_create_router()` (server_core.rs:1088), which is where the
engine bakes the key into the flows router (`crates/screenpipe-engine/src/server.rs:1501-1510`
passes `self.flow_activation_key.clone()` into `automation_flows::router`). Order is
correct: no window where the server serves with a `None` key on desktop. Engine
restarts keep the same key (OnceLock), matching the doc claim
(automation_flows.rs:20); the webview refetches per click
(`components/automation-flows/api.ts:219-225`), so an app restart cannot strand a stale key.

**`shortcuts.rs`** — a hidden global demo shortcut ⌃⌥⌘D (`DEMO_SHORTCUT`,
shortcuts.rs:26), registered last in `apply_shortcuts` (shortcuts.rs:529-536) after the
user's set, emitting `shortcut-automation-flows-demo` to the "home" window
(`run_demo_shortcut`, shortcuts.rs:32-54). Headless fallback: if Home is missing it
re-opens it via `run_on_main_thread` + `ShowRewindWindow::Home` (window label "home"
verified at `window/show.rs:113`) and emits after a fixed 3 s sleep (shortcuts.rs:48-53).
Adds one parse test (shortcuts.rs:643-652).

## Quality assessment

Solid overall. Verified good:

- **Key hygiene**: `FlowActivationKey` is constant-time compared (engine automation_flows.rs:176-185),
  `Debug`-redacted (:180-183), 2×UUIDv4 (~244 bits, :158-166); only callers of
  `activation_key()` are server_core.rs:652 and the command — never logged, env, or file
  (grep `flow_activation_key|FlowActivationKey` across `crates/screenpipe-engine/src`).
- **Blast-radius containment**: the agent's owned browser refuses app origins so
  third-party pages cannot reach app-only commands (`owned_browser.rs:1597-1621`, with
  tests `:1678-1706`); capabilities are `local: true` with `windows: ["*"]`
  (`src-tauri/capabilities/main.json`), so remote content gets no IPC at all.
- **Conflict & cleanup posture** (my focus): demo is registered **last** (shortcuts.rs:529)
  after `unregister_all()` (shortcuts.rs:333), so a user-configured ⌃⌥⌘D wins and the
  demo's failed registration only logs (529-536); re-apply cycles
  (`update_global_shortcuts`, suspend/resume 541-558) unregister and re-register it
  consistently, and enterprise hidden-UI modes intentionally drop it
  (shortcuts.rs:270-301, 315-328). No *default* user shortcut equals ⌃⌥⌘D — checked all
  defaults in `store.rs:2145-2178` (Super+Ctrl+{S,U,X,A,Z,L,K,B}, Alt+Shift+{...},
  Super+Shift+L, Ctrl+Shift+L).

## Risks / issues (details in comments file)

1. **P2** — headless path: fixed 3 s sleep before emit is a race; if Home's webview
   mounts slower the press is lost with no retry, and the emit fires even when the
   window failed to open (shortcuts.rs:39-53).
2. **P3** — the module doc says "only the Review Screen" holds the key, but the command
   is invocable from every local app webview (`windows: ["*"]`) — any first-party
   window's JS, not just the Flows screen, can fetch it (automation_flows.rs:26-32).
3. **P3** — Rust↔TS event-constant sync is comment-only; the TS test re-types the
   literal in its `vi.mock` (`components/automation-flows/__tests__/demo-shortcut-listener.test.tsx:43-47`)
   rather than importing the real constant, and the new Rust test never runs in CI
   (src-tauri has no CI test job).
4. **P3** — demo press is silently swallowed by the trial-activation lock
   (shortcuts.rs:208-217) — a trial-locked presenter gets no feedback.

Already posted on the PR (not duplicated): CodeRabbit's Major on
`shortcuts.rs:527-536` — the demo shortcut ships in production builds, is
non-configurable, and its handler deletes real user Flows.
