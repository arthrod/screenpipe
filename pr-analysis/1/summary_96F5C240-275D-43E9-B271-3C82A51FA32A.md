## What this slice changes and how it fits the PR

The PR adds Automation Flows (ScreenPipe automations on self-hosted n8n). This slice is the app-shell plumbing:

1. **Home page** (`apps/screenpipe-app-tauri/app/(main)/home/page.tsx:1315`): inside the existing `navigate` Tauri-event handler, calls `followFlowsNavigation(url)` before `setActiveSection(mapped)`, so a navigation to `?section=pipes&tab=flows` (failure notification, chat overlay) opens the Flow's Review Screen.
   - The helper (`lib/workflows/automation-flows.ts:172-178`) early-returns `false` unless `section=pipes&tab=flows`, rewrites the URL, and dispatches `switch-pipes-tab`; it is called on every in-`ALL_SECTIONS` navigation but the check is a cheap param compare. `"pipes"` is in `ALL_SECTIONS` (`app/(main)/home/page.tsx:163-165`), so the path is reachable.
   - Ordering is correct for both mount states of the Automations view: the `switch-pipes-tab` event covers the already-mounted-hidden case and the replaced URL covers the not-yet-mounted case (`lib/workflows/automation-flows.ts:180-183`). The lib comment at `:155-158` documents why Home's listener is the single switch point (doing it twice opened the Flow twice). The boolean return is intentionally ignored — `setActiveSection` follows unconditionally.
   - Tested: accept/reject cases in `lib/workflows/automation-flows.test.ts:209-222`.

2. **Providers** (`apps/screenpipe-app-tauri/app/providers.tsx:10,200`): mounts the new `DemoShortcutListener` with `{!isOverlay && ...}` alongside `WorkflowsRolloutSync`, inside the `mounted && startupAuthenticationStatus` bootstrap gate.
   - No hydration risk by construction: client-only component, renders `null`, sits below the gate whose purpose is to keep first render identical to the static prerender (`providers.tsx:59-72`).
   - The listener itself (`components/automation-flows/demo-shortcut-listener.tsx:20-42`) early-returns in browser-mock mode, scopes its Tauri listener to the current webview window (avoids the once-per-open-window double-fire the comment explains), cleans up on unmount, and routes handler errors to a destructive toast. Its `[toast]` dep is stable — `toast` is a module-level export, not a hook-made closure (`components/ui/use-toast.ts:176-192,196`), so the effect runs once.

3. **Markdown** (`apps/screenpipe-app-tauri/components/markdown.tsx:95-96`): adds `"flows"` to `chatUrlTransform`'s allowlist so `screenpipe://flows/<id>` links survive sanitization in chat markdown.
   - No code-block or link-rendering regression: a `urlTransform` only receives link `href`/image `src` candidates; code content never passes through it. Everything not matching `screenpipe:` + allowed host still falls to `defaultUrlTransform` (`markdown.tsx:65-86`).
   - The memo comparator at `markdown.tsx:319-325` compares `urlTransform` identity — `chatUrlTransform` is a module-level export, so memoization is unaffected.
   - A click handler exists and validates: `components/chat/markdown-block.tsx:208-225` routes `screenpipe://flows/` clicks to `openFlowReviewLink`; the id is parsed with protocol/host checks and `decodeURIComponent` inside try/catch (`lib/workflows/automation-flows.ts:102-110`) and re-encoded everywhere it is used (`:98,114,128`, `components/automation-flows/api.ts:280-281`). A hand-crafted malformed link degrades to a no-op or a 404 error state; no injection surface found.

4. **Notification handler** (`apps/screenpipe-app-tauri/components/notification-handler.tsx:258`): replaces hardcoded `Content-Type: application/json` with `await notificationApiHeaders(action.url)` for `api` actions.
   - Verified no regression for existing actions: `notificationApiHeaders` returns `JSON_HEADERS` (exactly the old `{ "Content-Type": "application/json" }`) for every URL that is not the retry route, and `clickHeaders()` (JSON + credential) only for `/automation-flows/<id>/runs/<run>/retry` (`components/automation-flows/api.ts:211,229-245`); the regex is anchored. The `isLocalApiUrl` gate at `notification-handler.tsx:252` predates and still bounds this branch. `activationKey()` failures degrade to JSON-only headers (`api.ts:219-226`).
   - Payload validation otherwise: dispatch is gated on truthy `action.url` + local-URL check; non-string/throwing payloads land in the outer try/catch with an `notification_action_error` analytics event (`notification-handler.tsx:343-353`). The credential-provenance weakness (any pipe/chat-created notification can carry a retry URL and receive the UI credential) is real but **already reported** on the PR (coderabbitai[bot] 4330471422).

5. **Standalone chat** (`apps/screenpipe-app-tauri/components/standalone-chat.tsx:337-349,2483`): new `startFlowCreation` callback fills the composer with the creation prompt plus whatever the user had typed, and is passed as `onCreateFlow` to the home summary cards.
   - Mirrors the adjacent `fillContextualHomeSuggestion` (`:325-336`) exactly, and correctly clears `pendingContextualHomeSuggestionRef` so a later send isn't misattributed to the contextual-suggestion experiment (`:320-324,350-356`). Deps `[inputRef, inputValueRef, setInput]` are all stable; the omitted `setHomeCardPromptPreview` is a stable state setter.
   - Double-prefix is prevented: `withCreationPrompt` returns the draft unchanged when it already starts with the prompt (`components/automation-flows/api.ts:466-470`), with dedicated tests (`components/automation-flows/__tests__/api.test.ts:395-409`).
   - Consumer types match: `onCreateFlow?: () => void` (`components/chat/summary-cards.tsx:66`), button renders only when the prop is passed and captures `home_card_clicked {kind: "create_flow"}` (`:405-417`); click tested in `components/chat/summary-cards.test.tsx:220-244`.

6. **Thinking level** (`apps/screenpipe-app-tauri/components/thinking-level-selector.tsx:16,18,29-30`): adds a fourth `"max"` level.
   - Invalid levels are guarded at all three entry points: the settings read (`:143`), the session report (`:154`), and the slider callback (`:215`). The Tauri binding takes a plain string (`lib/utils/tauri.ts:1948`), and the Rust command validates against `["low", "medium", "high", "max"]` before persisting or RPC-ing (`apps/screenpipe-app-tauri/src-tauri/src/pi.rs:5718-5723`), so the new level is accepted end-to-end and an out-of-protocol value can neither render nor persist.
   - User selection is preserved by the existing choice/report arbitration (optimistic `setShownLevel` at `:182`, stale-report guard at `:159`, clamp-settling covered by existing tests).
   - The slider is generic over step count — `Home`/`End` commit first/last (`components/chat/standalone/composer-effort-slider.tsx:66,194-200`) — so the fourth step needs no slider change. The only `ThinkingLevel` consumer outside tests, `components/chat/standalone/composer-controls-row.tsx:18-19,75,195`, uses the hook generically; no exhaustive three-value switch exists anywhere in the app (searched).

7. **Test sync** (`apps/screenpipe-app-tauri/components/thinking-level-selector.test.tsx:227`): the `End`-key expectation changed `"High"` → `"Max"`, exactly what the component change implies (End = last step). In sync.
