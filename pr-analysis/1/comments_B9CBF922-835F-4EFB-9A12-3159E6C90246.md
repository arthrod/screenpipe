**`packages/n8n-nodes-screenpipe/nodes/ScreenPipe/ScreenPipe.node.ts:387-398` — P2**

**`toCapture` silently drops fields for Input and Memory hits.** I checked every content shape against the engine: `InputContent` names its window field `window_title` (`crates/screenpipe-engine/src/routes/content.rs:201`), but the node reads only `c.window_name`, so `window` is missing on every input event; `MemoryContent` has `created_at`, not `timestamp` (`content.rs:111`), so `timestamp` is missing on every memory hit. Because the result goes through `withoutEmpty` (line 380-384), these come out as absent keys with no error — a workflow or AI tool just gets less information. The tests only exercise UI and Audio shapes (`test/screenpipe.node.test.ts:28-38,118`), so this is untested today. Fix is two fallbacks: `window: c.window_name ?? c.window_title`, `timestamp: c.timestamp ?? c.created_at`, plus one input and one memory fixture.

**`packages/n8n-nodes-screenpipe/nodes/ScreenPipe/ScreenPipe.node.ts:332` — P3**

**`shown` depends on an exact human-readable string owned by another codebase.** `shown: message === "Notification sent successfully"` is the only shown/held signal today (every 200 reply from `/notify` carries `success: true` — `apps/screenpipe-app-tauri/src-tauri/src/server.rs:39-43`, `notifications/routes.rs:600-602`), so the coupling is understandable, but any wording change in the app silently flips `shown` to `false` for successful sends. Note also the persisted-dedup path answers "Notification already sent" (`notifications/routes.rs:490-492`) and classifies as `shown: false` even though the notification was shown on the first delivery. Safer: have the server expose a structured `shown`/`delivered` field, or at minimum co-locate the expected string with the server constant and a cross-referencing comment in both files.

**`packages/n8n-nodes-screenpipe/nodes/ScreenPipe/ScreenPipe.node.ts:301` — P3**

**`new URL(url)` sits outside the try, so a malformed `notifyUrl` bypasses the node's error mapping.** Every other failure in this file becomes a `NodeApiError` naming the URL and asking "is ScreenPipe running?"; an invalid URL throws a bare `TypeError: Invalid URL` instead. It is still caught by the item-level `continueOnFail` catch (lines 235-239), so impact is minor, but the error the user sees is inconsistent with the rest of the file. Parsing inside a try (or wrapping in a `NodeApiError`) keeps one error style.

**`packages/n8n-nodes-screenpipe/nodes/ScreenPipe/ScreenPipe.node.ts:350-358` — P3**

**The read operations send no `timeout`, unlike `notify`.** `notify` sets `NOTIFY_TIMEOUT_MS = 5000` (lines 19, 312) precisely so a notification never holds a run; `getJson` relies on whatever default `ctx.helpers.httpRequest` has, so a stuck ScreenPipe can hold a search/activity-summary item indefinitely. A generous cap (60–120 s — activity summaries over long ranges can legitimately take seconds, so nothing as tight as notify's 5 s) would make the failure mode the same one the tests already cover.

**`packages/n8n-nodes-screenpipe/nodes/ScreenPipe/ScreenPipe.node.ts:105` — P3**

**The "Notification ID" description contradicts the actual behavior.** It says "Leave empty for one per run and node", but the synthesized ID includes the item index (line 286: `n8n:${workflow.id}:${executionId}:${node}:${i}`), so two items produce two notifications. The test name states the real contract ("each run and item gets its own", `test/screenpipe.node.test.ts:318`). One-word description fix ("per run and item").

**`packages/n8n-nodes-screenpipe/nodes/ScreenPipe/ScreenPipe.node.ts:370` — P3**

**Non-2xx `detail` can render as "[object Object]".** `String((body as IDataObject).error ?? JSON.stringify(body))` stringifies the whole body only when `error` is absent; when the server returns `{ "error": { ... } }` (an object), the user sees `ScreenPipe returned HTTP 500 for /search` with description "[object Object]". Check `typeof error === "string"` before using it, else `JSON.stringify` it.
