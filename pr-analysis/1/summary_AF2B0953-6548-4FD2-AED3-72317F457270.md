subtle ones: idempotent activation when n8n already runs the reviewed version
(:1500-1517 vs automation_flows.rs:1493-1514), `already_running` approval without a
publish call, second dismiss logging nothing (:1684-1694 vs automation_flows.rs:1655),
one publish/unpublish for repeated clicks (:1780-1791 vs `write_lock` + idempotence
checks), pagination preserving the tag filter (:1387-1399), and the CSRF middleware

The security tests are real: guessed/API-key-in-activation-header refusals assert no
publish happened and n8n stays off; the `..%2Fcredentials` route asserts 404 before any
n8n call; the credential/host-leak canary (`no_step_shows_n8n_credentials_or_called_hosts`)
scans the one Flow response that actually contains credential names and a called host.
No timing-sensitive assertions in this range (the running-wait tests that own the
`RunningWait` pacing live at 2963+), so no flakiness risk observed in my slice.

## Risks / limitations

1. **P3 coverage gap (posted):** with the default desktop app harness (`App::new()`,
   local API auth off — the configuration every lifecycle test in the slice uses), no
   test asserts that `POST /:id/activate` with a *wrong* activation credential is
   refused. Wrong-key refusals are asserted only with local auth on (:1943-1951) or
   headless (:2082-2092). The gate (`from_user`, automation_flows.rs:1459-1464) is
   independent of api_auth, so this only guards against future coupling — hence P3.
2. **Fake fidelity is the suite's inherent ceiling:** the fake n8n mirrors n8n 2.42.2
   behavior as the author understood it (its comments cite versions, e.g.
   :78, :298-299, :412-414). If real n8n deviates (unpublish semantics, retry shape,
   paging), these tests still pass. Inherent to wiremock suites; noting, not faulting.
3. Repeated-click tests (:1753) click sequentially; the concurrent-double-click path
   through `write_lock` is untested, but sequential clicks already exercise the same
   idempotency branch, so I did not post this.
4. Slice-focus mismatch: confirm the reviewer assigned ~lines 2943–3051 actually
   covered the running-execution wait tests; that behavior (never lose the email being
   processed) is the PR's most important guarantee per the module doc
   (automation_flows.rs:186-208).

Nothing in this slice blocks the PR. The one posted comment is a P3 test-coverage
