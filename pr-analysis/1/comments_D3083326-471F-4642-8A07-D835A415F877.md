## Review: `crates/screenpipe-engine/tests/automation_flows_test.rs` (lines 1–1017) — setup realism & assertion quality

Nice harness overall: hermetic per-test `App` (tempdir + in-memory SQLite + audio
disabled), precise error-code discrimination tests (412 vs 502 vs
`n8n_unauthorized` vs `n8n_failed`), and negative assertions that pin real behavior
(create POST must not carry `active`, no `publish` after the auto-unpublish, empty
`activationLog`). All 8 tests in this range pass locally
(`cargo test -p screenpipe-engine --test automation_flows_test -- <the 8 names>` →
8 passed, 99 filtered out). Four small findings, all test-infrastructure quality:

---

**P3 — `crates/screenpipe-engine/tests/automation_flows_test.rs:471-474`**
**The fake's two encodings of "finished" disagree, which can mask a retry regression.**
Executions completed via the poll countdown get `status: "success"` and a `stoppedAt`
but no `finished` field, while the retry handler refuses only `original["finished"] == true`
(line 426). So a poll-finished execution is still retryable *in the fake*. The engine's
own `retryable` gate (`retry.rs:75-81`) would never send such a retry today, but if a
regression made it retry a finished run, the fake would answer 200-success instead of
the modeled 409, and no test would catch it. Set `finished: true` when completing an
execution via the countdown (or key the retry refusal on `status` too) so the fake's
state stays in one vocabulary.

---

**P3 — `crates/screenpipe-engine/tests/automation_flows_test.rs:367-383`**
**`publish` accepts any `versionId`; `retry` ignores its request body — the fake cannot
catch wrong-payload bugs on the two safety-critical endpoints.** The design rule is
that only the version the user reviewed goes live, and the engine does send
`{"loadWorkflow": …}` on retry (`automation_flows/retry.rs:95`). But the fake publishes
whatever `versionId` arrives (falling back to the current one) without checking it is a
version the workflow actually holds, and the retry handler never reads `loadWorkflow`.
A test asserting that n8n refuses (or the fake 400s) an unknown `versionId` would turn
these endpoints into real guards rather than echo chambers; modeling `loadWorkflow`
(e.g. only succeed the retry when it matches the saved/published state) would do the
same for retries.

---

**P3 — `crates/screenpipe-engine/tests/automation_flows_test.rs:576-585`**
**Positional booleans make the `SCServer::new` call unreadable.**
`SCServer::new(db, addr, dir, true, true, audio_manager, false, "balanced".to_string())`
means `vision_disabled=true, audio_disabled=true, use_pii_removal=false` only after
reading `server.rs:392-400`. Two one-line named locals (or a short comment) would keep
the setup self-documenting:

```rust
let (vision_disabled, audio_disabled, use_pii_removal) = (true, true, false);
```

---

**P3 — `crates/screenpipe-engine/tests/automation_flows_test.rs:533`**
**Stale doc comment on `App::new`.** "local API auth off (as in the tests above)" —
there are no tests above this helper; it is defined before all of them. Presumably it
means the desktop app's default engine configuration; rewording to that effect (e.g.
"local API auth off — the desktop default") removes the confusing reference.
