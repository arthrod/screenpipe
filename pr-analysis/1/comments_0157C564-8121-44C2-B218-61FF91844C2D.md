**Review of `infra/automation-flows/demo/reset.ts` + `reset.test.ts` (demo-reset slice)**

The deletion scope is right and verifiably so: only records with `sourceTaskId === DEMO_TASK_ID` plus the bundled fixed id are removed, chat-created Flow records survive, other tagged Flows are only listed (`reset.test.ts:96-112`, `reset.test.ts:226-240`). I cross-checked the engine contract claims (`sourceTaskId` camelCase, `FLOW_TAG`, `valid_workflow_id`, `instance_url`, the `connections.json` fallback) and they all match; `bun test infra/automation-flows/demo/reset.test.ts` passes 13/13 locally. Nothing below is a blocker; all P3s.

**[P3] `infra/automation-flows/demo/reset.ts:93-94` — archive-on-delete claim contradicts the engine's own comment**

reset.ts says "n8n 2.x deletes only archived workflows" and the test fake's `strictArchive` mode encodes exactly that (`reset.test.ts:57`), but the engine's `delete_workflow` asserts the opposite: "n8n's public `DELETE` removes it, it does not archive it" (`crates/screenpipe-engine/src/automation_flows.rs:874-881`). Your delete → archive-on-refusal → delete order (`reset.ts:92-99`) is correct under either behavior, so nothing breaks — but one of these two statements about n8n 2.x is wrong, and whoever debugs a real-machine reset later will start from a false premise in one of the two files. Worth reconciling (or citing the observed n8n response that motivated `strictArchive`) so the two document the same API.

---

**[P3] `infra/automation-flows/demo/reset.ts:111-112` — `loadStore` accepts a JSON array, then the records step rewrites it**

`typeof [] === "object"` and `store.flows === undefined` both pass the guard, so a store file containing a JSON array is accepted as valid; the records step then spreads it into an object (`{ ...current, flows }`, `reset.ts:199`), turning `[...]` into `{ "0": …, flows: … }` on disk. That silently rewrites a malformed store instead of leaving it untouched, which is exactly what this function's error path promises ("it was left untouched"). One `!Array.isArray(store)` in the condition closes it.

---

**[P3] `infra/automation-flows/demo/reset.ts:87-91` — unpublish doesn't wait for a running execution, unlike the engine's own unpublish**

The engine deliberately waits for running executions to finish before unpublishing (`RunningWait`, `crates/screenpipe-engine/src/automation_flows.rs:857-879`), so the in-flight run completes; reset unpublishes unconditionally and immediately. If reset runs while a demo Flow is mid-execution (a Gmail trigger just fired), the run is cut off and can leave partial side effects — a half-created Jira ticket, a sent notification — which is precisely the polluted start state this script exists to prevent before the next rehearsal. Consider checking `/executions?status=running&workflowId=` and waiting (bounded, like the engine) before switching off, or at least warning in the output when the workflow was running at unpublish time.

---

**[P3] `infra/automation-flows/demo/reset.ts:101-102` — the post-delete verification GET can turn a successful deletion into a reported failure**

After a 2xx DELETE, the follow-up `GET /workflows/{id}` is required to answer 404; a transient network error or 5xx there fails the whole step and keeps the record, even though the workflow is actually gone, and the CLI exits 1 on an effectively successful reset. It self-heals on the next run (GET → 404 → "already removed" → record removed), so this is only a spurious-red signal, but treating "delete acknowledged 2xx" as deleted — or retrying the verification GET once — would avoid reporting a failure for work that succeeded.
