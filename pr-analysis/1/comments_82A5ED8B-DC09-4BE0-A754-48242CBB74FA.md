**[P2] `infra/automation-flows/demo/catalog.test.ts:3` — these demo tests never run in CI.** `test-frontend.yml`'s bun:test step (`.github/workflows/test-frontend.yml:91`) runs `bun scripts/run-bun-tests.ts`, whose discovery root is `apps/screenpipe-app-tauri` (`apps/screenpipe-app-tauri/scripts/run-bun-tests.ts:14` → `collectBunTestFiles(appRoot)`, and `bun-test-files.ts` walks only that root), and no workflow in `.github/workflows/` references `infra/automation-flows` at all; vitest also runs from the app root and excludes `bun:test` files by design. `docs/automation-flows/history/flows-round-two/coverage.md:22-24` records `bun test infra/automation-flows` as a manual command only. That matters here because these files pin the revision-bump reinstall semantics that keep local issue #17 fixed (`docs/automation-flows/history/flows-round-two/issues/17-create-automation-stale-task-page.md` — the stale Task Page that fails the first « Create automation » click on stage), so a future regression in `upsertTask`/`clearAnswers`/`writeCatalog` or in the fake-`/search` contract would merge green. Both slice files pass today (`bun test infra/automation-flows/demo/catalog.test.ts infra/automation-flows/demo/recorded-evidence.test.ts` → 12 pass / 0 fail; full documented scope `bun test infra/automation-flows` → 65 pass / 0 fail in 2.4 s), so adding that one command as a CI step — or extending the bun-test discovery root to the repo — is a cheap, verified fix. Same gap applies to `recorded-evidence.test.ts` and `reset.test.ts`.

**[P3] `infra/automation-flows/demo/recorded-evidence.test.ts:86` — the 503 branch is unreachable in the test named for it.** « Finds every capture when ScreenPipe serves one search at a time and answers 503 to the others » builds the fake server with `maxConcurrent = 1`, but the client under test is strictly sequential — `findRecordedFrames` awaits each capture (`demo-task/recorded-evidence.ts:78-81`) and each capture awaits its before/after searches (`recorded-evidence.ts:68-69`) — so every request arrives with `inFlight === 0` and the `inFlight >= maxConcurrent → 503` guard at `recorded-evidence.test.ts:25` never fires. Deleting the entire 503-retry loop (`recorded-evidence.ts:48-55`) would still pass this test, so the retry path that matters when the real engine is busy has no coverage. Failing the first attempt per search (e.g., on a request counter) instead of on concurrency would actually exercise the backoff/retry loop while keeping the same assertions.
