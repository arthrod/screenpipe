## 2. Review of the slice code as it exists on `origin/main` (base branch, commit 5ce7edfcd — NOT this PR)

I extracted the base versions (`git show origin/main:<path>`) and read all four files in full, plus the cross-crate `crates/screenpipe-db/src/db/privacy_release.rs` (base) they depend on. Line numbers below refer to those base versions unless marked otherwise.

### worker/mod.rs — dispatch/backpressure focus

**Solid against the repo's hot-path rules.** The run loop bounds background work and never capture: the resource governor is acquired only around `process_one` ("Capture itself never enters this background lane", worker/mod.rs:326-338); per-table adaptive work slices (batch 16, initial 4, target 250 ms, worker/mod.rs:53-118, 289-301); pause + `background_work::is_suspended()` honored (worker/mod.rs:304-316). Errors defer, never drop: transient → 2 s backoff (worker/mod.rs:445-452), DB hard fault → 300 s (worker/mod.rs:423-444), missing schema → target disabled for the run (worker/mod.rs:406-422). No path deletes a captured row.

The +17 dispatch change (worker/mod.rs:506-517): when the release policy requires text, `FullText` routes to `process_release_slice` and every other table returns `Ok(0)`. Surface coverage survives because the release scheduler's kind registry covers all text surfaces — `frames, audio, input, elements, memory, parsed, segments, activity_tasks, activity_actions, exports` (`privacy_release.rs:44-118`, `text_release_kinds` at :121-127) — so funneling everything through the `FullText` slot loses no surface. Gated-but-unredacted records stay **hidden, not dropped**: protected read views substitute placeholders/NULL until a receipt exists (`privacy_release.rs:774-794`), which is the retain-and-defer posture the AGENTS.md hot-path section demands.

- Nit: `db.release_policy().await?` runs once per table per sweep (worker/mod.rs:508) plus once inside `release_pending_ordered` (`privacy_release.rs:426`) — up to ~6 cheap single-row reads per idle sweep. Correct but could share one read per sweep.

### worker/hybrid.rs — handoff focus

The +1 (worker/hybrid.rs:31) makes `with_frame_storage` also set `release_db`. This closes a real wiring hole: the production engine wires the text worker via `.with_frame_storage(...)` only (`screenpipe-engine.rs:2342`, base), so without this line the release gate would silently never engage (`release_db: None` falls through to the legacy destructive path at worker/mod.rs:519). With it, the gate engages as soon as policy text flips on, and the hybrid frame path hands off correctly:

- While text policy is on, `process_hybrid_frames` is bypassed; frames are instead processed as release jobs that carry a `storage_generation` snapshot (`privacy_release.rs:490-512`) and publish through generation-aware `replace_frame_payload_with_release` with an explicit guard "Never update archived payload columns through raw SQL" (`privacy_release.rs:626-648`). `configure_release` sets `required_surfaces: 63` on frame storage when text is required (`privacy_release.rs:361-366`), matching what the release path publishes with. Coherent handoff.
- Fragility (P3): gate activation still depends on which builder production calls — `new_with_writer` leaves `release_db = None` (worker/mod.rs:158), and unlike the image worker there is no `with_release_storage` for the text worker. Any future wiring path that skips `with_frame_storage` silently disables the PII release gate and reverts to destructive in-place redaction. A fail-loud default would be safer.

### worker/release.rs — release gate (consent, atomicity, audit) focus

New 273-line file; overall well-built for its safety goal:

- **Atomicity**: partial redaction lives only in the in-memory `Progress` ("Partial results stay in memory and are never visible until atomic publish", release.rs:130-133); publish happens only when *all* fields are done (release.rs:215-225) and `publish_release` revalidates `(policy identity, revision, required-flag, rows_affected)` inside an immediate transaction, rejecting stale results as retryable (privacy_release.rs:649-707; image analog :948-968). In-flight progress is discarded when superseded via `release_job_current` (release.rs:154-158, query at privacy_release.rs:601-604) — this is what makes concurrent privacy revocation safe.
- **Consent/policy**: gating requires a non-empty policy identity (privacy_release.rs:165-167); every defer/publish rebinds the job's policy identity (`defer_release` WHERE clause, privacy_release.rs:936-937); policy changes bump `epoch`/`receipt_key`, void prior receipts and re-enroll (privacy_release.rs:164-197). Failures back off with a capped schedule `min(3600, 30*(attempts+1))` s and never delete the source row (privacy_release.rs:934-942).
- **Audit trail**: per-revision receipts in `_privacy_release` plus an ordered `_privacy_ready` stream exposed via `release_ready`/`ready_changes` (privacy_release.rs:710-732); failure messages carry only kind/id/revision and sanitized HTTP classes — never captured text (release.rs:230-245). Good log hygiene.
- **Backpressure**: slice is bounded by attempts, "all kinds empty", pause, and `target_batch_duration`, yielding between per-field detector steps (release.rs:144-150, 200-210); DB errors inside the sweep notify + count as empty instead of aborting (release.rs:169-182).
- **P3 — poison-pill rows**: `Progress::new` treats a malformed JSON column as a hard error (release.rs:59-61). Malformed `accessibility_tree_json`/`properties` blobs are a known-real shape (every legacy path warn+skips them to avoid busy-loops, e.g. worker/mod.rs:605-614). Here the row is deferred and retried forever (defer has no attempts cap; retry caps at 1 h) — the record stays gated (unreadable placeholders) indefinitely with recurring hourly churn and warns. No head-of-line blocking (defer advances `available_at`), but there is no give-up/flag path. Suggest a bounded-attempts escalation or a terminal "unredactable" receipt state.
- **P3 — non-string JSON scalars pass unredacted**: `collect` only redacts JSON strings (release.rs:248-273); a PII value stored as a JSON number/bool in `metadata_json`/`properties` is published verbatim under a "processing complete" receipt. Inherent to text redaction, but worth an explicit decision/doc since the release gate is the privacy boundary.
- Nit: in the two error paths, `db.defer_release(&job).await?` (release.rs:192, 212) — if the defer itself fails, its error masks the original redactor error and no backoff is written, so the job is re-picked after only the worker's 2 s backoff.

### image/worker.rs — memory bounds per frame focus

**Bounds are sound.** One image in flight at a time: the 16-job batch (image/worker.rs:393-400) is row descriptors only, and the loop returns after the first processed job (image/worker.rs:474-475); the a11y payload fetch is explicitly single-frame (`frame_payloads(&[id], ...)`, image/worker.rs:444-446); dimension reads are header-only (`image::image_dimensions`, image/worker.rs:451); `redact_frame` decodes one full frame and writes atomically via sibling tempfile + fsync + rename (frame_redactor.rs:57-140 — blob identical on both branches, so working-tree lines are valid). No per-frame allocation on any capture callback; this is all in the reconciliation task behind the governor (image/worker.rs:215-233). The CPU-lane restructure (image/worker.rs:235-276) now drops the shared permit before idle/error naps and is proven by a new test (`empty_image_queue_releases_cpu_lane_before_idle_poll`, image/worker.rs:537-571).

- **P3 — head-of-line on non-numeric job id**: `let id: i64 = job.id.parse()?;` (image/worker.rs:402) errors the whole call **without** deferring the job — no `attempts`/backoff write — so with the oldest/newest alternation (`release_oldest.fetch_xor`, image/worker.rs:398) every oldest-ordered pass re-fails at the same head row forever, roughly halving image throughput. This is exactly the starvation shape the same commit fixes for malformed timestamps two lines later (defer+continue at image/worker.rs:403-413, with a dedicated test at :573-630) — it just missed the parse case. Likelihood is low (ids are `CAST(int_pk AS TEXT)` from `discover_release_work`, privacy_release.rs:583-585) but the table is durable, so corruption/migration debris is reachable. Defer+continue would match the neighboring handling.
- Minor: `Err(error) => { db.defer_release(&job).await?; return Err(error); }` (image/worker.rs:476-479) — a failing defer masks the inference error (same nit as release.rs above).
- The TOCTOU guard (size+mtime before/after detect, image/worker.rs:441-461) narrows but cannot eliminate a concurrent file rewrite (the file is re-read after the check by `redact_frame`); acceptable given capture writes immutable per-frame files. The age double-check (image/worker.rs:414-418) backs the SQL predicate (`privacy_release.rs:440-452`, with `schedule_image_maturity` bounding skewed timestamps at :516-537).
