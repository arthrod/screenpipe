**[P2] `crates/screenpipe-db/tests/physical_disk_full_vm_test.rs:72-79` (origin/main, added by b1266c89f) — Recovery is proven only across an app restart, and no auto-recovery path exists.**
The test frees space, drops the faulted `DatabaseManager`, constructs a new one, and proves durable writes resume (lines 72-79) with pre-fault rows intact (82-94). That is genuine recovery, and the test correctly asserts recovery rather than blessing rejection as a terminal state. But it silently codifies "recording resumes only after an app restart": I grepped origin/main hard-fault handling (`crates/screenpipe-db/src/db/mod.rs:143-156`, `crates/screenpipe-db/src/db/maintenance.rs:55,1585-1608`) and found fault latching and reporting hooks, but no path that un-latches a hard-faulted writer when capacity returns. If that matches production, a user who clears disk space keeps a dead recorder until the app restarts — a recording-availability gap worth an explicit design decision (auto-probe + un-retire, or an intentional restart-only contract surfaced to the user), plus a test for whichever is chosen.

**[P3] `crates/screenpipe-db/src/migrations/20261016210000_starred_session_sync.sql:10,15-25` (origin/main, added by #7677) — Delete cleanup is FK-cascade-only, and the sync feed can never echo deletions.**
There is no `AFTER DELETE` trigger; row cleanup relies entirely on `ON DELETE CASCADE` firing under sqlx's default `PRAGMA foreign_keys = ON` (the reliance is documented at `crates/screenpipe-db/src/db/mod.rs:417`). Today no production code deletes `starred_sessions` rows (only tests do, via raw SQL), so nothing dangles — but if one ever deletes rows with FK enforcement off (raw connection, maintenance tool), orphaned sync rows accumulate silently, and the consumer's INNER JOIN (`crates/screenpipe-db/src/db/starred.rs:29`) drops them from output. Related design note: because the feed is a sequence cursor over existing rows, a future unstar/delete feature can never propagate deletions to enterprise consumers. Worth a stated decision (tombstones vs. documented out-of-scope) before a delete feature lands.

**[P3] `crates/screenpipe-db/src/migrations/20261016210000_starred_session_sync.sql:14` (origin/main) — Backfill and live rows use different timestamp semantics.**
Backfilled rows get `timestamp = session start` (line 14), while both triggers stamp wall-clock `strftime('%Y-%m-%dT%H:%M:%fZ','now')` (lines 18, 24). Harmless today — the consumer's cursor is `sequence`, and `c.timestamp` is informational in the tuple returned by `starred_sessions_for_sync` (`starred.rs:23-28`) — but a trap for any future filter on `timestamp`. A comment on the backfill line, or `strftime('now')` in the backfill too, would remove the ambiguity.

(a) Line 50's `"x".repeat(128 * 1024)` path string is the trick that forces real bytes through the batched writer so ENOSPC surfaces quickly; it deserves a comment.
