## Review: Review Screen actions & Learned-from provenance

Reviewed `flow-review.tsx` and `flow-learned-from.tsx` (both new in this PR) against the engine/API contract (`api.ts`, `common.tsx`, `flow-activation.tsx`, `flow-activity.tsx`, the demo task data and `flows-tab.test.tsx`). Permission gating in this slice is sound — "Turn on" only renders from a user click, with the version the user loaded (`flow-review.tsx:66`) and the UI credential (`api.ts:229-232`) — and the demo's learned-from evidence is real recorded data, not invented. The findings below are the gaps I could not clear; none duplicates what is already on the PR.

---

**[P2] `apps/screenpipe-app-tauri/components/automation-flows/flow-learned-from.tsx:41-43` — a load failure renders exactly like "the user never did this by hand".**

When `api.repetitions` rejects, the catch path does `setRepetitions([])`, and the section then renders the same UI as a task with zero repetitions: no cards, no count, and — when `flow.sourceMoment` exists — the "View in timeline" button of the empty state (`flow-learned-from.tsx:61`). For a section whose entire purpose is provenance ("Learned from" evidence), silently showing absence-of-evidence when the catalog could not be read misrepresents what happened; the only rejection source is `loadTaskCatalog` (`api.ts:388-398` — per-capture errors are already swallowed into placeholders), i.e. a real disk/read failure. The sibling Activity section on the same screen gets this right: it prints "Could not read the activity from n8n right now." (`flow-activity.tsx:58-62`). Please distinguish the error state (a quiet failure line, ideally with the same retry affordance) and add a test for the rejection path — `flows-tab.test.tsx:776-813` covers only the rendering paths.

---

**[P2] `apps/screenpipe-app-tauri/components/automation-flows/flow-learned-from.tsx:74` — "Times you did it by hand" (and the count badge at `:55-57`) is only truthful for demo-shaped data.**

The cards come from `task.stages.map(stage => ({ title: stage.name, … }))` (`api.ts:392-397`), so the component's labels assume one stage = one time the user did the task. That holds for the demo task, whose stages are literally built from `REPETITIONS` and named "Repetition 1 · …" (`lib/automation-flows/demo-task/detected-task.ts:137-149,184`). For a genuinely detected task, a `WorkflowStage` is a *phase* of the task with its own `observedOccurrences` (`packages/workflows-ui/src/model.ts:95-119`) and the real number of times is `WorkflowMap.repetitions` (`model.ts:179`) — there the section would present 3-4 phase cards under the aria-label "Times you did it by hand" with a matching count badge, overstating how many times the user performed the task. That is exactly the "fabricated labels" failure mode this section must avoid, and it also diverges from the plan, which wanted "one card per repetition of the source task, with its captures as a strip (email → form → ticket)" (`docs/automation-flows/history/hackathon/flow-front-merge.md:62-63`). Either derive the cards/count from the task's actual repetition structure, or reword the label (and the file's header comment at `:7-8`) so it claims stages, not times, when the two can differ.

**[P3] `apps/screenpipe-app-tauri/components/automation-flows/__tests__/flows-tab.test.tsx:790` — the Learned-from card test is timezone-dependent and fails west of UTC.**

Ran `bun x vitest run --config vitest.config.ts components/automation-flows` on a machine in `America/New_York`: **1 failed | 122 passed**, with this test expecting `/Oct 17, .+ · Gmail, Jira$/` while the card renders `Fri, Oct 16, 10:05 PM · Gmail, Jira` for capture `2026-10-17T02:05:41Z` (`formatDate` renders local time, `labels.ts:38-48`; the card meta is `flow-learned-from.tsx:128-130`). Re-running just this test with `TZ=UTC` **passes**, which confirms the diagnosis: the suite is green in UTC+ runners and red for anyone west of UTC, masking real regressions in this area. Pin the timezone for the test (or assert the date TZ-independently, as the dialog test at `:804` already does with `.+`).

---

**[P3] `apps/screenpipe-app-tauri/components/automation-flows/flow-learned-from.tsx:139-157` — `CaptureImage`'s `broken` flag goes stale when the dialog switches to another capture.**

`broken` is component state that never resets on prop changes, and the dialog's main image mounts `CaptureImage` unkeyed at a fixed position (`:184-189`), so switching captures with the thumbnails (`onSelect`, `:203`) reuses the same instance. If one capture's image fails to render (`onError` → `broken=true`) and the user clicks a thumbnail whose image is valid, the placeholder still shows because `!capture.image || broken` keeps the short-circuit. The thumbnail strips are unaffected (they key by frame, `:110` and `:201`). Add `key={capture.frameId}` to the dialog's main `CaptureImage` (or reset `broken` when `capture` changes).

---

**[P3] `apps/screenpipe-app-tauri/components/automation-flows/flow-review.tsx:130,135` — "Review and edit" and "Open in n8n" can fail with no feedback, unlike every other control on the screen.**

Both handlers are `void`-ed promises. `api.openTaskPage` awaits `routeNotificationDeeplink`, which throws on failure (`lib/notifications/actions.ts:171` and the error paths below it), so a failed Task Page handoff is an unhandled rejection with zero UI signal; `api.openInN8n` catches `openUrl` failures internally (`api.ts:371-382`) but its `window.open` fallback can still throw in the web-dev loop. Every other action on this screen reports failure inline — activation via `FlowActivationNotices`, delete via its error box, timeline/chat via `OpenButton`'s `failure` message. Wrapping both clicks in `OpenButton` (or a shared catch that shows the same quiet inline failure) would close the inconsistency.
