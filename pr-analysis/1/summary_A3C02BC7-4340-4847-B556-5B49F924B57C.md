# Slice summary: Automation Flows failure reporting (`failures.rs`) and retry (`retry.rs`)

Reviewer: reviewer-rust-flows-failures · PR #1 (`arthrod/screenpipe`, host github.com, account arthrod) · Both files are new in this PR (354 + 112 lines, `git diff origin/main...HEAD`).

## What the slice changes

**`crates/screenpipe-engine/src/automation_flows/failures.rs` (SPEC D16)** — failure *reporting*, not error typing:

- Installs one shared n8n "error workflow" (Error Trigger → HTTP node) tagged `screenpipe-flow-errors`, published because n8n 2.x refuses a Flow naming an unpublished error workflow (`error_workflow_id`, failures.rs:110-136). Best-effort: any refusal degrades to health-check-only reporting and never blocks a Flow write (`name_error_workflow`, failures.rs:343-354).
- `POST /:id/failures` (`report_failure`, failures.rs:171-223): the error workflow calls back with an execution id; the engine verifies the execution belongs to that Flow (failures.rs:188), pulls its data with the n8n key, and hands the notice to `health::notify_run` so a run is notified once across both paths (failures.rs:202-208).
- `failure_notice` (failures.rs:229-283): builds the notification — sender/subject extracted from the run data (`handled_email`, failures.rs:289-308), failing step + error, Review Screen deeplink, and a « Retry » api-action when there is a run to retry (failures.rs:263-272).
- Delivery classification: `notify` (failures.rs:320-338) splits outcomes into `Undelivered::Gated` (server took it but did not show it — terminal, never retried) vs `Undelivered::Unreachable` (retried by the health check with backoff, health.rs:75-87). This is the slice's "retryable vs terminal" policy.

**`crates/screenpipe-engine/src/automation_flows/retry.rs` (SPEC D17)** — single user-click retry:

- `POST /:id/runs/:run/retry` gated on the UI credential `from_user` (retry.rs:35-37, same gate as activation), validates the run id before splicing into the n8n URL (retry.rs:39-41), verifies execution↔Flow ownership (retry.rs:46), and refuses non-failed/already-retried runs via `retryable()` (retry.rs:75-81).
- `load_workflow` is true only when the current n8n version is the published or user-reviewed one (retry.rs:54-61) — a retry never executes unreviewed chat edits. Good.
- `retry_execution` (retry.rs:85-112): 180 s per-request timeout override on the shared client; maps timeout-without-connect → `RetryStillRunning` (504) and connect failures → `Unreachable` (502), 401/403 → `Unauthorized`.

**Scope note on the ask's framing:** the ask describes this file as "retry policy: backoff bounds and max attempts (one extra retry per commit 368a17b9a)". `retry.rs` contains no backoff and no max-attempts loop — it is one user-initiated retry with a 180 s wait. Commit 368a17b9a ("the AI step gives up after 8 s instead of 12 s, then tries once more") touched only `infra/automation-flows/workflows/novadesk-support-tickets.json`, its test, and `.scratch/hackathon/DEMO.md` (verified with `git show --stat 368a17b9a`) — the n8n-node-level retry, outside this slice. The only policy bounds in this slice are `RETRY_WAIT = 180 s` (retry.rs:26) and the Gated/Unreachable classification.

## Fit in the whole PR

These two files complete the failure story of Automation Flows: D16 (report), D17 (retry), D19 (health check, `health.rs`, other slice) interlock through the shared ledger (`notify_run`/`notify_once`, health.rs:211-245) so a run is notified exactly once no matter which path reports it, and `activity.rs` reads n8n executions as the source of truth. The Retry api-action emitted here (failures.rs:264-271) is what the app's `notificationApiHeaders` credentials (a security comment already on the PR covers its provenance gating — not repeated here), and coderabbitai already posted the concurrent-double-retry race on retry.rs:63-66 (in-flight guard missing) — not repeated here either.

## Findings (details in comments file; posted)

1. **P1 — transient delivery gates are classified terminal.** `notify()` maps every 2xx answer except the exact message "Notification sent successfully" to `Undelivered::Gated` (failures.rs:332); `health::notify_once` records Gated runs in the ledger (health.rs:240-244) so the health check skips them forever (health.rs:405-407). But the app's `/notify` suppression paths (quiet hours/snooze/master-off routes.rs:300-318, pipe toggle routes.rs:349-369, per-pipe mute routes.rs:392-406) return *before* the history write (routes.rs:457; the comment at routes.rs:294-299 says suppressed alerts "never write history"), and the notice is `type: "pipe"` (failures.rs:277) with no critical-type/VIP punch-through (gate.rs:10-19, 82-110). Net: a run failing while quiet hours or pause/mute is active is reported nowhere, ever — no panel, no history row, ledger says delivered. Contradicts the D16 promise (failures.rs:5) and the notice doc "shows each failed run once" (failures.rs:227-228). The authors documented "handled, never retried" (health.rs:202-203), but the "handled" premise is false: nothing survives. Suggested direction: treat pause/disable/mute answers as retryable (leave the ledger unmarked so D19 re-delivers after the pause lifts) and keep only "duplicate/already sent" terminal.
2. **P2 — `retryable()` disagrees with `health::failed()` on executions without a `status` field.** retry.rs:76-79 treats a missing `status` as "ended"; a run with no `status` and no `stoppedAt` (still running on an n8n whose public API omits `status`) then passes `finished != true` and is sent to n8n's retry endpoint, surfacing as 502 instead of the intended 409 `run_not_failed`. health.rs:447-452 handles that shape defensively (`finished == false && stoppedAt` present). One shared classifier would remove the drift.
3. **P2 — zero tests for the classification logic.** `retryable`, `handled_email`, `failure_notice`, and `notify`'s status/message matrix are pure functions over JSON — the exact retryable-vs-terminal decisions this slice owns — with no unit tests anywhere (`grep` for tests referencing them found none; `cargo test -p screenpipe-engine automation_flows` runs exactly 5 tests, all in `automation_flows.rs`/`health.rs` pacing). health.rs got pacing tests; these got none.
4. **P3 — queue-mode n8n answers a retry before the run finishes.** retry.rs:24-26 assumes "n8n answers once the retried run has finished"; in queue mode the public API returns immediately with the new execution still `new`/`running`, `flow_run` returns None (activity.rs:87), and the route answers 502 "answered the retry without its run" (retry.rs:67-69) although the retry started. I could not verify the bundled n8n's execution mode from this repo (conditional finding; recoverable via Activity).
5. **P3 (folded into finding 1) — the success protocol is exact English copy.** `notify()` matches "Notification sent successfully" (failures.rs:331); the app's own client repeats the same string (apps/.../lib/automation-flows/find-automation.ts:57). The `ApiResponse.success` field is `true` on every 200 including suppressions, so today the copy is the only discriminator — a wording change on either side silently reclassifies outcomes.
