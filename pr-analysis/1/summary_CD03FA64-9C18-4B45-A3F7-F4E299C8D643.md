## How it fits the whole PR

This slice is the edge of a package-wide dark-theme token migration. On `origin/main` the workflows-ui package contains zero `hsl(var(...))` usages (`git show origin/main:packages/workflows-ui/src/workflows-app.module.css | grep -c 'hsl(var('` → 0); the PR head has 20 added `hsl(var(` lines in `workflows-app.module.css` alone and converts `workflow-assistant.module.css:102-109` the same way (identical `--chat-*` → token mapping at `workflow-assistant.module.css:106`). My two files follow that same package decision. The coderabbit summary on the PR describes this as "Workflow screens now follow light and dark themes."

## Correctness of the token swap (chat-primitives.module.css:29)

- All four tokens exist and are defined as shadcn-style HSL channel triplets in the only dark-capable consumer, so `hsl(var(--token))` resolves: `apps/screenpipe-app-tauri/app/globals.css:104`/`239` (`--border`), `:49`/`:184` (`--foreground`), `:57`/`:192` (`--card`), `:53`/`:188` (`--surface-secondary`).
- Value shifts are warm→neutral but pairings stay correct in dark: border #44443f→#333, ink #e6e6df→#F5F5F5, surface #20211e→#141414, soft #30312e→#212121 (hover bg stays lighter than surface via `chat-primitives.module.css:27`). This matches the app's neutral dark contract ("Shared app + website color contract", `globals.css:44`, dark values `:183-194`).
- Mechanism is sound: the rule sets custom properties on `.jumpAnchor` (`chat-primitives.module.css:23`) which inherit into the `.jump` button (`:24`) whose declarations use `var(--chat-*, <light hex>)`. Selector specificity and position are unchanged, so nothing else reorders.

## The one risk: new host-token dependency (latent, not a current bug)

Dark mode of `.jump` now requires the host page to define the four tokens. Failure mode if a host ever applies `.dark` without them: `--chat-*` become invalid at computed-value time and every `var(--chat-*, <light hex>)` falls back to its **light** value — a white jump button in dark mode. Today this cannot fire: the Tauri app defines all tokens (above), and the only other consumer of the package, `apps/screenpipe-workflows-web` (imports at `apps/screenpipe-workflows-web/app/workflows-client.tsx:6`), defines no tokens at all and never applies a `.dark` class (`app/globals.css` is 12 lines, `:root` only), so the rule is inert there. The coupling is PR-wide (same pattern in `workflow-assistant.module.css:106`, `workflows-app.module.css:837,910-917`), so I posted it as a single P3 on my file rather than per-file noise. Not covered by existing PR comments (coderabbit's 15 line comments touch neither file).

## rich-text `.error` dark color (rich-text.module.css:87)

- Genuine fix: light `.error` is `#b42318` (`rich-text.module.css:86`, pre-existing on main) — near-illegible on dark surfaces; the element renders via `rich-text.tsx:205-211` (12px text).
- Contrast (my arithmetic, not a browser measurement): `#f4a199` on the dark card #141414 ≈ 9.1:1, on the canvas #0A0A0A higher — comfortably above WCAG AA 4.5:1 for 12px text. Light-mode counterpart #b42318 on white ≈ 6.6:1.
- Color-only declaration → no layout impact; this satisfies the slice's "no visual regression in rich-text layout" focus trivially (no layout property in either changed line).
- Hardcoded hex rather than a token is consistent with the design contract: the app deliberately keeps status colors grayscale (`globals.css:76`), so there is no red token to use, and the light `.error` is hardcoded red too.
- This is the only red in the package's CSS (`grep` over `packages/workflows-ui/src/*.css`), so no sibling error color was left without a dark variant.
