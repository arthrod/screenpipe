# Slice review: flows-round-two issue docs 07–12

Reviewer slice: six new history docs under
`docs/automation-flows/history/flows-round-two/issues/` (07, 08, 09, 10, 11, 12 —
542 added lines, all new files). Each is a per-ticket build record: "What to
build", checkboxes, "What was built / How it works", a "Live check (ticket 16)"
section still marked pending, and "Tests run" counts.

## How the slice fits the PR

The docs record round two of Automation Flows (drafts, simplified AI step,
abstention, duplicate-safe tickets, failure notification, retry). All six were
committed together in `754fbfbfa` ("docs: Automation Flows as a real feature,
out of hackathon mode", 2026-10-18 11:06). Hours later the same day, parallel
commits now also in this PR rewrote the demo workflow they describe:
`1955e12b8` 14:30 ("Gmail Trigger every 5 s, fast English AI ticket, ScreenPipe
notify node"), `cbe58446e` ("the AI writes a clear ticket for developers"),
`368a17b9a` 14:36 ("the AI step gives up after 8 s instead of 12 s"). The docs
were truthful for the workflow at their own commit (I confirmed the JSON at
`754fbfbfa` still had the IMAP trigger + `CUSTOM.screenPipeTool` nodes + HTTP
notify node), but the head ships a different demo workflow, so several doc
claims and all the pending "Live check (ticket 16)" instructions reference
nodes, strings and a mechanism that no longer exist at the PR head.

## Per-doc verdicts

**07 (build step by step) — accurate and runnable.** Draft routes
`POST /drafts`, `GET/PUT /drafts/:id`, `POST /drafts/:id/finish` exist
(automation_flows.rs:288-290); `409 flow_under_construction` /
`flow_not_under_construction` (:563, :570); `screenpipe-flow-building` tag
(:64); `flow_checks::inspect` → `Report::inventions` (flow_checks.rs:136,156);

step » (SKILL.md:262); finish names the error workflow (name_error_workflow at
automation_flows.rs:2007). Only stale bits are French labels (« Terminer »)
for an UI that is now English. No comment posted.

**08 (simplified AI step) — materially stale vs head.** The focus asks about
the 8 s timeout of commit 368a17b9a: the timeout **is** in the head JSON
(`screenpipe AI model` options `timeout: 8000, maxRetries: 0`), but the doc
never mentions any timeout, and its central claim — one agent with two
ScreenPipe tools (« Historique ScreenPipe », « Activité ScreenPipe »
`CUSTOM.screenPipeTool`) — is false at head: the rewritten agent has **no tool
nodes at all** (verified by listing node types in
`infra/automation-flows/workflows/novadesk-support-tickets.json`), the answer
schema gained `reporter/steps/expected/actual/impact/investigation_leads/
acceptance_criteria` on top of the doc's `confidence`, and the create-node
description is a richer ADF document than the doc's "a paragraph, then a
codeBlock". Its live check ("both ScreenPipe tools were called") cannot be run
against the bundled workflow.

**09 (abstain when unsure) — contract holds, mechanism stale.** Everything
security-relevant survives at head, moved into the `CUSTOM.screenPipe` node
("Sort by hand"): Host-header DNS-rebinding guard
(ScreenPipe.node.ts:302-303), Markdown escaping (:290, :336), id-based dedupe,
`type: "pipe"`, `priority: "high"`, `transient: false` (:291-293), and the
"Notification sent successfully" gate shared with `find-automation.ts:57`
(the node returns `shown` at ScreenPipe.node.ts:325). The confidence gate
matches (`caseSensitive: true`, strict `equals "high"`). But the doc's raw
HTTP-node mechanism, its "No action button" claim (head has `buttonLabel:
"View Flow"` + `screenpipe://flows/<id>`), the French node names and its
live-check expectation of `success: true` (now `shown`) are all stale.

**10 (duplicate-safe) — best matching doc; mechanism verified at head.**
Create node `onError: continueErrorOutput`, no `retryOnFail`; « Check the
creation » gate `$runIndex < 2`; StopAndError using
`$json.error?.message ?? $json.error` — all present in the head JSON, plus a
later-added 10 s "Let Jira index" Wait in the loop (commit 846066681, absent
from the doc). FNV-1a 32-bit constants identical in the head's search and
create expressions. Stale: the label input is now Gmail `e.id` →
`e.messageId` → `from|date|subject`, not the doc's IMAP
`metadata['message-id']`; the doc's IMAP-payload rationale and its live check
step 2 ("Mark that email unread again in Gmail … or the IMAP catch-up")
describe the replaced trigger. Verified running: flow_checks 9 ✓, infra
workflows 31 ✓ (both commands above).

## Risks / quality issues

1. The pending "Live check (ticket 16)" sections in docs 08, 09, 10, 11, 12
   instruct a future runner to verify French node names, IMAP behavior,
   ScreenPipe tools and French notification strings that the head's demo
   workflow no longer has. Ticket 16 (`16-full-live-check.md`, status
   "ready-for-agent") will be executed against the head; its per-ticket
   inputs are these sections. Either the docs need a supersession note
   pointing at the rewritten workflow / hackathon DEMO.md, or ticket 16's
   checklist will misfire.
2. Doc 12's "open to any local caller" paragraph is the one finding I'd treat
   as more than stale copy: it inverts a deliberate security decision.
3. Everything else in the slice is internally honest: recorded test counts
   reconcile with the suites as merged (107 engine tests at head), invented
   checks are marked pending rather than claimed, and known limits (Jira
   search-index lag, "Création refusée par Jira" retries failing again) are
   stated in the docs and match the code.
