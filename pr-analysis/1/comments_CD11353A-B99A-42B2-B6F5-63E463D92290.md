## Review: `crates/screenpipe-engine/src/n8n_nodes.rs` (node catalog)

Focus of this review: the catalog must only contain real node types. **Verified — no invented nodes.** The embedded `n8n-nodes.json.gz` is generated by `n8n-catalog.ts` from the running n8n container's own `nodes.json` manifests (nothing hand-typed); all 843 index entries (707 `n8n-nodes-base.*`, 132 `@n8n/n8n-nodes-langchain.*`, 4 `CUSTOM.*`) match the check layer's 840 types + 3 excluded exactly, in both directions; the 4 CUSTOM types trace to 3 real node dirs plus the `usableAsTool` twin of `ScreenPipe.node.ts`; and `cargo test -p screenpipe-engine --lib n8n_nodes` passes. Two minor findings below.

---

**[P3] `crates/screenpipe-engine/src/n8n_nodes.rs:267-281` — the offered-value check unions options across resource groups, so a combination the node does not offer is accepted.**

n8n nodes define several `operation` parameters, one per resource group. In the real gmail card, there are four `operation` groups with `show.resource` = draft/label/message/thread, each with its own options (e.g. `send` exists only under `message`). The validation at `crates/screenpipe-engine/src/n8n_nodes.rs:267-273` collects options from *every* kept property named `selector` (`flat_map` over all groups), so `resource=label` with `operation=send` returns no error, although the doc contract at `crates/screenpipe-engine/src/n8n_nodes.rs:172-173` promises "`Err` for a choice the node does not offer" — and this is a choice the node does not offer. The save-time check does not catch it either: `inspect_node` (`crates/screenpipe-engine/src/flow_checks.rs:207-219`) only reports required parameters whose display rules evaluate as shown at the node's actual params, so a cross-resource combo hides the operation's required fields from the check and passes review into n8n, where the node silently does nothing useful. Suggest validating each chosen selector against only the option groups whose `show` rules match the other chosen selectors (the rules are already on the card's properties), or documenting the union semantics on the card so the chat narrows itself using the visible `show` rules.

---

**[P3] `crates/screenpipe-engine/src/n8n_nodes.rs:315-336` — no unit tests for `narrow()`, `search()` ranking, or `add_credential_state()`.**

The module's only test asserts catalog consistency (every usable type has a card and a skeleton). That leaves the file's subtlest logic untested: `narrow()`'s per-selector verdicts, menu-vs-non-menu hiding and the two error paths; `search()`'s ranking guarantees ("A node before its AI-tool twin, then by name", `crates/screenpipe-engine/src/n8n_nodes.rs:156-161`, plus the exact-name bonus at `:107`); and `add_credential_state()`'s none/one/several branches. All three are pure functions over the embedded catalog, so each case is a few lines with the gz already in the test binary. This matters doubly here because the module's correctness depends on generated data whose shape can shift when `n8n-catalog.ts` is re-run against a newer n8n image — table tests would pin the behavior the doc comments promise.
