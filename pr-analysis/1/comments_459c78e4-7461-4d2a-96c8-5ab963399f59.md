## Review: n8n invocation paths in `automation_flows.rs` (middle third, ~751–1500)

Reviewed `crates/screenpipe-engine/src/automation_flows.rs` (all 2246 lines read; slice is new code) with focus on timeouts, secret handling, and duplicate-safe execution. Timeouts (shared 3 s/20 s client at `automation_flows.rs:256-260`), secret handling (constant-time `FlowActivationKey` compare at 169–177, key only ever in a header at 633–637, `N8nCredential` holds no secret per `flow_checks.rs:81-99`), and double-click idempotency in `activate_flow` (1493–1505) all hold up. Findings below; nothing here duplicates existing review threads.

---

**P1 | `crates/screenpipe-engine/src/automation_flows.rs:847` — `is_running` misses `new`/`waiting` executions, defeating the email-loss guarantee `unpublish` exists for.**

The module doc says n8n's mail triggers count an email as taken *before its execution starts*, and an execution caught by an unpublish never finishes — the email is lost (186–191). But `is_running` queries n8n with `("status", "running")` only (843–851), so an execution sitting in n8n's `new` state — exactly the "taken but not started" window the doc describes — reads as "not running" and `unpublish` (861–878) flips the switch. The rest of this PR disagrees with itself: `last_execution` maps `"running" | "new" | "waiting"` to running (802–809) and `retryable` treats `new`/`waiting` as not ended (`automation_flows/retry.rs:75-81`). Two of three call sites know `new` is live; the one guarding against email loss is not. I could not run the pinned n8n 2.42.2 (`infra/automation-flows/docker-compose.yml:13`) to confirm its public-API status semantics, so the n8n-side behavior is unverified — but the internal inconsistency alone justifies aligning `is_running` with the other two (e.g. drop the `status` filter and check the returned executions' statuses client-side, like `last_execution` does).

**P2 | `crates/screenpipe-engine/src/automation_flows.rs:861-878` — `unpublish` can hold the single global `write_lock` for ~90 s, stalling every other Flow mutation.**

Every mutating handler serializes on `state.write_lock` (225, 269; taken at 1484, 1545, 1584, 1648, 1675, and in the creation paths). `unpublish` polls `is_running` once per second until the `RunningWait` deadline — 90 s by default (204–206, wired via `server.rs:435`) — so pausing or deleting one Flow whose execution hangs (the very case the deadline exists for) blocks activating, creating, or deleting any *other* Flow for up to 90 s, and each poll can overshoot by up to the 20 s client timeout (843–851 vs 256–259). The user's HTTP request is also held open the whole time. The serialization itself is right for duplicate-safety; consider waiting outside the lock (re-check under the lock before the final `unpublish`) or a per-flow lock so one stuck email doesn't freeze the whole Flows UI.

**P3 | `crates/screenpipe-engine/src/automation_flows.rs:1398` — `list_flows` makes N+1 serial n8n calls.**

For each tagged workflow the handler awaits `api.last_execution(id)` one at a time (1390–1399); `build_flow` repeats the pattern per GET (1290–1295). Each call is a separate `/executions` round trip with a 20 s timeout, so list latency grows linearly with Flow count and the Flows list (which the UI renders on every open) degrades accordingly. `futures`-style concurrent fetches with a small bound, or a shared helper, would keep this flat.

**P3 | `crates/screenpipe-engine/src/automation_flows.rs:802-809` — `last_execution` labels `canceled` runs as "error".**

The catch-all `Some(_) => "error"` maps n8n's `canceled` (a user-stopped run) to "error", which the Review Screen then surfaces as a failure worth retrying (the retry route will refuse it as `run_not_failed`, since `retryable` sees it as ended, `automation_flows/retry.rs:75-81`). A distinct "stopped" outcome, or at least excluding `canceled` from "error", would stop the UI showing a retryable-looking failure that can never be retried.

**P3 | `crates/screenpipe-engine/src/automation_flows.rs:868` — one failed poll aborts a user's explicit stop.**

`while self.is_running(workflow_id).await?` propagates any single n8n error — one 5xx or a 20 s timeout — and the whole deactivate fails after possibly a long wait, leaving the Flow on and the user to restart the entire 90 s dance. The failure direction is safe (nothing is lost), but for `user_stop` the deadline already exists to bound the wait; treating poll errors as "keep waiting until the deadline" (and only failing if the deadline passes) would make the explicit stop as decisive as its doc promises (856–860).

**P3 | `crates/screenpipe-engine/src/automation_flows.rs:1101-1110` — a corrupt `automation-flows.json` permanently 500s every route, including reads.**

`FlowStore::load` turns a parse error into `FlowError::Internal` on every route. Fail-closed is the right call for writes — the comment at 2040–2042 explains why an unreadable store must not pair with new n8n state — but it also bricks `GET /` and `GET /:id` with no recovery path short of hand-editing the file. Renaming the unreadable file aside (preserving it) while serving an empty store would let the user keep working and keep the evidence for diagnosis. Low likelihood given atomic writes (`atomic_file.rs:41-75`), hence P3.

**P3 | `crates/screenpipe-engine/src/automation_flows.rs:2188-2246` — the wait logic and credential preservation have no tests.**

The unit tests cover `derive_status`, fixture import, and id validation (2205–2245). Untested: `keep_user_credentials` (971–996 — the guarantee that the chat cannot pick up credentials is exactly the kind of invariant that regresses silently), `unpublish`'s deadline/user-stop branches (861–878, now parameterizable over a clock), and the `FlowStore` save/load round-trip. All are pure or easily mockable; `cargo test -p screenpipe-engine --lib automation_flows` (which I ran: 5 passed, 0 failed, 1791 filtered out) is the natural home.
