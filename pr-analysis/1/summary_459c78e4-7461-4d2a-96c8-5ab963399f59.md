## What I checked and what holds up

**Timeouts.** All n8n calls share one `reqwest::Client` with 3 s connect / 20 s total timeouts (automation_flows.rs:256–260, cloned into `N8nApi` at 622). `retry_execution` overrides per-request with 180 s because n8n answers only after the retried run finishes (retry.rs:26, 94). The module doc ties the 90 s `RunningWait` deadline to the demo's 10–25 s AI step (automation_flows.rs:186–208). The 8 s AI-node timeout itself lives in `infra/automation-flows/workflows/novadesk-support-tickets.json` and is already covered by an existing PR comment (stale "12 seconds" note); I did not duplicate it.

**Secret handling — no leaks found in this slice.** `FlowActivationKey` is two UUIDv4s (244 bits, automation_flows.rs:152–161), compared with a fold-XOR constant-time compare (169–177), `Debug`-redacted (180–184), and required by `from_user` before any activation (1459–1464, 1476–1478). The n8n API key travels only in a request header (633–637); error strings include the n8n base URL but not the key (641–643), and reqwest error `Display` includes URLs, not headers. `N8nCredential` carries only id/name/kind, never the secret (flow_checks.rs:81–99), and `keep_user_credentials` (971–996) lets a chat edit keep only credential references that the current workflow already had on a node of the same name and type — the chat cannot attach credentials to new or retyped nodes (verified against flow_checks.rs wiring, which wires only from n8n's own credential list).

**Duplicate-safe execution.** The `write_lock: Arc<Mutex<()>>` (225, 269) serializes all mutating handlers, each taking the guard before loading state (activate 1484–1485, deactivate 1545, delete 1584, dismiss 1648, update 1675; creations 1913, 2038, 2094). `activate_flow` is idempotent for a double click: re-publishing the same reviewed version returns the current Flow without a second n8n `publish` (1493–1505). `create_from_task` dedupes by `source_task_id` and by the import script's fixed workflow id (2098–2148, outside the slice but read for context). `tag_id` handles the concurrent-create 409 by re-reading (703–722). Store writes are atomic (temp file + fsync + atomic persist + dir fsync, atomic_file.rs:41–75).

## Findings (detail in comments file)

1. **P1 — `is_running` filters `status=running` only (847)**, while the same file maps `"running" | "new" | "waiting"` to running in `last_execution` (802–809) and `retryable` treats `new`/`waiting` as not ended (retry.rs:75–81). The module doc's stated loss mode — n8n's mail triggers count an email as taken *before its execution starts* (186–191) — is exactly n8n's `new` status, so `unpublish` (861–878) can unpublish during that window and defeat the email-loss guarantee the function exists for. I could not run n8n 2.42.2 (pinned in infra/automation-flows/docker-compose.yml:13) to confirm its public-API status semantics; the finding stands on the internal inconsistency plus the documented race.
2. **P2 — `unpublish` polls up to the 90 s deadline (861–878) while every mutating caller holds the single global `write_lock`** (e.g. deactivate 1545, delete 1604 via delete, update 1692), so one Flow with a hung execution blocks activation/creation/deletion of every other Flow for up to ~90 s (plus up to a 20 s client-timeout overshoot per poll), and the user's HTTP request is held open the whole time.
3. **P3 — `list_flows` is N+1 serial** (1390–1399): one `/executions` call per Flow, each up to 20 s; `build_flow` repeats it per GET (1290–1295).
4. **P3 — `last_execution` maps every other status string, including `canceled`, to "error"** (802–809).
5. **P3 — one failed poll aborts `unpublish`** (868 `await?`): a single transient n8n error turns a user's explicit stop into an error after a long wait (fail-safe direction, but intolerant).
6. **P3 — a corrupt `automation-flows.json` 500s every route** (1101–1110); this is a deliberate fail-closed choice for writes (comment at 2040–2042) but also bricks read routes with no quarantine/rename-aside recovery.
7. **P3 — unit tests cover only pure helpers** (2205–2246: `derive_status`, `importable`/`review_graph` on fixtures, `valid_workflow_id`); `keep_user_credentials`, `unpublish`'s wait logic, and `FlowStore` round-trip are untested.
