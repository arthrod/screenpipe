# Slice review — `crates/screenpipe-engine/tests/automation_flows_test.rs` lines 3052–4068

Focus: fourth fifth — evidence/notification tests.

## What this slice is

The file is entirely new in this PR (5085 insertions; `git diff origin/main...HEAD --stat`):
the integration suite for Automation Flows, running the engine's `/automation-flows`
router against a wiremock fake n8n (file header at `tests/automation_flows_test.rs:5-6`).
My range covers five groups:

1. **Deletion / switch-off (3062–3255).** Idle delete asks n8n once and unpublishes
   before deleting (3062–3084); active delete waits for the in-flight email, then
   unpublish→delete in that order with nothing orphaned (3119–3143); a run still
   processing at the deadline returns 409 `flow_running` and leaves n8n and the local
   store byte-identical (3146–3166); a flow n8n already lost is still cleared locally,
   and a second delete is 404 (3169–3187); archived flows delete for good (3190–3205);
   chat deletion works with the shared local API key alone, and is refused without
   JSON content-type (3208–3237); an unrelated n8n workflow is never deleted (3240–3255).
2. **Node catalog lookup (3261–3512).** `/nodes` search (ranking, 20-entry cap +
   total, switched-off flagging, empty-query 400), `/nodes/card` (operation-narrowed
   fields + skeleton, hidden fields without an operation, n8n credential presence
   none/one/several, switched-off and invented types), plus the round-trip proof that
   a node built from the card's skeleton passes the flow check (3470–3491) and that
   lookup requires the local API key (3494–3512).
3. **Error workflow (D16) installation (3519–3651).** An installed-but-unpublished
   error workflow is published before a flow names it, switching no flow on
   (3519–3549); n8n refusing to publish still creates the flow without the
   `errorWorkflow` setting (3552–3574); one error workflow serves all flows, is never
   listed as a flow, posts back to `host.docker.internal:3030/…/failures` with the
   `screenpipeApi` credential, and a chat edit that drops the setting gets it
   re-added (3577–3651).
4. **Failure notifications (3655–3830).** The `POST /:id/failures` route: a failed
   run becomes one notification carrying sender, subject, failing step and error,
   the `screenpipe://flows/{id}` deeplink and a Retry API action, id
   `automation-flow-failure:{flow}:{run}`; the flow stays active and nothing is
   written to n8n (3705–3768); a failing trigger (no execution) notifies without a
   Retry action (3771–3800); runs of other flows, missing runs and unknown flows all
   404 without notifying (3803–3830).
5. **Activity / evidence (D18) (3837–4068).** `GET /:id/activity` derives per-run
   outcome from n8n run data: ticket with the created key + AI reason (3899–3952),
   abstained on low confidence (3955–3993), ignored on high-confidence "none"
   (3996–4030), and newest-first ordering that excludes running executions and other
   flows' runs and explains failed runs (4033–4086, tail just past the slice edge).

## How it fits the PR

This file is the executable contract for the engine half of Automation Flows
(`crates/screenpipe-engine/src/automation_flows.rs` + `automation_flows/{failures,
activity,retry,health}.rs`). The harness (`App`, 520–705) builds a real `SCServer`
router with an in-memory DB, a fake notification server (`/notify`, 595–606), and a
scaled-down `RunningWait` (590–593); the fake n8n models n8n 2.x semantics faithfully
(version-on-edit, publish/unpublish, orphaned executions on unpublish-while-running
384–400, retry rules 412–450). Assertions check both HTTP responses and what the fake
n8n now holds or received — the right level for this suite. It also encodes the
binding design rules from `README.md:155-176` (nothing runs without the user, n8n as
source of truth, credentials never to the AI).

## Notable risks / quality issues

- **P2 — trigger-failure notifications are never deduped.** With `executionId: null`
  the notice id embeds a millisecond timestamp
  (`src/automation_flows/failures.rs:253-255`), and the health ledger is keyed on
  execution ids only (`src/automation_flows/health.rs:232`, `:405`), so the same
  failing trigger notifies on every occurrence — the demo's Gmail trigger polls every
  5 s (commit 1955e12b8), so bad credentials could mean a notification every 5 s. The
  slice's test pins the no-Retry action but not the id; the once-only comment at
  3754–3755 holds only for runs. Posted as a review comment.
- **P2 — the notification/evidence routes are only tested with local API auth off.**
  All of 3655–4068 uses `App::new()`/`app.call` (no `Authorization`); production
  enables `api_auth`, `/:id/failures` is not exempt (`src/server.rs:365-376`), and the
  error workflow authenticates via the `screenpipeApi` credential's Bearer header
  (`packages/n8n-nodes-screenpipe/credentials/ScreenPipeApi.credentials.ts:33-36`,
  wired at `failures.rs:88-89`). The file has auth-on tests for delete (3208) and
  lookup (3494) but not for the n8n callback or `/activity` — a header drift would
  kill all failure notifications with every test green. Posted as a review comment.
- **P3 — activity extraction is demo-shaped and tie ordering is untested.** Outcome
  logic keys on `output` objects, `confidence`, and Jira's `{key, self}`/`{issues}`
  shapes (`src/automation_flows/activity.rs:110-131`, `:181-196`); fixtures always use
  distinct `startTime`s, whereas `handled_email` (`failures.rs:296-299`) and
  `output_items` (`activity.rs:167-170`) break ties by serde map order (BTreeMap —
  alphabetical by node name, since `preserve_order` is not enabled). Benign for the
  demo (both AI-shaped items carry the same answer) but unpinned for custom flows.
- **Design note (not posted):** delete needs only the shared local API key
  (3208–3237), i.e. any pipe/MCP client can irreversibly delete flows (n8n DELETE
  removes for good, fake comment 343–345), while activate/deactivate/retry are
  UI-credential gated (1917–1974). This is deliberate — the chat skill deletes flows,
  and `automation_flows.rs:1533` documents switch-off as "always safe" — but it is the
  least-gated destructive operation in the suite, worth the lead reviewer knowing.
- What I could not check: I did not run the fake n8n against real n8n 2.x, nor the
  desktop-app side of notification handling (`lib/notifications/actions.ts` — another
  reviewer's slice); the cross-host click-through contract (Retry action → retry
  route) is asserted here only as JSON shape (3744–3753).
