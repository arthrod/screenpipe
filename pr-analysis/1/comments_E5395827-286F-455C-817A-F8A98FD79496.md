## Review of `docs/automation-flows/history/flows-round-two/` (issues 13–17 + coverage.md)

Verified before writing this: all 36 files the slice references exist; all 128 explicit test identifiers in these docs map to real tests; and I ran the scoped suites at HEAD — `cargo test -p screenpipe-engine --test automation_flows_test` (107 passed, 0 failed), `cargo test -p screenpipe-engine --lib automation_flows` (5 passed), `bun test infra/automation-flows` (65 pass), `cd packages/n8n-nodes-screenpipe && bun test` (56 pass). The engine side of the docs' claims is solid. The findings below are where the docs no longer match the code they describe.

---

**[P2] `docs/automation-flows/history/flows-round-two/coverage.md:153` — this row cites tests that commit 1955e12b8 deleted later in this same PR.** The row maps "IMAP trigger: unread only, marks read (the dedupe); catches up after a pause" to W tests « reads unread emails of the support inbox and marks them read; every activation catches up the unread emails ». `git log -S` shows those tests were removed by 1955e12b8 ("flows: Gmail Trigger every 5 s, fast English AI ticket, ScreenPipe notify node", PR-only, 2026-10-18 14:30 — three hours after coverage.md was committed in 754fbfbfa at 11:06, never updated since). The current file instead has "polls the support inbox through Gmail every 5 seconds and takes each new email, read or unread" (`infra/automation-flows/workflows/novadesk-support-tickets.test.ts:76`) and the workflow now uses `n8n-nodes-base.gmailTrigger` (workflow JSON line 9). The trigger feature is still tested, but under a different design and different names, so the row's premise — the matrix names the test that covers the feature — no longer holds at HEAD.

**[P2] `docs/automation-flows/history/flows-round-two/coverage.md:155` — same problem for the 27-38 row: the demo AI agent no longer has ScreenPipe tools.** The row maps "ScreenPipe history search and activity summary tools, limited to Jira screen text" to W tests « the AI Agent's tools are ScreenPipe's history search and activity summary…; an email cannot widen what the ScreenPipe tool reads… », both deleted by 1955e12b8. The current contract test asserts the opposite design: "the AI Agent has no tools: it judges the email alone" (`novadesk-support-tickets.test.ts:159`). Ticket 27's user story 38 still describes the tools design, so this row (and story 38 itself) needs a supersession note or an update — a reader auditing "every feature has a test" is pointed at tests that assert the feature was removed.

**[P2] `docs/automation-flows/history/flows-round-two/issues/13-flow-activity.md:22` — the quoted failure wording does not exist anywhere in the repo; the shipped strings are English.** The doc says the failed reason is « Échec à l'étape « … » : … »; the code produces `Failed at step “{step}”: {error}` (`crates/screenpipe-engine/src/automation_flows/activity.rs:151`, same wording as D16 at `failures.rs:247` — that half of the claim is true). The mock at lines 42–50 has the same problem: the labels are « Échec », « À trier à la main », « Ignoré · Ticket NOVA-28 créé », « Activité », while the app renders "Failed" / "Sort by hand" / "Ignored" / "Ticket … created" (`components/automation-flows/labels.ts:56-69`) under an "Activity" header (`flow-activity.tsx:53`). A `rg` for these French strings over crates/infra/packages/apps returns nothing. Since this doc's live check (lines 61–64) tells the operator to look for « Ticket NOVA-n créé », « Ignoré », « À trier à la main », following it verbatim fails. Please either quote the shipped English strings or note that the French is the spec-era naming.

**[P2] `docs/automation-flows/history/flows-round-two/issues/14-flow-health-check.md:54` — same French-vs-English drift, three instances.** The banner is quoted as « n8n injoignable, tes Flows ne tournent pas » (lines 3, 54–55 and the mock at 62), but the shipped banner is "n8n is unreachable: your Flows are not running" (`health-banner.tsx:16`); the live check's « Échec du Flow … » notification (line 76) is `Flow “{flow_name}” failed` in `failures.rs:279`. The banner mock and the live-check step 3 will not match what the built app shows. Everything else in this doc matched `health.rs` closely in my comparison — these strings are the outliers.

**[P2] `docs/automation-flows/history/flows-round-two/issues/14-flow-health-check.md:42` — "the first check looks 24 h back" is contradicted by the code and by a passing test.** `health.rs:173-178` bounds the first check at engine start (`since()` = last ledger check, else `started_at`), and the module doc says so explicitly (`health.rs:22-24`: "never at older ones"). The integration test `the_very_first_check_does_not_notify_runs_from_before_the_engine_started` passes in my run of `cargo test -p screenpipe-engine --test automation_flows_test` (107 passed, 0 failed). The 24 h constant in `health.rs:31` is only the ledger retention window, not a lookback. The shipped behavior is more conservative than documented (no burst of old failures), but the doc records a behavior that does not exist — and the same wrong note was copied into `docs/automation-flows/history/hackathon/SPEC.md:125`.

**[P2] `docs/automation-flows/history/flows-round-two/issues/15-spec-feature-coverage.md:41` — "All suites pass" for the app vitest suites is timezone-dependent: the automation-flows suite fails outside UTC-forward timezones.** I ran the scoped command `bunx vitest run --config vitest.config.ts components/automation-flows` (the config fix from this ticket worked — no `NODE_OPTIONS` needed): 1 failed, 122 passed, reproducibly. The failure is `flows-tab.test.tsx:790` expecting `/Oct 17, .+ · Gmail, Jira$/` from fixture `2026-10-17T02:05:41Z` (line 778) — `formatDate` (`labels.ts:38-44`) formats in local time with no `timeZone` option, so at UTC-4 the strip correctly renders "Oct 16" and the assertion fails. I proved the diagnosis: the same test passes under `TZ=UTC` and fails under the machine's `TZ=EDT`. Either pin the assertion (format in a fixed TZ in the test, or pass `timeZone: "UTC"` in `formatDate`) or the PR's "every listed test passes" claim only holds in part of the world.

**[P3] `docs/automation-flows/history/flows-round-two/issues/13-flow-activity.md:20` — the activity payload shape omits `retried`.** `FlowRun` also serializes `retried` (`activity.rs:28`, set at lines 71 and 104), and the Review Screen consumes it for the Retry affordance (`flow-activity.tsx:103`). The doc's integration note (lines 56–57) anticipates ticket 12 adding retry UI, so this is drift rather than error — but the shape list is what an implementer would code against.

**[P3] `docs/automation-flows/history/flows-round-two/issues/14-flow-health-check.md:38` — "every 30 s while … a failed run could not be handed to the notification server" oversimplifies.** For the unreachable case the wait is a fixed 30 s, but for undelivered notifications the wait starts at 30 s and doubles on each miss, capped at 15 min (`health.rs:44-47` and `Pacing::next_delay`, lines 81–87). The doc's own schedule test (`health.rs:459`) only pins the unreachable case. Worth one clause of correction so the recorded cadence matches the code.

**[P3] `docs/automation-flows/history/flows-round-two/issues/16-full-live-check.md:9` — the ticket does not record that a live check already ran, and names no evidence file.** Ticket 17 was "Found: live check (ticket 16), 2026-10-18 09:00" and its fix landed at 14:15 the same day (`bcb3e74c0`, verified in HEAD), yet ticket 16 is still "ready-for-agent" with all boxes unchecked and no note of the partial run — an agent picking this up cannot tell which steps were already exercised on 10-18 or that ticket 17's fix needs re-verifying as part of the run. Also, line 11 says results go "in the evidence file" without naming a path, and `flows-round-two/` contains no evidence-file convention to inherit. Suggest a one-line history note and a concrete path before handing this to an agent.
