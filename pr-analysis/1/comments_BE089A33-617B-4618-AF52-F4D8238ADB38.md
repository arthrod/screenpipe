**[P3] `infra/automation-flows/workflows/novadesk-support-tickets.test.ts:520-529` — a 32-bit label collision silently drops an email**

The duplicate-safety key is `mail-` + the first 8 hex of an FNV-1a **32-bit** hash (pinned at :522 with the published "foobar" vector — nice). If two different emails ever collide on those 32 bits, the second email's dedupe search finds the first one's ticket, the "Ticket already created?" branch takes its yes-output — which goes nowhere (:570) — and the run ends **successfully**: no ticket, no « Sort by hand » notification, no trace. Every other no-ticket path in this Flow is visible (abstention notifies, gate failures fail loudly), so this is the one silent-loss path, and the tests pin it without acknowledging it. At demo scale the odds are negligible (~N²/2³³ — about one in a million for a thousand-email inbox), so I don't think this blocks; but since this suite is the spec, either spend a few more hex characters (Jira labels accept long values; it's a one-expression change in both `jsonBody` nodes) or add a sentence to the workflow notes / review summary saying the hash is 32-bit and a collision is an accepted, silent drop.
