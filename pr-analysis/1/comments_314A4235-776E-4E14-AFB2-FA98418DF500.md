## Review — `infra/automation-flows/n8n-catalog.ts` and `n8n-catalog.test.ts`

Focus: parsing robustness of the catalog generator against malformed n8n
exports, and whether the tests pin the node-type extraction rules. Findings
below were verified by running the code (probes cited inline), not by reading
alone.

---

**[`infra/automation-flows/n8n-catalog.ts:109` — P2 robustness] A malformed `version` poisons the committed catalog silently and panics the engine far from the cause.**

`versions: [description.version].flat()` trusts the export. Probing the exported functions directly (`bun -e`): a description with no `version` writes `versions: [null]` into `n8n-catalog.json` (`JSON.stringify` turns the `undefined` into `null`) while the generator exits 0 and prints its success line; `version: null` makes `latest()` (`n8n-catalog.ts:124`) coerce to `0`; `version: []` yields `versions: []` and `latest()` = `-Infinity`. The engine `include_str!`s this file and runs `serde_json::from_str(...).expect("n8n-catalog.json is valid")` with `versions: Vec<f64>` (`crates/screenpipe-engine/src/flow_checks.rs:39,76`), so one malformed entry among hundreds panics the engine at first check use — the worst place to learn about a generation-time problem, given this file is the trust anchor for "refuses a Flow with an invented, disabled or incomplete node". Today's inputs (n8n's shipped `nodes.json`, this repo's own node classes) are well-formed, so this is future-proofing, but it is cheap: reject any entry whose version is not a finite number in `group()`/`add()` and the failure becomes loud where it happens.

**[`infra/automation-flows/n8n-catalog.test.ts:20` — P2 tests] The suite validates committed artifacts more than it pins the extraction rules its header claims to pin.**

Seven of the nine tests parse the committed `n8n-catalog.json` / `n8n-nodes.json.gz`, so a regression in the generator's parsing passes everything until someone happens to regenerate. The one true code-level pin — the `CUSTOM.*` round-trip at `n8n-catalog.test.ts:92-104` — covers only four simple types. The core extraction logic has no synthetic tests: `versionAllows` (`n8n-catalog.ts:134-154`, scalar-vs-array `version`, each `_cnd` op `eq`/`not`/`gte`/`lte`/`gt`/`lt`/`between`, the documented unknown-op fail-open) and `group()`'s transitive closure (`n8n-catalog.ts:90-96`, credential-rule seeding and multi-hop "a rule reads a param whose own rules read another") are exercised only incidentally by whatever the current pinned image contains. `group`, `detail` and `indexEntry` are exported, so a small table-driven `describe` with synthetic descriptions would pin exactly the rules the file header says are pinned, independent of the image.

**[`infra/automation-flows/n8n-catalog.ts:242` — P3 robustness] The two-package prefix heuristic silently mislabels any unexpected `nodes.json`.**

Every `dist/types/nodes.json` found under `.pnpm` whose path lacks `n8n-nodes-langchain` is prefixed `n8n-nodes-base.` (`n8n-catalog.ts:247`). If a future n8n image ships a third nodes package (a split, a vendored community package), its types are registered under the wrong prefix and the check layer will then refuse those nodes' real `n8n-nodes-<pkg>.<name>` type strings — a confusing "unknown node" failure rooted in a silent generation-time guess. The pin test (`n8n-catalog.test.ts:21-25`) guards the image version but not this mapping; failing or warning loudly when `find` returns a path that maps to neither known package would keep the guess honest.

**[`infra/automation-flows/n8n-catalog.ts:151` — P3 robustness] `versionAllows` fails in opposite directions for two kinds of malformed `@version` input.**

An unknown `_cnd` operator keeps the parameter (documented fail-open, `n8n-catalog.ts:133`), but a type-mismatched plain value silently drops it: probed with `show: {"@version": ["3"]}` against version 3, `holds` does `allowed === version`, fails, and the parameter vanishes from the card with no warning. Two different failure directions for two flavors of the same malformed input means a future n8n change could quietly empty a node's card while another equally odd change is fine. Consistency here is cheap: coerce or reject non-numeric `@version` values the same way unknown conditions are handled, and say which in the doc comment.

**[`infra/automation-flows/n8n-catalog.ts:230` — P3 robustness] `screenpipeTypes()` assumes every entry under `nodes/` is a well-formed node package.**

`readdirSync(customDir)` treats every entry as a node directory and then requires `<dir>/<dir>.node.ts` to exist and export a class named exactly `dir` (`n8n-catalog.ts:231-233`). A stray file (`.DS_Store`) or a shared `common/` helpers directory added later crashes the generator with a bare resolver error or `module[dir] is not a constructor` instead of naming the offending entry. No live bug today — the directory holds exactly `ScreenPipe`, `ScreenPipeAiTrigger`, `ScreenPipeTrigger` — but `readdirSync(..., { withFileTypes: true })` plus an error that names the entry makes the next addition self-diagnosing.
