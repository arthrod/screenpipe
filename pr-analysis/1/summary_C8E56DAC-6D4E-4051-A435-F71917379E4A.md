# Slice review: demo shortcut listener (PR #1)

Slice: `apps/screenpipe-app-tauri/components/automation-flows/demo-shortcut-listener.tsx` (new, 42 lines) and `apps/screenpipe-app-tauri/components/automation-flows/__tests__/demo-shortcut-listener.test.tsx` (new, 82 lines). Both are wholly new in this PR (`git diff origin/main...HEAD --stat` = 124 insertions, 0 deletions).

## What the slice does

`DemoShortcutListener` is the frontend end of the hidden demo shortcut ⌃⌥⌘D. The chord itself is captured natively by the global-shortcut plugin in `apps/screenpipe-app-tauri/src-tauri/src/shortcuts.rs` (`DEMO_SHORTCUT` at shortcuts.rs:24), which emits `DEMO_SHORTCUT_EVENT` with `app.emit_to("home", ...)` (shortcuts.rs:34, and shortcuts.rs:50 after re-opening a destroyed Home with a fixed 3 s sleep). The component (mounted in every non-overlay window, `app/providers.tsx:200`) listens for that event on its own window and runs `demoShortcutHandler` from `lib/automation-flows/demo-shortcut.ts:34` — the reset → find-automation → notify → Task Page demo sequence. On handler rejection it surfaces a destructive "Demo not started" toast (demo-shortcut-listener.tsx:37); `tell` also brings the Home window to front before toasting (demo-shortcut-listener.tsx:27).

## How it fits the whole PR

It is the in-app trigger for the hackathon demo path that the rest of the PR builds (DEMO.md runbook, demo task catalog, `resetDemoFlows`, notification deep link). It complements the native registration in `shortcuts.rs` (a different reviewer's slice; coderabbitai already flagged that the chord is registered unconditionally in production builds at shortcuts.rs:527-536 — I am not duplicating that).

## Key design decision — window-scoped listen, and why it is correct

The component deliberately uses `getCurrentWebviewWindow().listen(...)` (window-scoped, target `WebviewWindow{label}`) instead of the global `listen` (target `Any`), and documents why at demo-shortcut-listener.tsx:6-10: Tauri v2 delivers an `emit_to("home")` to every `Any`-target listener in every webview, so a global listener would run the demo once per open window. I verified this matches Tauri v2's `emit_filter`/`match_any_or_filter` dispatch rule by reading (target `Any` matches all events; label targets match only equal labels). I could not execute this against a real Tauri runtime in vitest — it is verified by reading only. The test encodes the same rule in a fake bus (test:8-23) whose comment cites the real function.

## Assessment against the slice focus

- "Keyboard event handling": there is no DOM keyboard handling in this slice — keys never reach this layer; the component consumes a Tauri event. That is the correct boundary, so there is nothing to review for keydown semantics. The test therefore simulates the event-bus dispatch (with the Tauri matching rule), not real key sequences — appropriate, but stated plainly because the ask phrased it as "real key sequences".
- "Cleanup on unmount / no global listener leaks": the component's cleanup is the correct async-safe pattern — the `unlisten` promise is captured in the effect disposer, so even an unmount before the listener finishes registering still removes it (demo-shortcut-listener.tsx:39). No global listener is created; the only listener is window-scoped. The effect's `[toast]` dependency is stable in the real app (module-level function, `components/ui/use-toast.ts:147`, returned at use-toast.ts:191), so there is no re-register churn.
- Test quality: the once-per-window guarantee (the bug the scoping exists to prevent) IS covered — test:71-75 (home receives it) and test:77-81 (settings ignores `emit_to("home")`). **Teardown is NOT asserted anywhere** — the explicit focus of my slice's test file. See posted comment 1 (P2).

## Notable risks / quality issues

1. **P2 — no teardown test.** The cleanup at demo-shortcut-listener.tsx:39 is completely untested; a regression (effect returning nothing, or a broken unlisten) would pass the suite. Posted.
2. **P3 — error path and mock guard untested.** The mocked `press` never rejects (test:44), so the `press().catch` → "Demo not started" toast path (component:37) is untested; the `NEXT_PUBLIC_SCREENPIPE_WEB_DEV === "mock"` early return (component:23) is also untested. Posted as one comment.
3. Minor, not posted: cleanup swallows unlisten failures with `.catch(() => {})` (component:39) — a teardown failure would be silent. Defensible for a disposer, but a leaked listener would keep a stale `press` closure (with captured deps) alive and could still run the demo from an unmounted subtree.
4. Minor, not posted: the fake bus's `emitTo` iterates the listener array while a handler could mutate it (splice during iteration); harmless in these tests, slight fidelity gap vs the real bus.
5. Cross-slice, out of my files: when Home is missing, the native side re-emits after a fixed 3 s sleep (shortcuts.rs:50); a slower-mounting webview misses the press. Left to the shortcuts.rs reviewer.
