Review of the Flows list state machine and shared components (`flows-tab.tsx`, `common.tsx`). Nothing invented from the API, the race handling in `useFlowsLoad` is sound, and the list/empty/error states are well tested — findings below, none blocking.

**[P2] `apps/screenpipe-app-tauri/components/automation-flows/__tests__/flows-tab.test.tsx:790` — timezone-sensitive assertion fails west of UTC-3.**
The fixture stamps the captures at `2026-10-17T02:05:41Z` (line 777) and the assertion demands `/Oct 17, .+ · Gmail, Jira$/`, but 02:05Z is already Oct 16 in any timezone of UTC-3 or further west. I ran the file: `bun run test:vitest components/automation-flows/__tests__/flows-tab.test.tsx` fails on this machine (EDT): 1 failed | 69 passed, and passes with `TZ=UTC`: 70/70. The sibling test at line 280-281 deliberately picks `09:05:00.000Z` and comments "any time zone from UTC-9 to UTC+14" — this one forgot the constraint. CI (UTC) stays green, so local runs for roughly half the world's timezones break silently. Use a mid-day UTC timestamp here like the sibling test does.

**[P2] `apps/screenpipe-app-tauri/components/automation-flows/flows-tab.tsx:90-94` — delete/restore reloads the whole list through "loading".**
`onDeleted={reload}` and `onRestore`'s `reload()` trigger a foreground read, which sets the whole hook to `loading` (common.tsx:56), so deleting or restoring one row replaces the entire tab — groups, scroll position, and every *other* row's open Delete confirmation (flow-delete.tsx:32) — with "Loading the Flows…" for a round-trip. Worse, if that post-action `list()` call fails (an n8n blip at the wrong moment), a delete that actually succeeded renders as the full error screen, telling the user their action failed. `useFlowsLoad.replace` (common.tsx:101-108) exists precisely to "show fresher data already in hand without going back through loading", and `api.restore` already returns the restored `Flow` (api.ts:362-368) which line 92 discards — the list could drop the deleted id / swap the restored flow in place instead.

**[P3] `apps/screenpipe-app-tauri/components/automation-flows/flows-tab.tsx:158-167` — `RestoreButton` never clears `busy` on success.**
`setBusy(false)` runs only in the `catch` branch; on success the button stays disabled. It works today only by accident: a successful restore triggers `reload()` (lines 91-94), which unmounts the row. If `onRestore` ever resolves without the row unmounting (server confirms but the reload result is dropped by the stale-read guard, common.tsx:57-60), the Restore button is permanently dead. Use `finally { setBusy(false) }` like `OpenButton` does (common.tsx:209-211).

**[P3] `apps/screenpipe-app-tauri/components/automation-flows/common.tsx:277-282` — generic error titles are written for the list, but the component also serves the single-Flow Review Screen.**
`FlowsErrorMessage` is rendered by `flow-review.tsx:61` for exactly one Flow, where the fallback reads "The Flows could not be loaded" (plural). The reverse also mismatches: a `not_found` on the list route (e.g. an older engine without the route) is titled "This Flow no longer exists in n8n" on a screen showing no specific Flow. Worth parameterizing the two titles (or taking an optional `subject: "Flow" | "Flows"` prop) so each screen says the right noun.

**[P3] `apps/screenpipe-app-tauri/components/automation-flows/common.tsx:251` — "Open Connections" fails silently.**
`onClick={() => void api.openN8nConnection()}` (also line 267) discards rejections: `openN8nConnection` awaits Tauri's `emit` (api.ts:420-422), which can reject, and then the user clicks and nothing happens with no message — inconsistent with `OpenButton`, which catches and shows a `role="alert"` (common.tsx:202-212, 225-229). Routing it through `OpenButton` (or catching locally) would give the same failure feedback as every other button on these screens.

**[P3] `apps/screenpipe-app-tauri/components/automation-flows/common.tsx:44-45` — `useFlowsLoad` is fragile to a render-phase ref write and a synchronously-throwing `load`.**
`loadRef.current = load` mutates a ref during render, so a discarded concurrent render can leave the ref holding a closure for data that was never committed — the next focus/interval refresh (common.tsx:86-98) would then fetch for the wrong screen. And `run` calls `loadRef.current()` unguarded (common.tsx:61): a load that throws *synchronously* would propagate out of the effect/interval tick and leave `pending.current` set forever, permanently blocking all future background reads via the guard at common.tsx:53. All three current call sites are async functions (flows-tab.tsx:48, health-banner.tsx:20, flow-review.tsx:43), so this is latent — but `Promise.resolve().then(loadRef.current)` plus assigning the ref in an effect would close both holes cheaply.
