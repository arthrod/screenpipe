## Notable risks and quality issues

1. **Buffered relay is intentional but worth the lead reviewer knowing** (`:14-17` doc, `:509-510`).
   A `stream: true` caller receives zero bytes until the entire Codex generation finishes; the
   whole answer then arrives as a single delta chunk. Client read-timeouts must therefore exceed
   full generation time. This is documented design, and the caller-stall consequence overlaps the
   already-posted coderabbit timeout finding at `:152-160`, so I did not post a duplicate comment.
2. **Second-half quality is good.** `finish_reason`/usage/`created` mapping is faithful
   (`:469-507`); error statuses pass through so 429/401 surface as such (`:184-192`); the
   char-safe 300-char clip in `upstream_message` is panic-free; the token is only ever sent to
   `https://chatgpt.com` (`:32`, `:152-160`) and never logged (`:164`, `:176`, `:186` log status
   and upstream message only). `account_id()` decodes the JWT payload without signature
   verification (`:114-127`), which is fine: the token is itself the credential, and the claim
   only populates the `chatgpt-account-id` header.
3. **Token/cookie handling in this slice** reduces to the test-side JWT construction and the
   account-id claim tests (`:586-596`, `:696-700`); the actual token read/refresh lives in the
   first half and in `screenpipe-core` (`pipes/mod.rs:1697-1756`). No cookies are handled in this
   file. I did not review the core token reader beyond confirming it exists and is called via
   `spawn_blocking` (`:78-82`).
4. **Test gaps in the slice (posted as a P3 comment)**: streamed tool-call delta `index`
   insertion (`:523-534`) is untested — the streaming test (`:838-866`) covers text only and the
   tool-call test (`:798-821`) is non-streaming; `response.incomplete` → `length`/`content_filter`
   mapping (`:473-481`) has no test; `upstream_message`'s raw-body fallback (`:558-562`) has no test.
5. **Route exposure context (pre-existing pattern, not new to this file)**: the route inherits the
   engine API-auth middleware (`crates/screenpipe-engine/src/server.rs:1612-1712`); `api_auth`
   defaults to false (`:424`), so any local process can spend the user's ChatGPT quota through
   this proxy — the same trust boundary the pre-existing cloud proxy already exposes.
6. Minor, not posted: `error()` sets `type` to a machine code rather than an OpenAI error class
   like `invalid_request_error` (`:567`) — speculative client impact, and `upstream_message` can
   echo CDN/HTML noise from a non-JSON error body, bounded to 300 chars (`:558-562`).
