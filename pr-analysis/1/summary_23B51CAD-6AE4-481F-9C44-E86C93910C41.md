# Slice review: automation-flows agent-facing skill (SKILL.md + n8n-guide.md)

PR #1 (arthrod/screenpipe), diff base `origin/main`. Slice: the two new files under
`crates/screenpipe-core/assets/skills/automation-flows/` — both are entirely new in this PR
(`git diff origin/main...HEAD --stat`: 341 + 229 insertions, 0 deletions).

## What this slice is and how it fits the PR

These two markdown files are the instructions the ScreenPipe chat agent follows to list, build,
change and delete Automation Flows through the `/automation-flows` API:

- `SKILL.md` — rules (never activate, one sentence per node, lookup before building, no invented
  nodes, no credential writing), the API table with error codes, the node-lookup/card protocol,
  the change/create/draft/delete walkthroughs, and one worked example on the NovaDesk demo Flow
  (SKILL.md:175-183).
- `n8n-guide.md` — an n8n authoring primer (expressions, item routing, IF/Switch/Merge shapes,
  error settings, LangChain AI sub-node wiring, `$fromAI`), plus three complete example Flow
  bodies that the guide claims are accepted as-is by ScreenPipe (n8n-guide.md:130-131).

The files ship as embedded assets of `screenpipe-core` and are surfaced to the chat agent by
`crates/screenpipe-core/src/agents/pi.rs` (also in this PR); the guide's example bodies are
compiled into `crates/screenpipe-engine/tests/automation_flows_test.rs` via
`include_str!` (tests/automation_flows_test.rs:2586). So these are executable documentation in a
real sense: wrong instructions propagate straight into agent behavior, which is the slice's focus.

## Findings

### P1 — SKILL.md:179 — worked example misquotes the NovaDesk demo workflow

SKILL.md:177-180 says the node « Create the Jira ticket » (`httpRequest`) "builds the Jira issue in
`parameters.jsonBody`, which holds `labels: [ $json.output.label ]`. Change it to
`labels: [ $json.output.label, 'auto' ]`". In the shipped demo workflow
(`infra/automation-flows/workflows/novadesk-support-tickets.json`, node "Create the Jira ticket")
the jsonBody holds `labels: [ o.label, (e => 'mail-' + …FNV hash…)(($('New support email').item.json)) ]`
— `o` is a local binding for the parsed AI answer inside the same expression, and there are **zero**
occurrences of `$json.output.label` in the whole file (checked by parsing the JSON). The second
label is a per-email dedup key that must survive the edit. An agent following the example cannot
find the quoted expression and may "edit" the wrong thing or retype the JSON (which rule 3/SKILL.md:157
forbids). Fix: quote the real expression and say to append `'auto'` to that array.

### P2 — SKILL.md:81 — status enumeration omits `dismissed`

SKILL.md:81-82 says "`status` is `draft` (never activated), `active`, `paused` or `needs_review`".
`derive_status` (crates/screenpipe-engine/src/automation_flows.rs) also returns `"dismissed"` when
the user set the Flow aside (`record.dismissed`), and the router exposes `POST /:id/dismiss` and
`/:id/restore` (automation_flows.rs:298-299). A dismissed Flow is listed by `GET /automation-flows`
with a status the skill claims cannot exist, so an agent identifying a Flow for the user (delete,
SKILL.md:330) can misreport it.

## Quality assessment

Overall this is unusually careful agent-facing documentation: the lookup-before-build protocol is
backed by the same catalog the checker enforces (n8n_nodes.rs header, flow_checks), the guardrails
(rules 1, 4, 5, 7, 8) match real engine behavior, and the examples are machine-checked. The two
findings above are the only inaccuracies I could find against shipped code.

## Not verified / limits

- I did not run the real n8n container; runtime n8n semantics (e.g. whether n8n's scheduler accepts
  `pollTimes` on the custom trigger at runtime) rest on the convention seen in n8n-owned polling
  trigger cards and the engine's fake-n8n test, not on a live n8n run.
- Switch `options.fallbackOutput` value `"extra"` (n8n-guide.md:68): the card lists the field but
  its `options` array is empty (n8n builds the choices dynamically), so I confirmed the field
  exists but not the `extra` value against a card; it matches upstream n8n behavior, which I did
  not execute.
- The draft-state `nodes[].complete` field (SKILL.md:294) comes from `check_draft`/`inspect`
  output; I read the handler and `NodeReport` (`missing`, `credentials`, `invention`) but did not
  trace every serialized field name to its assertion.
