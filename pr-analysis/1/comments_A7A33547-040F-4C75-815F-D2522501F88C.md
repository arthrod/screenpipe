## Review: app-origin blocking rule in the owned browser (`owned_browser.rs`)

Reviewed the 139 added lines: `is_app_origin` (owned_browser.rs:1609-1627), its enforcement in `on_navigation` (owned_browser.rs:584-594) and `normalize_url` (owned_browser.rs:1592-1597), and the 6 new tests. The rule itself is well built — scheme/host truth table covers case, trailing dot, ports, the Windows `*.localhost` hosts, and `blob:` recursion; it's enforced on both the agent-request path and the page-driven path; and the `tauri.conf.json` devUrl tie-in test (owned_browser.rs:1744) is exactly the right drift guard. Three findings:

**[P1] `apps/screenpipe-app-tauri/src-tauri/src/owned_browser.rs:587` — On Windows the rule never sees subframe navigations, so an iframe can still load the app.**

wry 0.55.1 (the version in `src-tauri/Cargo.lock`) maps `on_navigation` to WebView2's `add_NavigationStarting` and never registers `FrameNavigationStarting` (verified in `wry-0.55.1/src/webview2/mod.rs:674-698`; `FrameNavigationStarting` occurs 0 times in that file). `NavigationStarting` fires for main-document navigations only, so on Windows a visited page can embed `<iframe src="http://tauri.localhost/">` (or `asset.localhost` / `ipc.localhost`) and the check at this line never runs for that frame. That frame is not inert: Tauri's IPC init script runs in child frames on WebView2 (Microsoft's `AddScriptToExecuteOnDocumentCreated` docs: it "runs on all top-level document and child frame page navigations"), and `capabilities/main.json` grants `"windows": ["*"]` with `local: true` — including `fs:allow-read-file` over `$HOME/**`, the `shell:allow-execute` screenpipe sidecar with `args: true`, and `http:default` for all URLs — to every webview label, so an app page there plausibly gets real IPC, which is precisely the ticket-20 outcome this rule exists to prevent. Honest caveat: whether the child frame's invoke actually reaches tauri's `on_message`, and with a frame-derived origin (tauri 2.11.2 `src/webview/mod.rs:1743` trusts `request.url` from the IPC transport), I could not exercise from macOS — please verify on Windows. Suggested two-part fix: (1) enforce the rule at frame level too (upstream wry `FrameNavigationStarting`, or deny app hosts in a `FrameCreated` handler), and (2) structurally, scope the sensitive capabilities to the real app window labels instead of `"*"`, so an app page inside any foreign webview gets nothing even if it loads. For contrast, macOS is covered (your own comment at owned_browser.rs:595-597 cites wry#1593 — `on_navigation` sees iframe targets there) and `window.open` is denied by default on WebView2 (wry webview2/mod.rs:786 `SetHandled(true)` when no handler is set), so top-level and popup paths are closed; Windows subframes are the remaining hole.

**[P3] `apps/screenpipe-app-tauri/src-tauri/src/owned_browser.rs:1620` — dev-server block misses IPv4-mapped IPv6 loopback spellings.**

`LOOPBACK` is `["localhost", "127.0.0.1", "[::1]"]`, but a host like `[::ffff:127.0.0.1]` canonicalizes to the IPv4-mapped form (`[::ffff:7f00:1]` per WHATWG serialization; the `url` crate keeps the mixed `::ffff:` notation) and matches neither entry, so `http://[::ffff:127.0.0.1]:1420/` reaches the dev server and loads the dev app inside the agent browser on dev builds. Exposure is dev-only (release builds load from `tauri://`), hence P3 — but the fix is cheap: parse the host with `url::Host` and treat any loopback IPv4/IPv6 address (including the whole `::ffff:0:0/96` mapped range) as loopback. For reference, the plain IPv4 shorthand `127.1` already canonicalizes to `127.0.0.1` and is covered.

**[P3] `apps/screenpipe-app-tauri/src-tauri/src/owned_browser.rs:587-594` — a blocked page-initiated navigation is invisible to the user.**

When the agent requests an app URL it gets the clear explanation from `normalize_url` (owned_browser.rs:1592-1597), but when a *page* link or redirect targets the app, the navigation is cancelled here with only a `warn!` in the logs — the user clicks a link and nothing happens, with no indication why. Consider emitting a state event or reusing the sidebar notice channel on this path so the sidebar can say "this link points at the screenpipe app itself and was blocked", mirroring the explanation the error string already gives the agent.
