## Risks / issues found (details in comments file)

1. **P2 — notify tests only exercise the node's happy path.** `notificationFor`'s stub (`test.ts:1100-1104`) always returns HTTP 200 + "Notification sent successfully". The node's unreachable-server branch (`ScreenPipe.node.ts:316-322`), non-2xx branch (323–331), held-back `shown: false` outcome (332), and its `continueOnFail` catch (235–239) are never executed — yet the suite's own failure-semantics claims (abstention must fail the run, `test.ts:287-289`; ticket notification must not, `test.ts:658`) rest on exactly those branches. The stub also discards the request options (`timeout: 5000`, `returnFullResponse`, `ignoreHttpStatusErrors`), so the "a notification must never hold a run" contract (`ScreenPipe.node.ts:18-19`) is unpinned.
2. **P3 — the hostile-notification escape check asserts 7 of the ~17 characters `escapeMarkdown` escapes** (`test.ts:303` vs `ScreenPipe.node.ts:337`); dropping `>`, `_`, `)`, `|`, etc. from the node's set would pass.
3. **P3 — the "short notification" bounds (800/120 chars, `test.ts:325,655-656`) measure the evaluated JSON expression only**, bypassing the node's slice(0,2000)+escape step (`ScreenPipe.node.ts:290`), which can inflate the delivered body to ~4000 chars; the test names promise more than they measure.
4. Harness notes (summary-only): `evaluateIf` treats any unrecognized `combinator` as "and" (`test.ts:993`) — fine today, silently wrong if a future gate typo's it; `evaluate` uses `new Function` but only on the committed fixture (comment at `test.ts:929-930` makes the constraint explicit) — acceptable.
