**P3 (nit, latent)** — `packages/workflows-ui/src/chat-primitives.module.css:29`

Moving the dark `.jumpAnchor` variables from hardcoded hexes to `hsl(var(--border))` / `hsl(var(--foreground))` / `hsl(var(--card))` / `hsl(var(--surface-secondary))` makes the jump-to-latest button's dark mode depend on the host page defining those four tokens. If a future consumer ever renders under a `.dark` class without them, each `--chat-*` becomes invalid at computed-value time and the light-mode fallbacks in `.jump` (`chat-primitives.module.css:24,27`, e.g. `var(--chat-surface, #fff)`) win — producing a white button on a dark background. Today this can't fire: the Tauri app defines all four tokens (`apps/screenpipe-app-tauri/app/globals.css:53,57,49,104` light, `:188,192,184,239` dark), and the package's only other consumer, `apps/screenpipe-workflows-web`, never applies `.dark` at all (its `app/globals.css` is 12 lines, no tokens), so the rule is inert there. Since the same token swap lands package-wide in this PR (`workflow-assistant.module.css:106`, `workflows-app.module.css:837,910-917`), this is a deliberate migration rather than a defect — noting it only because `workflows-view-theme.test.tsx` can't catch the failure mode: it neither resolves `var()` nor injects the tokens (`workflows-view-theme.test.tsx:68-69`), so a token-less dark host would pass it silently. No action required for this PR; worth remembering if a third consumer of `@screenpipe/workflows-ui` ever gets a dark theme.
