## Review — workflows routing slice (`routes/workflows.rs`, `routes/workflow_edits.rs`)

**[P2] `crates/screenpipe-engine/src/routes/workflows.rs:41` — the new consumer enabled by this visibility widening skips the history-access policy this module enforces.**

Widening `read_catalog` from `pub(super)` to `pub(crate)` is the right minimal change and breaks no existing consumer — it exists so `automation_flows.rs` (new in this PR) can read the catalog at `automation_flows.rs:1252` to compute a Detected Task's first-seen moment. But both HTTP handlers in this file deliberately filter catalog output through `visible()`/`HistoryAccessPolicy` (`workflows.rs:171`, `:210`), with the rule "Never authorize it using analyzedAt alone" (`workflows.rs:94-95`) and a passing test proving old stage evidence cannot bypass the policy (`workflows.rs:356-364`). `source_moment` (`automation_flows.rs:1251-1284`) reads the same catalog and returns the earliest evidence/frame timestamp plus a `frameId` with no policy filter — `automation_flows.rs` has no reference to `visible` or `history_access` — yet the flows router is nested on the same local server (`server.rs:1502`). A caller that can list flows therefore learns "this task was first seen at T" and a frame pointer even when that content sits outside the user's history window. Frame contents remain gated behind the policy-checked `/frames/:id` endpoints, so this is metadata-level exposure, but it is inconsistent with the invariant this module documents and tests. Please either filter the catalog through the history policy in `source_moment` (the `FlowsState` already carries the catalog source; the policy is on `AppState`) or document why flows are exempt.

**[P2, pre-existing — not introduced by this PR] `crates/screenpipe-engine/src/routes/workflow_edits.rs:217` — the owner-only edit gate passes any request with a fabricated or absent pipe token.**

`edit` correctly returns 403 for any request carrying pipe permissions (covered by `agent_capabilities_cannot_submit_manual_edits`), and this PR does not change that. But the gate only sees permissions the middleware inserted: `OptionalPipePerms` (`routes/search.rs:22-45`) yields `None` both for requests with no `Authorization` header and for `Bearer sp_pipe_*` tokens not in the registry, because `pipe_permissions_middleware.rs:110-117` deliberately treats unregistered tokens ("likely hallucinated by the model") as regular user requests. So an agent that omits its token — or invents one — is classified as the desktop owner and may apply manual edits, defeating the "Only the desktop owner" boundary for exactly the non-compliant caller this check exists to stop. This behavior is identical on `origin/main`, so it is not a regression of this PR, but the PR ships agent-facing automation (chat skill, Automation Flows) around the same catalog, raising the stakes. Suggested defense in depth: on owner-only mutation endpoints, reject well-formed `sp_pipe_*` tokens that are not in the registry instead of silently reclassifying them as owner requests. At minimum, the handler's threat model ("Owner-authored edits… never metadata supplied by an agent", `workflow_edits.rs:4-5`) deserves a comment acknowledging this path.
