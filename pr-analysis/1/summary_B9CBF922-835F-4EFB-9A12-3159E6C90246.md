# Review slice: `packages/n8n-nodes-screenpipe/nodes/ScreenPipe/ScreenPipe.node.ts`

Focus: API error mapping and displayNames correctness. New 412-line file (all of it is the
PR diff; `git diff origin/main...HEAD` shows one new file). It is the plain n8n node of the
new community package: three operations (`searchContent`, `activitySummary`, `notify`),
`usableAsTool` for AI agents, sharing `screenpipeApi` credentials with the two trigger nodes.

## What the file does

- `execute` (ScreenPipe.node.ts:221-242) loops items, dispatches per operation (line 231),
  tags each output with `pairedItem`, and on error either rethrows or, with
  `continueOnFail`, returns `{ error: message: description }` per item (lines 235-239).
- `searchContent` (247-260) GETs `/search`; `activitySummary` (262-272) GETs
  `/activity-summary`; `notify` (280-333) POSTs to the app's notification server with a
  5 s timeout (line 19, 312) and a Host-header override for `host.docker.internal`
  (300-303). `getJson` (341-378) maps transport failures and non-2xx to `NodeApiError`.

## Findings (detail in comments file)

1. **P2 — `toCapture` silently drops fields for two of six content types**
   (ScreenPipe.node.ts:387-398 vs `routes/content.rs:196-204,100-113`). Input hits name
   their window field `window_title` (node reads only `window_name`); memory hits carry
   `created_at`, not `timestamp`. `withoutEmpty` (380-384) then erases the undefined
   fields with no error or trace. Tests only cover UI and Audio shapes
   (`test/screenpipe.node.test.ts:28-38,118`).
2. **P3 — `shown` is derived by string-matching the server's human message** (line 332).
   Today that is the only shown/held signal (200s always carry `success:true`), but it
   silently breaks on any server wording change, and "Notification already sent"
   (persisted-dedup, routes.rs:490-492) classifies as `shown:false` although the
   notification was shown earlier.
3. **P3 — `new URL(url)` (line 301) sits outside the try** — a malformed `notifyUrl`
   throws a bare `TypeError` instead of the file's `NodeApiError` mapping; caught only by
   the item-level `continueOnFail` catch.
4. **P3 — `getJson` sends no `timeout`** (350-358) while notify does (19, 312); a stuck
   ScreenPipe holds the run indefinitely. Needs a generous value (search/summary can
   legitimately take seconds).
5. **P3 — "Notification ID" description contradicts behavior** (line 105 vs 284-286):
   says "one per run and node" but the synthesized ID includes the item index, so N items
   → N notifications (the test name at `test/screenpipe.node.test.ts:318` states it
   right).
6. **P3 — non-2xx `detail` can render "[object Object]"** (line 370) when the server
   returns `{error: {...}}` as an object.

Not posted (summary-only nits): `subtitle` shows the raw operation value
("searchContent") instead of the display name (line 32); escaped notify bodies can be up
to ~2× the 2000-char slice for markdown-dense text (289-290, 337).

## Fit in the PR / risks

This node is the consumer half of the Automation Flows story (the app side creates flows,
the n8n side runs them and notifies the user). Its main integration risks are exactly the
cross-boundary contracts above, which are mostly verified correct; the exceptions are the
finding-1 field gaps and finding-2's string coupling. Error handling is genuinely good
for an n8n community node — status codes surfaced, `continueOnFail` respected, API key
kept out of error objects — and it is the best-tested node in the package. Nothing here
blocks the PR; the P2 is a small, contained fix plus two test fixtures.
