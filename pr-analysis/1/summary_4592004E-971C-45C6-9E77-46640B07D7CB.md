# Review: `lib/workflows/automation-flows.ts` + its contract tests (PR #1)

## What this slice is

Two new files (184 + 225 lines, both entirely new — verified via `git diff origin/main...HEAD --stat`):

- **`apps/screenpipe-app-tauri/lib/workflows/automation-flows.ts`** — the desktop binding of the host-agnostic `WorkflowsPlatform` flows hooks (`packages/workflows-ui/src/platform.ts:48-57`): `canCreateAutomationFlow`, `createAutomationFlow`, `findAutomationFlow`, `openAutomationFlow`, plus the `screenpipe://flows/<id>` link parser/builders and the Home-window navigation plumbing that opens a Flow's Review Screen.
- **`apps/screenpipe-app-tauri/lib/workflows/automation-flows.test.ts`** — contract tests for that bridge, driven through `mockAutomationFlowsResponse` (`components/automation-flows/mock.ts:170`) so the bridge is exercised against the same shapes the UI gets in the browser mock.

## How it fits the PR

This is the seam between the shared workflows-ui Task Page and the Flow service. Consumers verified in-tree: `components/workflows/integrated-workflows.tsx:43` (spreads the four platform hooks), `components/chat/markdown-block.tsx:225` (chat `screenpipe://flows/` links), `lib/notifications/actions.ts:104-105` (failure-notification deeplinks via `flowIdFromReviewLink` + `flowReviewPage`), and `app/(main)/home/page.tsx:1316` (Home's `navigate` listener calls `followFlowsNavigation`). The engine side of the contract is pinned elsewhere: `components/automation-flows/__tests__/api.test.ts:371-374` reads the engine's bundled `novadesk-support-tickets.json` against `fixtureFlow`, so the chain engine-JSON → fixture → mock → this bridge is covered end to end.

## Type safety (slice focus) — verified

- `CREATION_ERROR: Record<FlowsErrorCode, string>` (`automation-flows.ts:16-33`) is exhaustive over the error-code union in `components/automation-flows/api.ts:167-191`; adding a code there breaks compile here. Non-creation codes are deliberately mapped to the generic copy with a comment (`:24-32`).
- All four platform hooks are declared as `NonNullable<WorkflowsPlatform[...]>` (`:40, :43, :70, :91`), so signature drift against `platform.ts:48-57` fails at compile time. Signatures match (read both).
- `commands.showWindowActivated({ Home: { page } })` (`:128`) type-checks against `ShowRewindWindow = ... | { Home: { page: string | null } }` (`lib/utils/tauri.ts:4499`). I verified the TS type only, not the native Rust parsing of the `page` string.
- URL construction encodes untrusted ids everywhere: `flowReviewLink` (`:98`), `flowReviewPage` (`:114`), route encodes again in `api.ts:281`. `flowIdFromReviewLink` (`:102-110`) requires exact `screenpipe:` protocol + host `flows`, and `decodeURIComponent` sits inside the try (malformed `%` input → `null`). No injection surface found; `emit`/CustomEvent payloads are same-origin DOM only.

## Error propagation (slice focus) — verified

`FlowsApiError.code` → user copy (`CREATION_ERROR`) → `throw new Error(msg, { cause })` (`:46-49`) → surfaced as `cause.message` under the action in `packages/workflows-ui/src/workflow-questions.tsx:268`, which also keeps the answers. The it.each test asserts the Task Page URL is unchanged and no navigation emitted on `not-configured`/`unauthorized`/`unreachable` (test lines 100-106). `rememberFlow` runs before `openFlowReview` (`:50-51`), so the flow id survives even if the handoff fails — recovery path for the timeouts below.

## Notable findings (posted as comments, all P3)

1. **`findAutomationFlow`'s transient-error branch is untested** (`:86-87`): non-404 errors return the remembered flowId anyway ("most likely still there"). Deliberate and documented, but the only branch of the function without a pinning test.
2. **The 10 s timeout resolves like success** (`:141-153`, used at `:164`): if the Review Screen never appears, `createAutomationFlow` resolves normally, `workflow-questions.tsx:268` shows nothing, and the user's busy state just stops — even though the Flow *was* created. Recoverable (the page then offers "open the automation"), but silent. `openFlowReview` also rewrote the address (`:162`) before knowing the handoff worked, so after a reload the user lands on Flows rather than the Task Page.
3. **Rust-source parse in the contract test fails confusingly on rename** (test `:155-165`): if `const DEMO_TASKS` moves/renames, `indexOf` → -1 and the assertion fails as an inscrutable array diff instead of "marker not found".
