## Review: workflow-step-evidence (carousel states, missing-evidence handling, caption overflow)

**`packages/workflows-ui/src/workflow-step-evidence.tsx:73-81` — P2 (keyboard accessibility): arrow-key navigation drops focus whenever the focused control is inside the keyed figure.** The group's `onKeyDown` handles ArrowLeft/ArrowRight for the whole carousel, and keydowns bubble up from descendants — the nav buttons deliberately rely on this (the "keeps keyboard focus on the control that changed the capture" test fires `keyDown` on the Next button). But the figure is keyed `${current.frameId}:${current.timestamp}` (line 78), so every move unmounts and remounts the entire figure subtree. When focus is on the image button (e.g. right after clicking Enlarge/Reduce) or on the placeholder's "Retry screenshot" button (line 128), that DOM node is destroyed and focus falls back to `document.body` — a keyboard user is dropped at the top of the page mid-browse. The comment on line 82 ("focus stays on the control that was used") holds only for the nav controls, which sit outside the figure, and the tests only exercise that case. Please restore focus after a move that started inside the figure (focus the new figure's image button, or the matching placeholder), and add a regression test for arrow keys pressed while the image button has focus.

**`packages/workflows-ui/src/workflow-step-evidence.module.css:11` (with `:49`) — P3: on coarse pointers the nav outgrows the reserved caption space.** `.paged figcaption` reserves `padding-right: 104px` for a nav that is 28+34+28+4 = 94px wide inside a 32px band, but the `pointer: coarse` override grows both nav buttons to 44×44 (line 49), making the nav ≈126px wide and 44px tall against the 32px `min-height`. Long captions can then run up to ~22px underneath the Previous button, and the buttons poke 12px up into the image. Consider widening the reservation inside the same media query (e.g. `padding-right: 130px; min-height: 44px` on `.paged figcaption`) or enlarging only the hit area, not the layout box.

**`packages/workflows-ui/src/workflow-step-evidence.tsx:128` — P3: the placeholder retry button lacks `type="button"`.** Every sibling control sets it explicitly (lines 71, 84, 86, 90, 105, 123); this one defaults to `submit`. Nothing currently wraps this component in a `<form>` (the package's forms live in `workflow-assistant.tsx:448`, `workflow-questions.tsx:293` and `document-block-editor.tsx:326`, none an ancestor here), so it is harmless today — but the first form ancestor turns a "Retry screenshot" click into a form submission. One-word consistency fix.

**`packages/workflows-ui/src/workflow-step-evidence.module.css:44-45` — P3: the labelled recording button can neither shrink nor wrap, so a narrow capture can push it over the nav.** `.recording` carries `flex-shrink: 0` and `.recording.labelled` adds `white-space: nowrap`, while `.paged figcaption` hands 104px of its row to the absolutely-positioned nav. In creation mode the caption row is caption text + the ~100px "View in timeline" button, and the carousel is `width: fit-content` — a portrait capture keeps it narrow (often ≲200px), leaving a content box smaller than the button, which then overflows to the right, straight into the nav's corner. Letting the label wrap (or shrinking the reserved padding when the button is present) would keep the row intact on narrow captures.

Context for the rest of the slice, no action needed: the collapsed-by-default compact frame, the fixed 16:9 missing-evidence placeholder, and the `isEmbeddedScreenshot` gate (embedded fixtures render their own pixels and skip recorder lookup and replay) all look right and are covered by the updated tests; caption overflow itself is properly handled by `min-width: 0; overflow-wrap: anywhere` on the caption span (css line 23), and all new CSS stays on theme tokens so dark mode is safe.
